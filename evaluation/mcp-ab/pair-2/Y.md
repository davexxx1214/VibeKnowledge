## 1. Visualization

### Command, extension host, and browser page

The UI contributes `knowledge.visualizeGraph` as “Knowledge: Visualize Graph” with a graph icon (`package.json:57`), including a graph-explorer title action (`package.json:244`). Its extension command calls `GraphView.createOrShow(context.extensionUri)` and catches synchronous opening errors (`src/extension.ts:643`). The extension supplies both the unified `KnowledgeGraphService` and `StructuralGraphService` to static GraphView setters (`src/extension.ts:242`).

`GraphView.createOrShow` is a singleton-panel operation. A current panel is revealed in column One; if its translated title has changed, `_update()` replaces its HTML, otherwise it only sends fresh ordinary graph data. A new panel enables scripts and retains context while hidden (`src/ui/webview/graphView.ts:157`). Construction generates the HTML, registers browser messages, disposal, and performance-setting changes (`src/ui/webview/graphView.ts:128`). Disposal clears the singleton and subscriptions (`src/ui/webview/graphView.ts:186`).

The page uses packaged `dist/d3.min.js`, the performance helper script, and the relationship-tooltip helper. D3 is loaded as a Webview URI under a nonce-based CSP; this is not a remote graph renderer (`src/ui/webview/graphView.ts:22`, `src/ui/webview/graphView.ts:718`, `src/ui/webview/graphView.ts:751`). On page load, `initGraph()` builds the SVG/zoom behavior and posts `ready`; the host responds with the current performance mode and ordinary graph groups (`src/ui/webview/graphView.ts:1205`, `src/ui/webview/graphView.ts:207`). Host `graphData` carries `{ groups, mode: 'knowledge' }`; the client uses the groups rather than branching on that mode (`src/ui/webview/graphView.ts:263`, `src/ui/webview/graphView.ts:1287`).

### Ordinary versus advanced views

Ordinary groups are deliberately independent views, not one merged dependency graph. `KnowledgeGraphService.getGroups()` preserves repeated symbols across framework/module/feature groups, while aggregate search/export snapshots deduplicate them (`src/services/knowledgeGraphService.ts:147`). GraphView maps each group's entities, observations, descriptions, provenance, structural keys, evidence, confidence and structural paths into a browser view model (`src/ui/webview/graphView.ts:457`). Thus a layout-only change must not replace these groups with the deduplicated aggregate or cache old source/evidence objects.

The page sorts groups by `order`, then name; creates one sidebar button per group; selects the previously selected key if present, otherwise the first group. Selection writes the key to Webview state, updates the active button, and renders only that group's nodes/relations (`src/ui/webview/graphView.ts:1372`, `src/ui/webview/graphView.ts:1423`, `src/ui/webview/graphView.ts:1449`). Empty group lists stop animations/simulation, clear geometry/cache and show the empty state. Selecting a group with no entities also shows empty state (`src/ui/webview/graphView.ts:1378`, `src/ui/webview/graphView.ts:1495`).

Advanced structure is requested separately: the toolbar offers boundary/community/file aggregation; its button sends `requestStructuralOverview` with the selected level (`src/ui/webview/graphView.ts:1101`, `src/ui/webview/graphView.ts:2091`). The host reads the structural graph and calls `aggregateStructuralGraph` with a limit of 80, then adapts it to the same group model (`src/ui/webview/graphView.ts:324`). Aggregate nodes retain their level, file membership and aggregate ID; aggregate relationships retain raw structural hops and counts (`src/ui/webview/graphView.ts:518`). This preserves a common rendering pipeline without treating an aggregate as an ordinary curated symbol.

Navigation semantics depend on provenance and must survive any renderer change:

- Double-click an aggregate node to request its raw slice; double-click a structural node to open its source; double-click an ordinary node to open its source. Shift-double-click or right-click an ordinary node with a structural key requests its structural neighbors (`src/ui/webview/graphView.ts:1761`).
- Double-click a relationship or relationship label only drills down when a nonempty `structuralPath` is present (`src/ui/webview/graphView.ts:1601`, `src/ui/webview/graphView.ts:1685`). The host matches hops against current relationships by source, target, verb and exact source location; it does not blindly trust the supplied hops as graph entities (`src/ui/webview/graphView.ts:340`, `src/ui/webview/graphView.ts:627`). A stale path may therefore produce an empty slice rather than an exception.
- Entity neighbors use both directions at depth 1, deduplicate relationships, limit them to 120 and entities to 80, then filter edges to included endpoints (`src/ui/webview/graphView.ts:365`). Aggregate drill-down uses supplied file membership when present, otherwise file/boundary matching; it limits to 80 entities and 120 internal relationships (`src/ui/webview/graphView.ts:407`). The path-drill-down implementation has no corresponding 80/120 cap (`src/ui/webview/graphView.ts:349`).
- Ordinary jumps resolve the knowledge entity ID, refuse external nodes, open under the first workspace folder and convert one-based source lines to VS Code ranges. Structural jumps resolve the structural key against the current graph and similarly skip external nodes (`src/ui/webview/graphView.ts:647`, `src/ui/webview/graphView.ts:687`).

The host posts `structuralGroup`; the page removes every existing `__structural_` group, inserts the new one, selects it and shows a status message. There is one transient advanced slot, not drill-down history (`src/ui/webview/graphView.ts:1401`). Aggregation keys are stable per level; raw drill-down group keys include `Date.now()` (`src/ui/webview/graphView.ts:520`, `src/ui/webview/graphView.ts:576`). A later ordinary `graphData` replaces the entire list, dropping that advanced slot and falling back to the first ordinary group if the selected structural key is absent (`src/ui/webview/graphView.ts:1287`, `src/ui/webview/graphView.ts:1372`). This happens on the page's refresh button and on re-executing the visualization command against an existing same-title panel; it is distinct from merely unhiding the retained page (`src/ui/webview/graphView.ts:157`, `src/ui/webview/graphView.ts:2086`).

### Performance selection changes execution, not graph content

`knowledgeGraph.visualization.performanceMode` is machine-scoped, defaults to `low`, and accepts `low`/`high` (`package.json:325`). The page immediately applies a changed selection, disables the selector, then sends `setPerformanceMode`; a host response applies the authoritative mode and re-enables it (`src/ui/webview/graphView.ts:2176`, `src/ui/webview/graphView.ts:1283`). The host validates the two values, updates global configuration, reports saving errors and always echoes the effective configuration in `finally`. Settings changes also push that value (`src/ui/webview/graphView.ts:150`, `src/ui/webview/graphView.ts:300`). A rejected write therefore rolls an optimistic UI choice back. Mode changes rerender the selected group using the same geometry cache (`src/ui/webview/graphView.ts:2077`).

Both modes build a D3 force simulation from fresh shallow-copied nodes and relationships, with link, charge, center and collision forces (`src/ui/webview/graphView.ts:1504`, `src/ui/webview/graphView.ts:1552`). Their execution differs:

- **Low:** stop the normal simulation timer; if cached layout is not settled, use explicit `tick()` batches on animation frames. Each batch yields after approximately 6 ms; completion occurs at 120 ticks, 600 ms accumulated compute time, or cooling, then alpha is set to zero. Geometry is explicitly updated because manual D3 ticks do not emit tick/end events. Exceptions stop the layout and call the error handler (`src/ui/webview/graphPerformanceScript.ts:46`). There are no particles, flowing-link class, glow or label halo; CSS disables animation/transitions; fit and hover changes are immediate (`src/ui/webview/graphView.ts:1080`, `src/ui/webview/graphView.ts:1594`, `src/ui/webview/graphView.ts:1619`, `src/ui/webview/graphView.ts:1668`, `src/ui/webview/graphView.ts:1727`, `src/ui/webview/graphView.ts:2073`). Low does not mean “no layout calculation” or “no interaction.”
- **High:** ordinary force simulation may run unless hidden or a settled layout was restored. It has animated hover/fit, glow, flowing agent links, and one particle loop for the selected group throttled to 30 fps. Particle positions use cached path lookup and cache path lengths on simulation end (`src/ui/webview/graphView.ts:1154`, `src/ui/webview/graphView.ts:1572`, `src/ui/webview/graphView.ts:1624`, `src/ui/webview/graphView.ts:1922`). Cached settled graphs need not reheat merely because mode changed.
- **Dragging:** low mode cancels pending static layout, stops alpha, directly moves only the dragged node with zero velocity and redraws its affected geometry; high mode reheats physics. Both release `fx`/`fy` and save the layout at drag end. Dragging disables auto-fit (`src/ui/webview/graphPerformanceScript.ts:91`, `src/ui/webview/graphView.ts:1950`). User-initiated zoom also disables auto-fit; normal zoom range and fitted scale are clamped to 0.1–4 (`src/ui/webview/graphView.ts:1360`, `src/ui/webview/graphView.ts:2053`).

### State lifetime and correctness boundaries

| Event/state | Actual behavior and limit |
| --- | --- |
| Group switch or mode rerender | Old loops/simulation are stopped and old geometry saved before teardown. The cache is keyed by group and a sorted topology signature: node IDs plus edge endpoint IDs/verbs. It restores x/y, zoom transform, settled status, alpha and auto-fit permission, but not velocities, pins or source/evidence objects. Metadata-only changes can reuse geometry while new objects supply current content (`src/ui/webview/graphView.ts:1479`, `src/ui/webview/graphView.ts:1556`, `src/ui/webview/graphPerformanceScript.ts:7`). |
| Cache limits | LRU maximum 8 groups and 2,000 total nodes; reject oversized groups, over 16,000 links per entry or nonfinite node positions. Topology changes invalidate retrieval. Raw structural drill-down's timestamp keys hinder reuse between newly requested slices (`src/ui/webview/graphPerformanceScript.ts:8`, `src/ui/webview/graphView.ts:576`). |
| Reveal/re-execute command | Same-title existing panel retains its document/cache but receives ordinary groups again. Ordinary selected keys survive when present, and compatible geometry is restored. Advanced selection does not survive that ordinary-data replacement. Title-change HTML replacement discards the page-local cache (`src/ui/webview/graphView.ts:157`, `src/ui/webview/graphView.ts:199`, `src/ui/webview/graphView.ts:1372`). |
| Webview state versus close/reopen | Only `{ selectedGroupKey }` is passed to `setState` and read at initialization; geometry and advanced contents are not serialized (`src/ui/webview/graphView.ts:1141`, `src/ui/webview/graphView.ts:1150`, `src/ui/webview/graphView.ts:1454`). A recreated document can use an available saved key only if new groups contain it. Closing disposes the panel, and a fresh panel has a new in-memory cache; source inspection found no panel serializer or extension-level selected-view persistence. Do not promise selection/layout recovery across closing/restarting. Global performance preference does survive new panels (`src/ui/webview/graphView.ts:186`, `src/ui/webview/graphView.ts:300`). |
| Hide/unhide without replacing page | Retained context preserves groups, geometry and ordinary/advanced selection. `visibilitychange` stops particles without dropping their resume callback, pauses static work, stops simulation, interrupts SVG transitions, clears fit/resize timers and saves geometry. On becoming visible, low resumes unfinished static work; high restarts only above minimum alpha; particles resume once. `beforeunload` cancels work rather than persisting geometry (`src/ui/webview/graphView.ts:1254`). |

Important change boundaries and failure risks:

1. Preserve the separation of selection state, bounded geometry cache and persistent machine preference. In-progress alpha/settled/auto-fit status is necessary: restoring coordinates alone can incorrectly freeze a partially laid-out graph. The signature intentionally ignores prose and evidence, so storing whole old entities would introduce stale descriptions even when topology matches (`src/ui/webview/graphPerformanceScript.ts:11`, `src/ui/webview/graphView.ts:1575`). The empty-list branch clears the in-memory selected key but does not clear `vscode.setState`; that asymmetry matters if persistence is changed (`src/ui/webview/graphView.ts:1378`).
2. Preserve cancellation and single-loop ownership when changing groups, performance modes or visibility. Otherwise old callbacks can update detached geometry or continue burning CPU. Resize is debounced 120 ms; low fits while high reheats when visible (`src/ui/webview/graphView.ts:1210`). **Risk/inference:** hiding during the high-mode initial one-second auto-fit cancels the timer, and the unhide branch does not recreate it; test the desired fit behavior when hidden before first fit (`src/ui/webview/graphView.ts:1262`, `src/ui/webview/graphView.ts:1940`). Cache restoration is view continuity, not exact force-simulation replay, since velocities are absent.
3. Preserve entity/link IDs and valid endpoints, provenance-specific gestures, and raw source-location identity. These govern D3 force resolution, relationship labels/particle lookup, tooltips, and source jumps. The displayed cyclic icon detects direct reciprocal edges, not arbitrary graph cycles; do not conflate it with the structural-analysis cycle algorithm (`src/ui/webview/graphView.ts:1524`, `src/ui/webview/graphView.ts:1588`).
4. Missing structural service, invalid drill-down input and thrown structural operations produce `structuralError` plus a VS Code warning; the client hides loading and shows temporary status without replacing the current graph (`src/ui/webview/graphView.ts:450`, `src/ui/webview/graphView.ts:1296`). **Risk/inference:** requests/responses have no correlation IDs, so a late response could select a structural view after the user selected an ordinary group (`src/ui/webview/graphView.ts:223`, `src/ui/webview/graphView.ts:446`, `src/ui/webview/graphView.ts:1401`).
5. Synchronous `renderGraph` exceptions and low-layout failures have explicit error UI that stops work; choosing a group reruns rendering and clears that error (`src/ui/webview/graphView.ts:1449`, `src/ui/webview/graphView.ts:1465`, `src/ui/webview/graphView.ts:1480`). This is not universal protection: `initGraph()` precedes `ready` outside that catch, and high-mode asynchronous tick/particle callbacks are not wrapped there (`src/ui/webview/graphView.ts:1205`, `src/ui/webview/graphView.ts:1632`, `src/ui/webview/graphView.ts:1920`). **Risk/inference:** a missing D3 bundle can prevent readiness entirely. Preserve the packaged dependency/CSP contract and avoid claiming all failures become the render-error screen.

## 2. Generate Copilot Instructions

### Actual UI and file-writing path

The command is contributed as `knowledge.generateCopilotInstructions` (“Knowledge: Generate Copilot Instructions,” file-code icon), beside Cursor and Generate All (`package.json:80`). Its extension registration awaits `entityCommands.generateCopilotInstructions()` with an outer logged/error-message catch (`src/extension.ts:680`). EntityCommands is constructed with the legacy entity/relation/observation services plus the unified KnowledgeGraphService; it constructs AIIntegrationService with only the three legacy services (`src/extension.ts:246`, `src/ui/commands/entityCommands.ts:23`).

The handler takes the **first** workspace folder, with no target chooser or active-editor routing; no workspace produces a localized error and returns. Inside its try block it collects graph data and passes it with the first folder's filesystem path to the generator (`src/ui/commands/entityCommands.ts:1255`). `getGraphData()` gets the unified snapshot and visits every entity to collect `{ entityId, entityName, content }` observations, returning entities, relations, observations and `sourceType: 'knowledge'` (`src/ui/commands/entityCommands.ts:42`).

The service ensures `<workspaceRoot>/.github` exists, computes `copilot-instructions.md`, calls a no-argument content builder, writes UTF-8 synchronously, and returns the path (`src/services/aiIntegrationService.ts:71`). The builder calls a common router with hard-coded English and the title `# VibeKnowledge Agent Instructions` (`src/services/aiIntegrationService.ts:404`). There is no model/API request in this generation path.

After a successful write, the handler offers “Open file” or “Show in folder.” The former opens/displays that returned path, the latter executes `revealFileInOS`; dismissing the message leaves the generated file in place (`src/ui/commands/entityCommands.ts:1269`). A display-only defect exists: the handler passes `.github/<basename>` to the success formatter, while both English and Chinese formatters prepend `.github/` again. The notification consequently duplicates `.github/`; the actual destination and open/reveal actions are correct (`src/ui/commands/entityCommands.ts:1271`, `src/i18n/en.ts:293`, `src/i18n/zh.ts:294`).

**Causal inference:** changing graph entities/observations, stack declarations or a scenario currently cannot make the generated Copilot text more specific. Changing the shared router would affect both generators; making only Copilot specific requires treating their shared implementation deliberately. Despite being content-inert, graph collection remains a runtime dependency of the **UI**: if snapshot/observation collection throws, generation never reaches mkdir/write. Empty graph data has no rejection gate (`src/ui/commands/entityCommands.ts:1262`). Direct service calls can generate without graph data or functional service methods, as the unit-test fixture also demonstrates (`src/services/aiIntegrationService.test.ts:42`).

### Shared paths and intended use

Cursor writes `<workspaceRoot>/.cursorrules` and uses the same `buildAgentKnowledgeRouterContent`; only the intended locale/title parameters differ. Service-level `generateAllAIConfigs` sequentially invokes Cursor then Copilot and returns their two paths (`src/services/aiIntegrationService.ts:58`, `src/services/aiIntegrationService.ts:89`, `src/services/aiIntegrationService.ts:101`). The UI Generate All command does **not** call that service wrapper: it separately collects one snapshot, runs those same two individual methods in a non-cancellable notification progress callback, then offers to view either file (`src/ui/commands/entityCommands.ts:1290`). Thus changing the individual builders affects single-command, UI-batch and service-batch use; changing only the service batch method would not change UI-batch behavior.

There is also an indirect regeneration entry: switching an AI scenario optionally executes `knowledge.generateAllAIConfigs` (`src/commands/scenarioCommands.ts:62`). It reaches the same compact builders, so the currently selected scenario does not get incorporated merely by accepting that prompt.

The generated file is a compact instruction router for a future coding agent. It tells that agent to use focused MCP `query_graph` for architecture/unfamiliar/cross-file/dependency/impact tasks; expand with `get_entity`, `get_neighbors` or `shortest_path`; request evidence only when auditing; fall back to the agent-context index and one best-matching group when useful MCP results are unavailable; avoid the complete human audit report by default; skip graph navigation for already-known small tasks; verify current source before edits/tests; and never edit `graph.sqlite` (`src/services/aiIntegrationService.ts:411`).

These are **instructions in text**, not generator actions. The generator does not query MCP, validate tool availability, open the named knowledge artifacts, refresh graphs, inspect project source, execute tests or change the database. It does not prove Copilot consumed the file. Its concrete effect is mkdir/write plus the user's optional open/reveal action (`src/services/aiIntegrationService.ts:71`, `src/ui/commands/entityCommands.ts:1269`). No external product behavior is assumed here.

### Existing destinations and failure contract

There is no existing-file read, comparison, merge, confirmation, backup, temporary-file rename or exclusive-create flag: `fs.writeFileSync(..., 'utf-8')` directly replaces the destination's contents. Existing custom instructions are not preserved (`src/services/aiIntegrationService.ts:71`). **Risk/inference:** this is not an atomic/transactional update; a write failure can leave an already-created directory or a truncated/partial destination depending on when the underlying failure occurs. A directory at `.github`, permissions, or destination-shape problems can reject the async method via its synchronous filesystem operations. The service has no local recovery/catch.

The UI's one try/catch covers graph collection, generation, the success prompt, opening and revealing; it reports a localized “failed to generate” error and does not rethrow (`src/ui/commands/entityCommands.ts:1262`). Thus a successful write followed by an open/reveal failure can still display a generation error, with the file already present. The extension catch is an outer fallback, not the normal recipient of errors swallowed by EntityCommands (`src/extension.ts:680`). There is no rollback in either layer.

Both batch paths write Cursor first, then Copilot (`src/services/aiIntegrationService.ts:89`, `src/ui/commands/entityCommands.ts:1306`). A Cursor failure prevents the Copilot step. A Copilot failure leaves the completed Cursor write, and possibly a newly created `.github` directory; no all-or-nothing behavior is implemented. The UI success notice follows completion of both awaited steps, and the service wrapper returns no complete path array on rejection. These semantics matter before adding more project reads or asynchronous generation work.

Those tests are relevant if stack extraction is reconnected for project-specific output; they are **not evidence that present instruction files contain stack data**.

Targeted searches found no EntityCommands/extension/scenario generation tests and no tests of either Generate All path. Important missing assertions are: supplied GraphData has no effect (or a future explicit project-specific contract), graph-collection exceptions before writing, no/multiple workspace behavior, exact destination path and UTF-8 content, existing custom-file overwrite/merge policy, mkdir/write failure and partial effects, batch ordering/partial success, success-prompt dismissal and open/reveal errors, the duplicate notification prefix, and actual locale behavior. The marker test confirms that one template is excluded, not all possible scenario/config input invariance. Existing tests contain negative graph-dump expectations that should be reconsidered intentionally if specificity is introduced; blindly wiring older full builders back in would change compactness, dependency requirements and both-file behavior at once.

## Overall conclusion

The visualization change spans a host/browser protocol, three different state lifetimes and two layout schedulers; it cannot safely be assessed as a rendering-file-only edit. Instruction specificity, by contrast, is currently absent from the active content path even though the UI still pays for graph collection and the class retains legacy analysis/template helpers. Preserve or explicitly revise these contracts with tests at the UI/message/filesystem boundaries; the existing isolated helper tests do not establish end-to-end behavior.
