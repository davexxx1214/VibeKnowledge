## 1. Visualization

### Command, host, and page flow

The user command is `knowledge.visualizeGraph`, contributed as “Knowledge: Visualize Graph” and exposed on the Knowledge Graph Explorer title toolbar (`package.json:57`, `package.json:244`). Its registered handler calls `GraphView.createOrShow(context.extensionUri)` and catches synchronous opening failures (`src/extension.ts:643`). Activation injects separate Knowledge Graph and structural-graph services into GraphView (`src/extension.ts:242`). This is not a browser fetching graph files itself.

GraphView owns one static current panel. New panels enable scripts and `retainContextWhenHidden`; the constructor supplies HTML, subscribes to page messages, panel disposal, and performance-setting changes (`src/ui/webview/graphView.ts:128`, `src/ui/webview/graphView.ts:157`). An existing panel is revealed; if its localized title is unchanged the host posts fresh ordinary graph data without replacing HTML. A changed title triggers `_update()`, which replaces HTML. Disposal clears the static reference and registered disposables (`src/ui/webview/graphView.ts:159`, `src/ui/webview/graphView.ts:186`, `src/ui/webview/graphView.ts:199`).

The HTML loads packaged `dist/d3.min.js` through a webview URI, under a nonce/source-restricted CSP (`src/ui/webview/graphView.ts:718`, `src/ui/webview/graphView.ts:751`). Page load calls `initGraph()` and then sends `ready`; the host answers with `performanceMode` and `graphData` (`src/ui/webview/graphView.ts:1205`, `src/ui/webview/graphView.ts:205`). Page message dispatch applies settings, replaces ordinary groups, or inserts an on-demand structural group (`src/ui/webview/graphView.ts:1280`). Toolbar refresh sends `refresh`, whose host handler resends groups; it is not a request to regenerate structural source data (`src/ui/webview/graphView.ts:219`, `src/ui/webview/graphView.ts:2086`).

### Ordinary groups and advanced structural views

Ordinary groups come from `KnowledgeGraphService.getGroups()`, not the service's de-duplicated aggregate snapshot. The service deliberately preserves repeated symbols in independent agent framework/module/feature groups (`src/services/knowledgeGraphService.ts:48`, `src/services/knowledgeGraphService.ts:147`). GraphView maps each group's entities and relations into page models, including observations, source/provenance, structural keys, evidence, confidence, and structural paths (`src/ui/webview/graphView.ts:457`). A missing Knowledge Graph service produces an empty groups array, rather than a structural overview (`src/ui/webview/graphView.ts:458`).

The page sorts groups by order then name, creates sidebar buttons using text content, chooses the saved selected key if present, otherwise the first group, and renders exactly that group (`src/ui/webview/graphView.ts:1372`, `src/ui/webview/graphView.ts:1423`, `src/ui/webview/graphView.ts:1449`). Selecting a group saves its key, updates the active button, and calls `renderGraph`. That render stops old layout/particle work, saves the outgoing layout, clears its SVG content, and constructs a new simulation from cloned entity/link objects (`src/ui/webview/graphView.ts:1479`, `src/ui/webview/graphView.ts:1504`, `src/ui/webview/graphView.ts:1552`). Thus D3's endpoint/geometry mutation does not replace the host's graph model.

Advanced structure is an explicit, separate on-demand route. The aggregation selector's current value is sent only when the structural button is clicked (`src/ui/webview/graphView.ts:2091`, `src/ui/webview/graphView.ts:2173`). The host reads the structural service, aggregates at the requested boundary/file/community level with limit 80, converts the result to a normal group-shaped page model, and sends `structuralGroup` (`src/ui/webview/graphView.ts:324`, `src/ui/webview/graphView.ts:518`). The page removes previous `__structural_` groups, appends and selects the new one, and reports its counts; it retains ordinary groups but only one current structural group (`src/ui/webview/graphView.ts:1401`). This uses the same rendering and performance machinery as ordinary groups, not an independent renderer or permanent project group mutation.

Additional navigation is causal, not merely decorative:

- Double-clicking an edge or its label with a nonempty structural path sends `drillDownRelation`. The host matches current raw relations by source, target, verb, file and line range; it displays the matching endpoint slice (`src/ui/webview/graphView.ts:1601`, `src/ui/webview/graphView.ts:1685`, `src/ui/webview/graphView.ts:340`, `src/ui/webview/graphView.ts:627`). A stale, nonempty path can match nothing and yield an empty slice; only an absent/empty path is explicitly rejected.
- A curated entity normally opens its code location; Shift-double-click or context-menu on a keyed curated entity requests structural neighbors. The host uses bidirectional depth-one impact, de-duplicates relations, caps at 120 relations/80 entities, then removes links to omitted endpoints (`src/ui/webview/graphView.ts:1761`, `src/ui/webview/graphView.ts:1791`, `src/ui/webview/graphView.ts:365`).
- Aggregate-node double-click sends its aggregation ID, level and files. The host selects matching files/entities, caps at 80 entities and 120 internal relations, then returns raw structure. Raw structural-node double-click resolves the structural key and opens code (`src/ui/webview/graphView.ts:1761`, `src/ui/webview/graphView.ts:407`, `src/ui/webview/graphView.ts:687`). Raw slice group keys use `Date.now()`, whereas aggregate keys are level-based (`src/ui/webview/graphView.ts:520`, `src/ui/webview/graphView.ts:576`). Reopening a raw slice is therefore not a stable group-cache identity.

Structural reads require an existing artifact; `StructuralGraphService.read()` throws when absent (`src/services/structuralGraph/structuralGraphService.ts:63`). Host structural operations catch errors, send `structuralError` and a warning. The page shows transient status and hides loading, rather than replacing the currently rendered group on failure (`src/ui/webview/graphView.ts:450`, `src/ui/webview/graphView.ts:1296`). The relation-path route does not apply the overview/neighbor 80/120 caps, so those caps must not be assumed universal (`src/ui/webview/graphView.ts:340`).

### Performance mode actually changes work

The setting is `knowledgeGraph.visualization.performanceMode`; only exact `high` is interpreted as high, otherwise low (`src/ui/webview/graphView.ts:300`, `src/ui/webview/graphPerformanceScript.ts:3`). The page optimistically applies the selector, disables it, and posts `setPerformanceMode`. The host validates low/high, writes `ConfigurationTarget.Global`, reports save failures, and always posts the effective setting back; that response re-enables the selector and can roll back the optimistic choice (`src/ui/webview/graphView.ts:309`, `src/ui/webview/graphView.ts:2176`, `src/ui/webview/graphView.ts:1283`). External Settings changes also post the effective mode (`src/ui/webview/graphView.ts:150`). This preference is separate from project graph data and page selection.

Applying a changed mode re-renders the current group, retaining geometry through the layout cache if its topology still matches (`src/ui/webview/graphView.ts:2077`). Low mode is not “no layout”: it stops D3's normal timer and runs explicit ticks in requestAnimationFrame batches, targeting roughly 6 ms per batch, with 120-tick or 600-ms accumulated compute budget or cooling termination. It explicitly redraws after ticks because manual D3 ticks do not emit tick/end events. On completion it sets alpha to zero, optionally fits, and saves (`src/ui/webview/graphPerformanceScript.ts:46`, `src/ui/webview/graphView.ts:1931`). The budgets cannot interrupt a single expensive tick; “6 ms” is a yield target, not a hard latency guarantee.

High mode retains animated physics when unsettled, uses a single throttled 30-fps particle loop, animates agent-edge flow, adds glow, text/label decoration and hover transitions, and animates fit for 750 ms. Low mode omits those particle/decorative workloads and uses immediate fit/hover changes (`src/ui/webview/graphView.ts:1154`, `src/ui/webview/graphView.ts:1572`, `src/ui/webview/graphView.ts:1590`, `src/ui/webview/graphView.ts:1613`, `src/ui/webview/graphView.ts:1667`, `src/ui/webview/graphView.ts:1720`, `src/ui/webview/graphView.ts:2073`). Labels, topology, tooltips and navigation remain present in low mode; it is a presentation/work policy, not a different knowledge dataset.

Low-mode dragging stops layout, moves only the dragged node, zeroes its velocity, redraws it and incident edges, releases fixed coordinates on end, and saves. High-mode dragging reheats the simulation (`src/ui/webview/graphPerformanceScript.ts:91`, `src/ui/webview/graphView.ts:1823`, `src/ui/webview/graphView.ts:1950`). User zoom/drag disables automatic fitting. Initial low layout fits on completion if allowed; high mode schedules an initial fit after one second. Resize is debounced 120 ms, updates the center force, fits in low mode, or reheats high mode if visible (`src/ui/webview/graphView.ts:1360`, `src/ui/webview/graphView.ts:1933`, `src/ui/webview/graphView.ts:1210`). Consequently a resize is allowed to alter the user's view; geometry restoration is not a promise that no later event can change it.

### Which state survives?

| State/event | Implemented behavior and boundary |
| --- | --- |
| Selected group | Only `{ selectedGroupKey }` is written with `vscode.setState`; startup reads that field (`src/ui/webview/graphView.ts:1150`, `src/ui/webview/graphView.ts:1453`). Each nonempty ordinary data replacement resolves the key against available groups and falls back to the first. An empty replacement sets the in-memory key to null and clears geometry, but does not explicitly clear the stored webview key (`src/ui/webview/graphView.ts:1378`). |
| Group switches / mode switches | Page-local cache stores node x/y, zoom x/y/scale, alpha, settled status and auto-fit eligibility, not observations/evidence or full source objects. Signature is sorted node IDs and sorted endpoint/verb tuples; prose changes keep geometry, topology changes invalidate it. LRU limits are eight groups and 2,000 total cached nodes; individual entries also reject oversized link sets/nonfinite positions (`src/ui/webview/graphPerformanceScript.ts:7`). Outgoing layout is saved by a closure tied to its own group/simulation, even though selection has already changed (`src/ui/webview/graphView.ts:1485`, `src/ui/webview/graphView.ts:1574`). Unfinished alpha/state must survive quick switches so an incomplete layout resumes rather than freezes. Velocities/fixed positions are not cached. |
| Reveal existing panel, same title | HTML and cache survive, but `graphData` still replaces the group list. Ordinary selection can survive; a transient structural group is absent from that new list, so structural selection falls back to an ordinary group (or empty). Geometry is then restored only on a valid cache hit (`src/ui/webview/graphView.ts:159`, `src/ui/webview/graphView.ts:1372`). |
| HTML replacement / close then reopen | `_update()` rebuilds page JavaScript, so its Map cache and transient structural group data disappear. A persisted webview key can only select a supplied group; it cannot reconstruct an advanced view. A disposed panel is recreated, and there is no explicit cross-panel geometry persistence in this implementation. Do not equate `getState/setState` with a guaranteed close/reopen graph-view restore. The global performance setting is explicitly reread into new HTML (`src/ui/webview/graphView.ts:186`, `src/ui/webview/graphView.ts:199`, `src/ui/webview/graphView.ts:1140`). |
| Hide and reveal page without a host data replacement | Retained page context keeps DOM/groups, selected key and cache. Visibility handling pauses particle/static/simulation work, interrupts transitions, cancels fit/resize timers, saves layout, then resumes low static work or still-hot high physics plus particles when visible (`src/ui/webview/graphView.ts:1254`). Settled high physics is not needlessly restarted. Canceled high auto-fit timers are not re-created by the visibility handler. |
| Unload | Stops particle/static/simulation work and clears timers; it does not serialize the layout cache (`src/ui/webview/graphView.ts:1272`). |

### Correctness boundaries and existing coverage

Changing view memory or animation requires preserving independent group IDs and endpoint integrity, fresh metadata with geometry-only caching, outgoing-versus-incoming closure ownership, invalidation/eviction, unfinished-layout state, and cancellation of replaced/hidden work. Stable raw entity IDs are SHA-1-derived from structural keys; relation identities include source locations, while newly requested raw groups have unstable time-based keys (`src/ui/webview/graphView.ts:564`, `src/ui/webview/graphView.ts:627`). Increasing persistent state cannot simply copy the graph model without introducing stale evidence/data retention and large-state risks. A change to reveal behavior must decide explicitly whether advanced structure should continue to be transient.

Rendering catches errors around group rendering and catches low-mode batch failures via `showRenderError`, which stops work and exposes an error view (`src/ui/webview/graphView.ts:1449`, `src/ui/webview/graphView.ts:1465`, `src/ui/webview/graphPerformanceScript.ts:71`). These are not universal page error boundaries: initial D3 setup precedes `ready` without that try/catch, and high-mode tick/particle callbacks are not wrapped by the low-mode failure handler (`src/ui/webview/graphView.ts:1205`, `src/ui/webview/graphView.ts:1303`, `src/ui/webview/graphView.ts:1632`, `src/ui/webview/graphView.ts:1920`). Missing assets or malformed endpoints can therefore fail differently. Code navigation additionally depends on resolving current keys and first-workspace file/line coordinates; external entities are excluded and open failures are handled (`src/ui/webview/graphView.ts:647`, `src/ui/webview/graphView.ts:687`).

Inspected test-to-risk mapping:

- `src/ui/webview/graphView.test.ts:58` checks manifest low default, low/high enum, machine scope, localized choices and compilation of the generated inline script. `:79` checks global save, unchanged HTML on reveal and high setting on a recreated panel. `:96` checks external configuration notifications, failed-save response and invalid-mode rejection. These use a mocked VS Code panel, not a running browser; “reopened” here proves performance preference, not camera or selected-group restoration.
- `src/ui/webview/graphPerformanceScript.test.ts:49` and `:65` exercise actual embedded helpers in a VM with simulated frames/time: yielding, budget/cooling completion and no remaining work. `:81` tests hide/pause, single resumption and replaced-layout cancellation; `:95` tests failure cleanup. These do not execute GraphView's complete visibility listener or real D3.
- `src/ui/webview/graphPerformanceScript.test.ts:105`, `:119`, `:133` cover geometry copied across prose/order changes, invalidation on verb/node changes, LRU/node limits and unfinished alpha/auto-fit state. `:142` covers direct low dragging versus high restart and save callback. Missing cases include full renderer switch/restore, changed endpoints/duplicate edge identity, rejected nonfinite/oversized entries, and real fit/zoom/resize timing.
- `src/services/knowledgeGraphService.test.ts:60` verifies repeated symbols remain independently represented in visualization groups and can still be resolved; `:11` distinguishes aggregate de-duplication. These support retaining `getGroups`, not replacing it with `getSnapshot`.
- `src/ui/webview/graphWebviewClientScript.test.ts:6` executes tooltip formatting with provenance, evidence and structural-hop count. `src/services/structuralGraph/structuralAnalysis.test.ts:15`, `:60`, `:113` test source-backed impact/path results, limited/truncated aggregation and containment navigation. They do not test webview structural message routing, replacement/fallback, current-source hop matching, missing artifacts or code-opening failures.

Consequential gaps: no full-page test in the inspected visualization suites proves camera/selection survival across group switches, title reload, close/reopen or hiding; no test proves advanced-group behavior on ordinary `graphData`; no real-browser timing test proves particle-loop cleanup, fit cancellation or responsiveness under large graphs. These are the highest-risk interaction regressions for the proposed change, even though helper tests already cover much of the intended policy.

## 2. Generate Copilot Instructions

### Actual command and write path

`knowledge.generateCopilotInstructions` is contributed as “Knowledge: Generate Copilot Instructions” (`package.json:86`). The extension registers an async command that awaits `entityCommands.generateCopilotInstructions()` and has an outer logging/error-message catch (`src/extension.ts:680`). Activation constructs EntityCommands with entity, relation, observation and unified Knowledge Graph services; EntityCommands constructs AIIntegrationService from the first three (`src/extension.ts:245`, `src/ui/commands/entityCommands.ts:23`).

The command chooses `workspaceFolders?.[0]`, not the active editor's containing root and not a user-picked destination. Without one it shows the localized no-workspace error and returns. Otherwise it builds `GraphData`, passes it with the root to the service, waits for a returned file path, and offers “Open file” or “Show in folder” (`src/ui/commands/entityCommands.ts:1255`). There is no graph-source picker, generation-options UI, overwrite confirmation or per-file progress UI in this command.

`getGraphData()` reads the unified snapshot and each entity's observations, flattening entity ID/name/content and adding `sourceType: 'knowledge'` (`src/ui/commands/entityCommands.ts:42`). The service then ensures `<root>/.github` exists, builds content, writes UTF-8 with `fs.writeFileSync` to `<root>/.github/copilot-instructions.md`, and returns that path (`src/services/aiIntegrationService.ts:71`). The async signature does not make that filesystem work asynchronous.

### Apparent inputs versus output dependencies

The current generated content is a small fixed English router, not project-specific architecture documentation. `generateCopilotInstructions` names its argument `_graphData`, does not read it, and calls a no-argument builder. That builder always passes `'en'` and the title `# VibeKnowledge Agent Instructions` to `buildAgentKnowledgeRouterContent`; the latter joins fixed strings (`src/services/aiIntegrationService.ts:71`, `src/services/aiIntegrationService.ts:404`, `src/services/aiIntegrationService.ts:411`).

These are intended instructions consumed later by an AI tool, not operations performed during generation. Existence or correctness of the named dependencies is not guaranteed by successful file creation.

### Shared paths and misleading adjacent behavior

Cursor generation writes `.cursorrules` and calls `buildCursorRulesContent`, which invokes the same router with a Cursor-specific heading (`src/services/aiIntegrationService.ts:58`, `src/services/aiIntegrationService.ts:101`). Thus changing the shared router affects both output types; changing only Copilot's wrapper does not automatically update Cursor. Both currently ignore graph data. Also, Cursor's branch compares `getLocale()` with `'zh'`, while the actual i18n helper returns `'zh-CN'` or `'en-US'` (`src/services/aiIntegrationService.ts:102`, `src/i18n/i18nService.ts:126`, `src/i18n/i18nService.ts:148`). **Implementation-derived finding:** with those supported runtime locale values, Cursor also takes the English branch; the Chinese router exists but is not selected by this code. UI localization and generated-file localization must not be conflated.

There are two all-config orchestrations. The service's public `generateAllAIConfigs` sequentially calls Cursor then Copilot and returns both paths (`src/services/aiIntegrationService.ts:89`). The UI's `generateAllAIConfigs` does not call that service wrapper: it collects graph data once, directly calls the two individual generators under noncancellable progress (0/50/100), then offers the corresponding files (`src/ui/commands/entityCommands.ts:1290`). The same actual writers/builders are shared despite duplicated orchestration.

The scenario-switch UI offers regeneration and executes `knowledge.generateAllAIConfigs` when accepted (`src/commands/scenarioCommands.ts:62`). **Implication:** this may appear to customize instructions for the new scenario, but the current router path ignores the scenario, so regeneration alone does not incorporate its template. Reconnecting project-specific inputs would change a presently generic contract, not merely improve an already-used template interpolation.

### Existing destinations, success, and failures

The writer checks only whether `.github` exists. It does not read, merge, preserve, back up, or ask permission for an existing `copilot-instructions.md`; normal `writeFileSync` semantics replace/truncate it (`src/services/aiIntegrationService.ts:72`). The code uses no temporary-file rename/transaction. If `.github` is absent it is created before content construction/write, so a later failure may leave the directory behind. If `.github` is an incompatible filesystem object or access/write fails, the service rejects; it has no internal catch or rollback (`src/services/aiIntegrationService.ts:71`). A mid-write failure cannot be claimed to leave the previous file intact.

The UI catches graph collection, generation, success-dialog, open and reveal failures in one block and shows the localized “Failed to generate Copilot Instructions” message (`src/ui/commands/entityCommands.ts:1262`). Consequently an editor/reveal failure can be reported as generation failure after the file has already been successfully written; there is no rollback. The normal catch consumes the failure rather than rethrowing, so the extension's outer catch is not the usual handler (`src/extension.ts:680`). Dismissing the success dialog simply leaves the created file unopened.

There is an existing presentation mismatch: the command passes `.github/` plus the basename to `translations.success`, and both EN/ZH formatters prepend `.github/` themselves (`src/ui/commands/entityCommands.ts:1271`, `src/i18n/en.ts:293`, `src/i18n/zh.ts:294`). The success text therefore contains `.github/.github/copilot-instructions.md`; the real filesystem path and open/reveal actions still use the correct service path. This is not a double-nested write.

In both all-config routes, Cursor is written first. If Copilot then fails, the new/overwritten Cursor file remains, the operation stops, and there is no all-files success result or rollback; a first-stage failure prevents the second write (`src/services/aiIntegrationService.ts:89`, `src/ui/commands/entityCommands.ts:1306`). UI failure after both writes likewise does not undo either file. These partial-success semantics matter if adding more expensive project analysis or additional dependencies.

### Tests and consequential gaps

`src/services/aiIntegrationService.test.ts:68` creates a temporary workspace with a marker in `ai-template.md`, calls the real service writer with no graph data, reads the returned output, and checks query-first tools/evidence guidance, fallback index/single view, and prohibition on default full-graph loading. It checks that the marker, tech stack, dependency detail and entity-count headings are absent. The mock services are empty objects (`:42`), supporting that this direct writer path needs no service analysis. Creating/reading the output also exercises creation of an initially absent `.github`, but the test does not explicitly assert the exact returned destination.

`src/services/aiIntegrationService.test.ts:100` checks analogous compact Cursor instructions and template/graph-dump exclusion. These tests protect the intentionally small shared-router contract. Project-specific additions should preserve or deliberately revise that contract, rather than accidentally embedding whole graphs/templates.

The same file's tests at `:121` and `:144` call the private JavaScript tech-stack extractor through a cast: they check that `@types/node` is not treated as the Node runtime, and that engines/.nvmrc declarations are used. They are **not** evidence that either current instruction-generation route extracts project dependencies. The tested helper is outside the reachable current router path.

No command-level generation tests were found in the inspected `src`/`tests` test sources. Consequential missing coverage includes:

- Nonempty graph data being ignored (or, after the proposed change, intentionally and safely incorporated), graph-collection exceptions before writes, selected scenario effects, and localized content/actual `getLocale()` values.
- Exact destination/first-root choice, no-workspace handling, preexisting destination behavior, `.github` already a file, mkdir/write errors, partial writes and the lack of transactional rollback.
- Both all-config orchestrations, first-versus-second-stage failure and which artifacts remain afterward.
- Success-dialog dismissal, open/reveal dispatch, post-write open/reveal failures, and the duplicate `.github/` success-label bug.
- A direct contract that generation itself makes no MCP/model calls or graph refresh, and does not silently require the named artifacts to exist. Current router content tests alone do not prove future additions preserve that boundary.

The key design implication is to separate useful project content from merely collected data and from instructional text about future agent actions. Adding project-specific output would introduce genuinely new content/failure dependencies; the current graph-data argument and rich legacy helper code must not be mistaken for an existing, exercised implementation of those features.
