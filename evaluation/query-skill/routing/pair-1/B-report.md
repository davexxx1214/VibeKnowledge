## discovery

- 入口是 `/auth/cli/authorize?user_code=…`，路由名 `CLIAuthAuthorize`，懒加载 `CLIAuthAuthorizeView.vue`，是顶层独立页面。它只声明 `requiresAuth: true`，没有管理员或超级管理员条件，因此正常登录的普通账号通过前端路由检查。全局守卫按匹配路由读取这些条件；有 token 但没有用户 ID 时先补取用户信息，失败则登出；未登录时保存含查询参数的 `to.fullPath` 到 `sessionStorage.redirect`，然后转 `/login`。登录判定本身是 token 非空，不是此页面单独验证 token 的有效性。（`web/src/router/index.js:36-41`、`:156-185`、`:187-223`；`web/src/stores/user.js:7-20`）
- 授权码来自浏览器当前路由的 `query.user_code`，不是本页生成：执行 `String(route.query.user_code || '').trim().toUpperCase()`，显示规范化后的值；API 层再用 `encodeURIComponent` 编入 URL 路径。没有授权码时显示“缺少 CLI 授权码”、结束 loading，不发会话请求。该组件没有证明终端如何生成或打开这个 URL。（`web/src/views/CLIAuthAuthorizeView.vue:22`、`:64-78`；`web/src/apis/auth_api.js:83-90`）
- 初次挂载执行 `loadSession`，调用 `GET /api/auth/cli/sessions/{encodedCode}`，把返回值直接存入 `session`；加载时显示转圈。正常结束后显示授权码、凭据名称 `session.key_name`（空值回退 `Yuxi CLI`）、状态 `session.status`（回退 `-`）、过期时间 `session.expires_at`（回退 `-`）及本人发起请求的警告、确认按钮。只有 `onMounted(loadSession)`，没有查询参数监听、轮询或倒计时；会话状态和过期时间只是展示，没有用于隐藏或禁用确认按钮。（`web/src/views/CLIAuthAuthorizeView.vue:9-45`、`:57-84`、`:98`；`web/src/apis/auth_api.js:83-85`）
- 只有点击“确认授权”才执行 `approveSession`：将 `approving` 置 true，使按钮显示 loading，发送 `POST /api/auth/cli/sessions/{encodedCode}/approve`，JSON 请求体为 `{}`。请求正常返回后直接将本地 `approved` 置 true，不读取或检查批准响应内容，也不根据先前的 `session.status` 推导批准成功。（`web/src/views/CLIAuthAuthorizeView.vue:43-45`、`:59-60`、`:86-95`；`web/src/apis/auth_api.js:88-90`；`web/src/apis/base.js:176-186`）
- GET 和 POST 均使用默认要求认证的通用请求方法；发送前检查 `userStore.isLoggedIn`，不满足则抛“用户未登录”，满足则添加 `Authorization: Bearer <当前网页 token>`，默认还带 `Content-Type: application/json`。它们不使用管理员专用请求方法，也不在请求体中传用户名、用户 ID 或新 API Key。token 初始化来自 `localStorage.user_token`，密码登录成功后由服务端 `access_token` 更新并保存；这里携带的是当前网页的登录身份。（`web/src/apis/auth_api.js:83-90`；`web/src/apis/base.js:17-40`、`:153-154`、`:176-191`；`web/src/stores/user.js:7`、`:49-63`、`:141-146`）
- 批准成功后，会话详情和按钮被“已授权，可以关闭此页面并回到终端。”替换；页面不会自动关闭或跳回终端。会话读取或批准异常都会写入 `errorMessage`，分别回退“获取 CLI 授权会话失败”或“确认 CLI 授权失败”，并在 finally 结束相应 loading。错误提示在模板中优先级最高，会遮掉会话、成功提示和按钮；页面没有重试或拒绝按钮，非本人请求的提示是关闭页面。（`web/src/views/CLIAuthAuthorizeView.vue:9-47`、`:70-98`）
- 通用层对非成功 HTTP 响应解析 `detail`/`message`，解析不了则使用状态码与状态文本；403 改成“没有权限执行此操作”，500 改成服务器内部错误提示。401 额外弹出认证失败或登录过期提示，清除已登录状态，并在 1500ms 后令 `window.location.href = '/login'`；本页 catch 同时接收抛出的错误。这里的 401 跳转分支没有保存原授权 URL。（`web/src/apis/base.js:42-119`；`web/src/stores/user.js:72-90`；`web/src/views/CLIAuthAuthorizeView.vue:79-83`、`:91-95`）
- “以当前身份创建一个 API Key 并返回给终端”是界面承诺。此处可证实的实现止于：携带网页 Bearer token 读取会话、显式提交批准，以及请求正常返回后显示本地成功页。组件既没有直接创建 API Key 的调用，也不消费批准响应中的 Key、不展示/保存 Key、不向终端传送数据。真正的 Key 创建、权限与归属、交付终端以及服务端对过期或重复批准的处理，不能由这段前端证明。（`web/src/views/CLIAuthAuthorizeView.vue:14-27`、`:52-98`；`web/src/apis/auth_api.js:83-90`）

## followup

- 未登录首次打开终端链接时，全局守卫先把 `to.fullPath` 保存为 `sessionStorage.redirect`，再转 `/login`。这里保留的是应用内完整目标路径（包括 `?user_code=…`，以及如有的其他查询参数和 hash），不是仅保存 `/auth/cli/authorize`，也不是把完整外站 URL交给登录页。两条成功路径都借助该浏览器会话存储恢复原目标。（`web/src/router/index.js:156-185`）
- 密码路径：登录页调用 `userStore.login({loginId, password})`；store 用 FormData 的 `username=loginId`、`password` 向 `/api/auth/token` POST。成功响应的 `access_token` 写入 store token 和 `localStorage.user_token`，同时写入用户资料，其中 `userId = data.user_id`，从而建立网页登录态。登录页随后读取 `sessionStorage.redirect || '/'`，立即删除 `redirect`；本题保存的是授权页路径而非 `/`，因此直接 `router.push(redirectPath)`，连同原 `user_code` 返回。（`web/src/views/LoginView.vue:442-465`；`web/src/stores/user.js:18`、`:23-65`）
- 手动 OIDC 路径：按钮处理函数调用的是无参数的 `authApi.getOIDCLoginUrl()`。该 API 默认 `redirectPath = '/'`，通过 URLSearchParams 发出 `GET /api/auth/oidc/login-url?redirect_path=%2F`。因此，请求交给服务端的 `redirect_path` 是 `/`，并非原 CLI 授权链接；服务端如何利用这个值不在这些前端代码中。收到 `login_url` 后，浏览器另行取 `sessionStorage.redirect`，其次才是登录页 `query.redirect`、最后 `/`，写入 `sessionStorage.oidc_redirect`，再用 `window.location.href = response.login_url` 离开。本题没有旧记录，故 `oidc_redirect` 保存的就是最初含 CLI 授权码的完整应用内目标路径。（`web/src/views/LoginView.vue:503-522`；`web/src/apis/auth_api.js:36-43`）
- OIDC 回调入口是 `/auth/oidc/callback`，不要求登录。未登录挂载时执行回调处理，从 URL 读非空字符串 `query.code`，以 JSON `{code}` POST `/api/auth/oidc/exchange-code`；这两个 OIDC 请求使用直接 `fetch`，没有添加当前网页 Bearer token。交换成功后先 `router.replace({path: route.path, query: {}})` 清空回调查询参数，再由回调组件直接更新用户 store、把 `tokenData.access_token` 写到 `localStorage.user_token`；这里实际写的是 `userStore.userId = tokenData.uid`，与密码登录使用 `data.user_id` 不同。随后读取 `oidc_redirect || '/'`，删除 `oidc_redirect` 并清除自动发起尝试标记，显示登录成功，500ms 后将本题的原目标传给 `router.push`。（`web/src/router/index.js:30-35`；`web/src/views/OIDCCallbackView.vue:53-109`、`:119-128`；`web/src/apis/auth_api.js:36-43`、`:66-80`）
- 清理差异：密码成功路径消费并删除原始 `redirect`；手动 OIDC 发起只是把 `redirect` 的值复制给 `oidc_redirect`，没有删除原项，成功回调只删除 `oidc_redirect` 和 `oidc_auto_start_attempted`，所以原来的 `sessionStorage.redirect` 在这条路径之后仍保留。另外回调清空的是回调 URL 的 query，不是保存的 CLI 目标链接，所以不会因此丢失其中的 `user_code`。（`web/src/views/LoginView.vue:449-465`、`:513-522`；`web/src/views/OIDCCallbackView.vue:69`、`:88-109`；`web/src/utils/oidcAutoStart.js:1`、`:31-34`）
- OIDC 回调 `code` 与 CLI `user_code` 是两条不同用途的数据：前者用于兑换网页登录结果并随后从回调 URL 清除；后者保留在待返回的 CLI 页面 URL 中，用于定位、读取和批准 CLI 授权会话。前端没有把它们视为同一个码或相互替换。两种登录成功都只建立网页登录态并恢复授权页，不会自动执行 CLI 批准；授权页挂载只读会话，仍需用户另行点击确认，批准请求成功才设置本地 `approved`。（`web/src/apis/auth_api.js:66-90`；`web/src/views/OIDCCallbackView.vue:56-83`；`web/src/views/CLIAuthAuthorizeView.vue:43-45`、`:64-98`）

## control

1. `userStore.isAdmin === false` 时，`normalizeTab('mcp')` 返回 `'skills'`。普通用户标签只有 `'skills'`，`allowedTabKeys` 不包含 `'mcp'`，因此回退到第一个标签的 key，即 `'skills'`。`userStore.isAdmin === true` 时，`normalizeTab(['skills', 'mcp'])` 返回 `'knowledge'`：管理员允许的 key 是四个字符串，而传入的是整个数组；`includes(tab)` 不会展开数组或取首项，所以匹配失败，回退到管理员第一个标签 `'knowledge'`。（`web/src/views/ExtensionsView.vue:51-65`）
2. 管理员的默认标签是 `'knowledge'`。对 `{ tab: 'mcp', q: 'needle' }` 独立调用 `replaceTabQuery('knowledge')`，先浅拷贝当前 query，再因目标等于默认标签删除副本的 `tab`，最终调用 `router.replace({ query: { q: 'needle' } })`。用的是 `replace`，不是 `push`；其余查询字段原样保留，函数不直接修改原 `route.query`，也没有额外传 `path` 或 `name`。（`web/src/views/ExtensionsView.vue:51-60`、`:67-75`）
