# Read-only source analysis

Scope: graph page/view interactions, followed by Generate Copilot Instructions. Findings below come from source and test inspection only; no tests or builds were run. Citations are repository-relative `path:line` references within this assigned workspace. “Implication” and “gap” identify analysis rather than a claimed runtime observation.

## 1. Visualization

### Command, host, and page

`Knowledge: Visualize Graph` is contributed as `knowledge.visualizeGraph` (`package.json:57`) and appears in the Knowledge Graph Explorer title navigation (`package.json:244`). The registered handler calls `GraphView.createOrShow(context.extensionUri)` and catches synchronous opening failures with an error notification (`src/extension.ts:643`). Activation supplies a `KnowledgeGraphService` backed by `AgentGraphService`, and a separate `StructuralGraphService`, to the static GraphView setters (`src/extension.ts:174`, `src/extension.ts:242`). Without a workspace, activation registers placeholder commands instead; both requested command IDs are among them, and they only warn to open a folder (`src/extension.ts:48`, `src/extension.ts:960`, `src/extension.ts:992`).

GraphView owns one static current panel. Creating it enables scripts and `retainContextWhenHidden`; revealing an existing panel normally sends data without replacing its HTML. A changed translated panel title causes HTML regeneration instead. Disposal clears the singleton and registered disposables (`src/ui/webview/graphView.ts:128`, `src/ui/webview/graphView.ts:157`, `src/ui/webview/graphView.ts:186`).

The host generates HTML containing the shared performance and tooltip JavaScript. The page loads a local `dist/d3.min.js` webview URI under a nonce/CSP, initializes SVG/zoom on `load`, then posts `ready`; the host responds with the effective performance setting and `graphData` (`src/ui/webview/graphView.ts:718`, `src/ui/webview/graphView.ts:751`, `src/ui/webview/graphView.ts:1137`, `src/ui/webview/graphView.ts:1205`, `src/ui/webview/graphView.ts:205`). The build copies D3 into that expected destination (`esbuild.js:11`). This is D3 rendering, not the repository's unrelated vis-network resource.

The page's Refresh button posts `refresh`; its host handler only recollects and sends the ordinary groups. It does not generate a structural graph (`src/ui/webview/graphView.ts:219`, `src/ui/webview/graphView.ts:263`, `src/ui/webview/graphView.ts:2086`). Background source-refresh machinery is outside this assessment.

### Ordinary groups and the advanced structural view

Ordinary groups come from `KnowledgeGraphService.getGroups()`, not its de-duplicated aggregate snapshot. Repeated symbols deliberately remain in independent framework/module/feature views; `getEntity()` also searches those group-specific IDs so navigation works for repeated occurrences (`src/services/knowledgeGraphService.ts:147`, `src/services/knowledgeGraphService.ts:192`). GraphView constructs independent view models containing IDs, code locations, observations, provenance, description, confidence/evidence and optional structural keys/paths (`src/ui/webview/graphView.ts:456`). Thus a layout change must not silently substitute the aggregate snapshot or discard metadata used by tooltips and navigation.

On `graphData`, the page replaces its group list, sorts by numeric order then name, renders safe DOM text labels and entity/relation counts, and selects the saved/current key if present, otherwise the first group (`src/ui/webview/graphView.ts:1287`, `src/ui/webview/graphView.ts:1372`, `src/ui/webview/graphView.ts:1423`). Selection updates the active button, writes only `{ selectedGroupKey }` to VS Code webview state and renders that one group (`src/ui/webview/graphView.ts:1449`). Zero groups clear simulations, geometry cache and SVG and show the empty state. An existing group with zero entities also shows the empty state, after stopping and saving the preceding view (`src/ui/webview/graphView.ts:1378`, `src/ui/webview/graphView.ts:1479`). The zero-group branch clears the in-memory selected key but does not write a cleared key with `setState`.

Advanced structure is explicitly requested: choosing Boundary/Community/File alone does not request data; pressing the structural button reads that selector and posts `requestStructuralOverview` (`src/ui/webview/graphView.ts:1101`, `src/ui/webview/graphView.ts:2091`, `src/ui/webview/graphView.ts:2173`). The host reads the existing raw graph, aggregates it at that level with an 80-node limit, and returns a synthetic `structuralGroup` named `Advanced · <level> structure`, with stable aggregate IDs, file lists, relationship counts and raw paths (`src/ui/webview/graphView.ts:324`, `src/ui/webview/graphView.ts:518`). The underlying service reads `.vscode/.knowledge/structural-graph.json`, rejects a missing file, parses it and validates its schema; this page action does not generate it (`src/services/structuralGraph/structuralGraphService.ts:25`, `src/services/structuralGraph/structuralGraphService.ts:63`, `src/services/structuralGraph/structuralGraphService.ts:101`).

The page removes all previous `__structural_` synthetic entries, inserts the new one beside the ordinary groups, selects it and shows a transient node/relation-count status. Consequently there is at most one advanced/raw slice in the sidebar, not a navigation history or a permanently added knowledge group (`src/ui/webview/graphView.ts:1401`). The prefix is therefore a reserved identity boundary in this implementation.

Drill-down behavior is distinct from ordinary navigation:

- Double-clicking an aggregate sends its aggregate ID, level and files. The host prefers that file list, selects at most 80 raw entities and at most 120 relationships whose endpoints are included (`src/ui/webview/graphView.ts:407`, `src/ui/webview/graphView.ts:1761`).
- Shift-double-click or right-click on a curated node with a structural key requests immediate upstream/downstream structural neighbors. The host uses depth 1, deduplicates relations, caps them at 120, caps entities at 80 and removes edges to excluded endpoints (`src/ui/webview/graphView.ts:365`, `src/ui/webview/graphView.ts:1778`).
- Double-clicking a relationship path or its label sends `structuralPath`; the host matches raw relationships by source, target, verb and complete source location, and derives their endpoints. This path handler does not apply the 80/120 caps (`src/ui/webview/graphView.ts:340`, `src/ui/webview/graphView.ts:627`, `src/ui/webview/graphView.ts:1601`, `src/ui/webview/graphView.ts:1685`).
- Raw slices have timestamp-based group keys but hashed stable entity IDs, raw provenance/evidence, and code locations (`src/ui/webview/graphView.ts:564`, `src/ui/webview/graphView.ts:643`). A raw-node double-click opens its source; an ordinary curated-node double-click opens the knowledge entity. Both convert one-based source lines to editor ranges; external entities are not opened (`src/ui/webview/graphView.ts:647`, `src/ui/webview/graphView.ts:687`, `src/ui/webview/graphView.ts:1771`).

Structural read/analysis errors become `structuralError` plus a host warning. The page shows the error status and hides the loading overlay without replacing the current groups, so the previous view remains available (`src/ui/webview/graphView.ts:450`, `src/ui/webview/graphView.ts:1296`). An obsolete path with no matching current relations can instead yield an empty slice: nonempty input is checked, but zero matches are not an error (`src/ui/webview/graphView.ts:340`).

### Performance selector and responsiveness

The setting is `knowledgeGraph.visualization.performanceMode`, a machine-scoped string with `low` default and `low`/`high` choices (`package.json:325`). Both host and page normalize anything other than explicit `high` to `low` (`src/ui/webview/graphView.ts:300`, `src/ui/webview/graphPerformanceScript.ts:3`). Changing the page selector immediately applies the mode and rerenders the same group, disables the selector and posts `setPerformanceMode`. The host validates the value and awaits a Global configuration update. Its `finally` always posts the effective value; the page applies that authoritative value and re-enables the selector. A failed save produces an error and rolls back the optimistic mode. Settings UI changes also post the current mode through a configuration listener (`src/ui/webview/graphView.ts:150`, `src/ui/webview/graphView.ts:309`, `src/ui/webview/graphView.ts:1283`, `src/ui/webview/graphView.ts:2077`, `src/ui/webview/graphView.ts:2176`). This is a display preference, not a graph-data write.

Both modes use the same D3 nodes, relationships and force configuration. Rendering clones nodes and links, so D3's simulation positions and endpoint object references belong to the render model (`src/ui/webview/graphView.ts:1504`, `src/ui/webview/graphView.ts:1552`). Differences are:

- Low stops D3's automatic simulation and, for an unsettled layout, runs manually ticked requestAnimationFrame batches. A batch yields at roughly 6 ms, with a maximum 120 ticks, 600 ms accumulated compute time, or cooling completion. It explicitly renders because manual D3 `tick()` does not emit tick/end events; it stops and reports callback failures (`src/ui/webview/graphPerformanceScript.ts:46`, `src/ui/webview/graphView.ts:1933`). The time budget is checked after a batch/tick, so it cannot preempt one unusually expensive tick.
- Low has no particles, animated agent-link flow, glow, text shadows or label halo; CSS disables animation/transitions, hover changes are immediate, and Fit changes zoom immediately. Relation labels, arrows, provenance styling, tooltips, highlighting, zoom and navigation remain (`src/ui/webview/graphView.ts:1080`, `src/ui/webview/graphView.ts:1585`, `src/ui/webview/graphView.ts:1618`, `src/ui/webview/graphView.ts:1667`, `src/ui/webview/graphView.ts:1720`, `src/ui/webview/graphView.ts:2073`).
- High retains normal interactive force simulation for unsettled layouts, particle animation throttled to about 30 FPS, animated dashed agent links and visual effects. It caches SVG path lengths after settling; geometry updates invalidate that cache (`src/ui/webview/graphView.ts:1154`, `src/ui/webview/graphView.ts:1566`, `src/ui/webview/graphView.ts:1624`, `src/ui/webview/graphView.ts:1823`, `src/ui/webview/graphView.ts:1922`). A high-mode graph restored from a settled cache stays physically settled; “high” does not force a new layout on every visit.
- Low-mode dragging stops pending layout, sets alpha to zero, moves only the dragged node directly and redraws that node plus incident edges/labels. High-mode dragging reheats the simulation to alphaTarget 0.3. Both temporarily pin and subsequently unpin the node and save geometry (`src/ui/webview/graphPerformanceScript.ts:91`, `src/ui/webview/graphView.ts:1823`, `src/ui/webview/graphView.ts:1950`).
- Initial low layout fits on completion, initial high layout schedules Fit after one second, and high Fit animates for 750 ms. User zoom/pan or dragging disables pending automatic Fit, avoiding a delayed reset of the user's chosen view (`src/ui/webview/graphView.ts:1360`, `src/ui/webview/graphView.ts:1933`, `src/ui/webview/graphView.ts:1957`, `src/ui/webview/graphView.ts:2053`). Resize is debounced 120 ms; low explicitly fits, while visible high mode reheats at alpha 0.15 (`src/ui/webview/graphView.ts:1210`). Therefore a resize can still change the remembered framing/layout.

### What actually survives

| Event/storage layer | Preserved behavior and limits |
| --- | --- |
| Switch ordinary groups or performance mode | Before replacement, the old simulation/layout/particles stop and the old group's geometry is saved. A matching cached entry restores x/y, zoom x/y/k, alpha, settled state and auto-fit permission. It does not preserve velocities, pins or source/evidence objects. Unfinished layouts can continue rather than being mistaken for settled ones. (`src/ui/webview/graphView.ts:1479`, `src/ui/webview/graphView.ts:1556`, `src/ui/webview/graphPerformanceScript.ts:24`.) |
| Cache validity and size | Keyed by group key plus sorted node IDs and sorted edge `(sourceId,targetId,verb)` tuples. Prose/evidence changes reuse geometry but new graph objects still provide current content; topology changes invalidate it. Cache is LRU, defaults to 8 groups and 2,000 total nodes; rejects nonfinite coordinates, a group over 2,000 nodes or over 16,000 links. These are cache limits, not a cap on ordinary-group rendering. (`src/ui/webview/graphPerformanceScript.ts:7`.) |
| Hide/show the existing page | Retained webview context keeps groups, selected key, selector values and in-memory cache. On hide, it pauses static batches, stops physics/particles, interrupts transitions, cancels fit/resize timers and saves layout; CSS gets `graph-paused`. On show it resumes unfinished static work or sufficiently warm high-mode physics and resumes particles. It does not intentionally reset the view. (`src/ui/webview/graphView.ts:175`, `src/ui/webview/graphView.ts:1254`.) |
| Invoke Visualize again on an existing panel | Same-title reveal does not reload HTML, but does send ordinary `graphData`. An ordinary selection survives if its key still exists, and matching geometry is reused. A selected advanced slice is lost because the replacement payload contains only ordinary groups; selection falls back to the first ordinary group. Merely making the retained tab visible is different from invoking this command. (`src/ui/webview/graphView.ts:157`, `src/ui/webview/graphView.ts:263`, `src/ui/webview/graphView.ts:1372`.) |
| Webview document regenerated | The only serialized view datum read is `selectedGroupKey`; layoutCache, zoom, structural groups and structural selector are created afresh. If that saved key is missing in incoming data, the first group wins. A language-title change takes this HTML regeneration path. (`src/ui/webview/graphView.ts:161`, `src/ui/webview/graphView.ts:199`, `src/ui/webview/graphView.ts:1101`, `src/ui/webview/graphView.ts:1141`, `src/ui/webview/graphView.ts:1150`.) |
| Close/dispose and open a new panel | The Global performance setting is deliberately reread. There is no host storage/serializer here restoring group data or geometry into a new panel; `getState` is only used for the webview's selected key, not cross-panel durable storage. Thus source supports no promise of full-view restoration after close or editor restart. Before unload, animation/layout/timers are stopped, not serialized. (`src/ui/webview/graphView.ts:157`, `src/ui/webview/graphView.ts:186`, `src/ui/webview/graphView.ts:300`, `src/ui/webview/graphView.ts:1272`.) |

An additional implication of the visibility code: hiding clears the high-mode delayed-fit timer and showing does not recreate it. A graph hidden before initial Fit may return without that pending auto-fit, although simulation can resume. This should be an explicit decision/test when changing view memory, not assumed to be equivalent to a fresh render (`src/ui/webview/graphView.ts:1254`, `src/ui/webview/graphView.ts:1940`).

### Correctness boundaries and test assessment

Rendering errors from synchronous group rendering are caught, the loading/empty states are hidden and an accessible error state is shown while animation is stopped; static batch failures use the same path (`src/ui/webview/graphView.ts:1458`, `src/ui/webview/graphView.ts:1465`, `src/ui/webview/graphView.ts:1934`). This boundary does not cover every lifecycle failure: D3 loading or `initGraph()` failures precede the ready handshake, and high-mode particle/tick callbacks are not wrapped by that selection try/catch (`src/ui/webview/graphView.ts:1205`, `src/ui/webview/graphView.ts:1632`, `src/ui/webview/graphView.ts:1920`). Implication: a change must preserve the local asset/CSP and handshake as well as render-error recovery; otherwise an opening failure can leave a loader rather than a useful render-error state.

## 2. Generate Copilot Instructions

### UI to output and completion

The command is contributed as `Knowledge: Generate Copilot Instructions` with ID `knowledge.generateCopilotInstructions` (`package.json:86`). Its extension handler awaits `EntityCommands.generateCopilotInstructions()` and has an outer error notification (`src/extension.ts:680`). Activation constructs EntityCommands with the entity, relation, observation and unified knowledge services; EntityCommands creates its own AIIntegrationService with the first three (`src/extension.ts:245`, `src/ui/commands/entityCommands.ts:23`).

The command uses `vscode.workspace.workspaceFolders?.[0]`, not the active editor's containing workspace or a folder picker. If absent, it reports a localized error and returns. There is no generation options dialog or destination picker. It gathers `GraphData`, passes that plus the first folder's `fsPath` into the service, then waits for the returned filename (`src/ui/commands/entityCommands.ts:1255`). `getGraphData()` obtains the unified snapshot, loops over every entity's knowledge observations and packages entities, relations, flattened `{entityId, entityName, content}` observations and literal `sourceType: 'knowledge'` (`src/ui/commands/entityCommands.ts:42`).

The actual service path is short: ensure `<workspaceRoot>/.github` exists with recursive mkdir, call the no-argument Copilot builder, synchronously write UTF-8 to `<workspaceRoot>/.github/copilot-instructions.md`, then return that path. Although the method is `async`, its file operations are synchronous (`src/services/aiIntegrationService.ts:71`). The builder delegates to `buildAgentKnowledgeRouterContent('en', '# VibeKnowledge Agent Instructions')`; the result is a static array joined with newlines, including a trailing newline (`src/services/aiIntegrationService.ts:404`, `src/services/aiIntegrationService.ts:432`).

After successful writing, the command offers Open file or Show in folder. Open uses `openTextDocument` and `showTextDocument`; Show in folder executes `revealFileInOS` for the actual URI. Dismissing the notification simply leaves the file written. All these steps are inside the same try/catch (`src/ui/commands/entityCommands.ts:1269`). There is a presentational mismatch: the caller prepends `.github/` before calling `translations.success`, while both English and Chinese success formatters also prepend `.github/`; the success message therefore repeats that segment. This does not change the actual destination or either follow-up action (`src/ui/commands/entityCommands.ts:1271`, `src/i18n/en.ts:293`, `src/i18n/zh.ts:294`).

### Shared and related generation paths

1. Cursor generation writes `<root>/.cursorrules`, using `buildCursorRulesContent` and then the same `buildAgentKnowledgeRouterContent`; graphData is ignored there too. Titles are caller-specific, but the router body is shared. Changing that shared builder affects both products; a Copilot-only change should not be assumed isolated if implemented there (`src/services/aiIntegrationService.ts:58`, `:101`, `:404`).
2. There is a locale-code mismatch in current Cursor code: it compares `getLocale()` with `'zh'`, but that helper returns `'zh-CN'` or `'en-US'`. Thus the reachable Cursor route also selects English under the current helper contract, despite the apparent bilingual branch. The Chinese router body exists but this comparison does not reach it (`src/services/aiIntegrationService.ts:101`, `src/i18n/i18nService.ts:126`, `:148`). Copilot is independently hardcoded to English, not dependent on this mismatch.
3. `AIIntegrationService.generateAllAIConfigs` sequentially invokes Cursor then Copilot and returns their paths (`src/services/aiIntegrationService.ts:89`). The UI's `EntityCommands.generateAllAIConfigs` does not call this convenience method: it repeats those same two service calls under noncancellable notification progress, using one collected graphData, then offers to open either output (`src/ui/commands/entityCommands.ts:1290`). The command is registered separately (`src/extension.ts:692`). Both paths share the same final builders/writers and order.
4. Switching AI scenario can prompt the user to regenerate. Only accepting Generate invokes `knowledge.generateAllAIConfigs`; selecting the same scenario returns early, and cancelling/Later does not generate (`src/commands/scenarioCommands.ts:38`, `:50`, `:63`). This is an indirect route to overwriting both files, not evidence that scenario content is currently included. Changing scenario without another relevant code change still yields the same Copilot router.

### Existing destinations and failures

The only existence check is for the `.github` directory. The destination file is not read, merged, appended, backed up or confirmed before `fs.writeFileSync`; an existing `copilot-instructions.md`, including hand-written project guidance, is replaced. No temporary file/rename transaction or rollback is implemented (`src/services/aiIntegrationService.ts:71`). A future project-specific writer must make an explicit preservation policy rather than assume one exists today.

Filesystem failures (for example `.github` being a file, permissions, or a failed write) reject the async service call; the service has no catch/recovery. The command catches graph-collection, generation and follow-up Open/Reveal failures and emits the same localized “failed to generate” error (`src/ui/commands/entityCommands.ts:1262`, `:1282`). The outer extension handler is a fallback for an escaping rejection, not normally a second handler for errors already swallowed by EntityCommands (`src/extension.ts:680`).

Consequences of the direct-write implementation:

- There is no guarantee of atomic replacement or preservation after a mid-write failure; an already-created `.github` directory or partially changed destination is not undone.
- A file may have been generated successfully even when opening/revealing it subsequently fails and the user sees a generation-error notification. There is no rollback of the generated file, and the initial success notification can already have been shown.
- In either generate-all implementation, Cursor runs first. If Cursor fails, Copilot is not attempted; if Copilot fails, the already-written Cursor file remains. There is no all-or-nothing transaction or partial-success summary (`src/services/aiIntegrationService.ts:89`, `src/ui/commands/entityCommands.ts:1306`, `:1332`).

These are source-derived failure possibilities, not failures reproduced in this task.

### Intended consumer behavior versus generator actions

The `.github/copilot-instructions.md` file is intended as guidance for the coding assistant consuming it. Its content says to use the knowledge graph as an on-demand dependency navigator: use MCP `query_graph` first for architecture/unfamiliar/cross-file/dependency/impact tasks with a focused question and token budget; expand using `get_entity`, `get_neighbors` or `shortest_path`; request evidence only for auditing; fall back to `agent-context/index.md` and one best-matching group; avoid loading the full audit report by default; skip graph queries for small known-file work; verify current source before changes/tests; and never edit `graph.sqlite` directly (`src/services/aiIntegrationService.ts:435`).

The generator merely writes those instructions and optionally opens/reveals the output. It does not execute those tools, read the named graph report/index, install/configure MCP, generate graph artifacts, modify SQLite, call Copilot/Gemini, inspect the project on the assistant's behalf, or perform the described verification. The UI's graph snapshot collection is separate from fulfilling any of those future instructions (`src/ui/commands/entityCommands.ts:42`, `src/services/aiIntegrationService.ts:71`, `:411`). Presence of the generated file alone does not establish that its suggested external facilities are available or that a consumer will follow it.
