# Visualization and Copilot Instructions: read-only impact analysis

Scope: the assigned repository, inspected without running tests/builds, generating output files, installing packages, using network access, or modifying source. The installed `vibeknowledge-query` Skill routed each named feature to its matching brief; both briefs reported matching cited-source hashes and no omitted blocks after expansion. Branches and tests needed for the conclusions below were verified in source. Brief freshness is not proof of runtime behavior or exhaustive callers. ## 1. Visualization

### Command → host → browser → selected view

The manifest contributes `knowledge.visualizeGraph` as “Knowledge: Visualize Graph” and puts it in the Knowledge Graph Explorer title navigation (`package.json:57`, `package.json:244`). Its extension callback calls `GraphView.createOrShow(context.extensionUri)` and catches synchronous opening errors for an error notification (`src/extension.ts:642`). Activation injects the knowledge and structural services into GraphView (`src/extension.ts:242`). This report concerns the page and its explicit refresh/reveal interactions, not background source refresh.

GraphView owns one static current panel. Creation enables scripts and `retainContextWhenHidden`; invoking the command with an existing panel reveals it, resends ordinary graph data if the translated title is unchanged, or replaces its HTML if the title changed. Disposal clears the singleton and subscriptions (`src/ui/webview/graphView.ts:150`, `src/ui/webview/graphView.ts:157`, `src/ui/webview/graphView.ts:186`, `src/ui/webview/graphView.ts:199`). The page initializes its SVG on `load`, then sends `ready`; the host responds with the current performance preference and `graphData` (`src/ui/webview/graphView.ts:1205`, `src/ui/webview/graphView.ts:205`). The refresh button sends `refresh`, which only resends graph data in this handler (`src/ui/webview/graphView.ts:2086`, `src/ui/webview/graphView.ts:219`).

The browser renderer depends on extension-local `dist/d3.min.js`, a nonce-based CSP and embedded helper strings, then D3 SVG, zoom and force simulation—not an independent web app fetching its own graph (`src/ui/webview/graphView.ts:718`, `src/ui/webview/graphView.ts:754`, `src/ui/webview/graphView.ts:1137`, `src/ui/webview/graphView.ts:1303`, `src/ui/webview/graphView.ts:1566`).

Ordinary groups are supplied by `KnowledgeGraphService.getGroups()`, which retains repeated symbols across framework/module/feature groups; its separate aggregate snapshot deduplicates them. Substituting the snapshot would therefore change independent views and their IDs (`src/services/knowledgeGraphService.ts:67`, `src/services/knowledgeGraphService.ts:147`). These curated groups originate in the Agent sidecar rather than the raw structural document (`src/services/agentGraph/agentGraphService.ts:87`). GraphView builds independent view models, adds each entity's observations and structural key, and preserves relation provenance/confidence/evidence/structural-path metadata (`src/ui/webview/graphView.ts:456`).

On `graphData`, the browser replaces `graphGroups`, sorts by `order` then name, rebuilds sidebar buttons showing kind plus entity/relation counts, and selects the saved key if present, otherwise the first group. Clicking a group writes `{ selectedGroupKey }` using the VS Code Webview state API and renders only that group (`src/ui/webview/graphView.ts:1287`, `src/ui/webview/graphView.ts:1372`, `src/ui/webview/graphView.ts:1423`, `src/ui/webview/graphView.ts:1449`). Empty group lists stop simulation/static layout/particles, clear the geometry cache and drawing, and show the empty state (`src/ui/webview/graphView.ts:1378`).

### Advanced structural selection is temporary page data

The toolbar has Boundary, Community and File options. Changing the select alone does not request a graph; pressing the advanced button sends `requestStructuralOverview` with the selected level (`src/ui/webview/graphView.ts:1101`, `src/ui/webview/graphView.ts:2091`, `src/ui/webview/graphView.ts:2173`). The host reads `StructuralGraphService`, calls `aggregateStructuralGraph` with a limit of 80 aggregate nodes, and posts a `structuralGroup` (`src/ui/webview/graphView.ts:324`). Structural service reads validate the document and throw on a missing, unreadable, malformed or invalid graph; this is an on-demand read, not graph generation (`src/services/structuralGraph/structuralGraphService.ts:63`, `src/services/structuralGraph/structuralGraphService.ts:101`).

Aggregate view models have `__structural_<level>` keys and `source: 'aggregate'`. Their nodes carry aggregate IDs/levels/files; relation display counts and drilldown samples are distinct (`src/ui/webview/graphView.ts:518`). The aggregation groups files/boundaries/communities, ranks retained nodes by entity count, drops within-group edges, keeps edges only between retained nodes, and stores at most eight raw relationships per counted aggregate edge (`resources/skills/vibeknowledge-dependency-graph/scripts/structural-analysis.mjs:391`, `resources/skills/vibeknowledge-dependency-graph/scripts/structural-analysis.mjs:416`). Consequently an edge's drilldown need not contain all relationships advertised by its count; the overview is not a complete raw graph.

Receiving a structural group removes every previous `__structural_` group, appends the new one, sorts, automatically selects it and displays status (`src/ui/webview/graphView.ts:1401`). Ordinary groups remain available in the sidebar. A later ordinary `graphData` message replaces the entire group list, so explicit refresh or re-invoking the visualize command can remove that temporary structural view and select the first ordinary group if its key no longer exists. Merely making the retained tab visible does not itself run that command (`src/ui/webview/graphView.ts:157`, `src/ui/webview/graphView.ts:1372`).

Interaction routes must remain distinct:

- Ordinary node double-click jumps to its curated entity; Shift-double-click, or curated-node context menu when a structural key exists, asks for structural neighbors. Aggregate-node double-click asks for raw members; raw structural-node double-click jumps to source (`src/ui/webview/graphView.ts:1761`, `src/ui/webview/graphView.ts:1791`).
- A relation path or label with a nonempty structural path sends `drillDownRelation`. The host matches current raw relationships by source, target, verb and file/line location; stale hops can therefore produce an empty slice rather than fabricated relationships (`src/ui/webview/graphView.ts:1599`, `src/ui/webview/graphView.ts:1685`, `src/ui/webview/graphView.ts:340`, `src/ui/webview/graphView.ts:627`).
- Entity drilldown is depth one in both directions, deduplicates relationships, caps them at 120 and entities at 80, then drops relationships whose endpoints were excluded. Aggregate drilldown selects supplied files first, otherwise the aggregate path/boundary, and caps at 80 entities/120 internal relations. These are bounded slices, not promises of exhaustive impact (`src/ui/webview/graphView.ts:365`, `src/ui/webview/graphView.ts:407`). Raw slices get timestamp-based group keys, so repeated drilldowns are not a stable navigation history (`src/ui/webview/graphView.ts:564`).

Structural failures post `structuralError` and a VS Code warning; the client hides loading and shows temporary error status without replacing the previous group (`src/ui/webview/graphView.ts:450`, `src/ui/webview/graphView.ts:1296`). Missing/unreadable Agent sidecar data instead yields an empty snapshot, and ordinary graph-data messages carry no generation-error field (`src/services/agentGraph/agentGraphService.ts:232`, `src/ui/webview/graphView.ts:263`). A renderer exception has a separate error panel and stops layout/animation (`src/ui/webview/graphView.ts:1458`, `src/ui/webview/graphView.ts:1465`). Thus “empty curated data,” “advanced request failed” and “render failed” are different failure contracts.

### Performance selector and responsiveness

The preference is `knowledgeGraph.visualization.performanceMode`, enum `low`/`high`, machine-scoped and defaulting to low (`package.json:325`). A UI change applies immediately, rerenders the selected group, disables the selector, then sends `setPerformanceMode`; no different graph data is requested. The host only accepts low/high, writes to `ConfigurationTarget.Global`, and always sends the actual preference back after a valid save attempt. Failure also displays an error; the reply restores the real mode and reenables the selector. Settings changes send the same message (`src/ui/webview/graphView.ts:150`, `src/ui/webview/graphView.ts:300`, `src/ui/webview/graphView.ts:1283`, `src/ui/webview/graphView.ts:2077`, `src/ui/webview/graphView.ts:2176`). Invalid messages return without a save or acknowledgment; the normal select only emits valid options.

Low mode still computes a force-directed layout. It stops D3's timer, uses explicit `tick()` calls in short animation-frame batches (nominally under 6 ms per batch), renders each batch, and ends after cooling, 120 ticks or 600 ms accumulated compute time. It sets alpha to zero on completion and reports failures without scheduling further work (`src/ui/webview/graphPerformanceScript.ts:46`). The 600 ms is not elapsed wall time, and a single costly tick can exceed the batch target—this is cooperative budgeting, not preemption. Low-mode dragging stops the pending static layout, directly updates the dragged node and incident geometry, zeros its velocity and does not restart physics; high mode reheats physics during drag (`src/ui/webview/graphPerformanceScript.ts:91`, `src/ui/webview/graphView.ts:1823`, `src/ui/webview/graphView.ts:1950`).

High mode adds a single approximately 30-fps particle loop, animated Agent links, glow, label halos/shadows, hover transitions and animated fit. Low mode omits these decorations and disables CSS transitions/animations while retaining text, interactions and geometry (`src/ui/webview/graphView.ts:1080`, `src/ui/webview/graphView.ts:1591`, `src/ui/webview/graphView.ts:1617`, `src/ui/webview/graphView.ts:1667`, `src/ui/webview/graphView.ts:1721`, `src/ui/webview/graphView.ts:2073`). A settled cached layout stays stopped even when switching to high; “high” does not unconditionally start a fresh simulation (`src/ui/webview/graphView.ts:1572`).

### What survives, and for how long

| Event/state | Implemented behavior |
| --- | --- |
| Switch groups or performance mode | Save old layout after stopping its work; recreate the current rendering and restore matching cached geometry, zoom/pan transform, alpha, settled flag and auto-fit flag. New topology resets geometry/transform. Only the selected key is written to Webview state. |
| Reinvoke visualize on existing panel | Retains the browser document when title is unchanged, so ordinary selection/layout cache can survive the resent data; missing selection falls back. Temporary structural group data is replaced. A changed translated title regenerates HTML. |
| Hide page, then make it visible | Retained page variables and selected/advanced data remain. Hiding pauses static layout, simulation and particles; interrupts transitions; clears fit/resize timers; saves layout. Showing resumes pending low work or still-warm high simulation and particles. |
| Close/dispose and create a new panel | Singleton and retained page are destroyed. Global performance preference is reused. The code has no host-side group/layout persistence or panel restoration implementation here; it does not establish selection/geometry survival across a true close/reopen. |

Evidence: `src/ui/webview/graphView.ts:157`, `src/ui/webview/graphView.ts:186`, `src/ui/webview/graphView.ts:1140`, `src/ui/webview/graphView.ts:1254`, `src/ui/webview/graphView.ts:1453`, `src/ui/webview/graphView.ts:1479`, `src/ui/webview/graphView.ts:1556`. Initialization reads `vscode.getState()?.selectedGroupKey`, so it can recover the key wherever VS Code retains that Webview state; this is not disk persistence of a complete view. No geometry or structural payload is passed to `setState`.

The in-memory LRU defaults to eight groups and 2,000 total cached nodes. It rejects nonfinite positions, an oversized node list or a link list over eight times the node budget. Validity compares sorted node IDs and edge source/target/verb tuples, not prose, evidence or relation IDs. It stores only x/y coordinates, transform and settling/auto-fit state—not entire graph objects, velocities or pinning (`src/ui/webview/graphPerformanceScript.ts:7`). This permits fresh tooltip/source data to coexist with old geometry. Group key stability, topology validity and cache limits are correctness requirements, not just optimizations.

Auto-fit is also part of the remembered view: actual user zoom/pan and drag disable it; new low layouts fit on completion, new high layouts may fit after one second. Fit clamps scale to 0.1–4 and ignores zero-sized bounds. Resize is debounced 120 ms; low mode fits immediately while high reheats only when visible (`src/ui/webview/graphView.ts:1210`, `src/ui/webview/graphView.ts:1360`, `src/ui/webview/graphView.ts:1931`, `src/ui/webview/graphView.ts:1957`, `src/ui/webview/graphView.ts:2053`). Inference: remembering a transform does not guarantee it is never changed by resize. Also the visibility handler clears a pending high auto-fit timer and does not rearm it on reveal; preserve or deliberately redefine this timing rather than assuming a universal “resume all work” rule.

Other consumer boundaries: source navigation uses the first workspace folder, one-based source lines converted to editor positions, and refuses external entities; file-open errors are surfaced (`src/ui/webview/graphView.ts:647`, `src/ui/webview/graphView.ts:687`). Music sends the selected key, but its host handler searches only ordinary curated groups and falls back to the first: selecting an advanced view does not make music consume that structural slice (`src/ui/webview/graphView.ts:279`, `src/ui/webview/graphView.ts:2115`). These are consequences of changing selected-view semantics.

Consequential gaps in the inspected tests: a real browser lifecycle with rapid group/mode switches, restoring transform without unwanted fit, title-triggered reload versus actual close, visibility/particle/timer integration, empty/error rendering cleanup, advanced replacement and drilldown/source navigation, and aggregate count-versus-sample behavior at the Webview boundary. The pending-cache test stores state but does not demonstrate a whole rerender resuming successfully. These are the highest-risk seams for the proposed state/performance change, rather than grounds to claim existing tests passed or the UI is already broken.

## 2. Generate Copilot Instructions

### Entry, actual inputs and content construction

The contributed command is `knowledge.generateCopilotInstructions` (“Knowledge: Generate Copilot Instructions,” file-code icon; `package.json:85`). Its registered extension callback awaits `EntityCommands.generateCopilotInstructions()` and has an outer logging/error catch (`src/extension.ts:679`). The command uses only the first workspace folder; without one it shows the localized no-workspace error and returns. There is no destination picker, graph/group picker or project-specific content prompt (`src/ui/commands/entityCommands.ts:1255`).

EntityCommands constructs AIIntegrationService from entity/relation/observation services, alongside KnowledgeGraphService (`src/ui/commands/entityCommands.ts:23`). `getGraphData()` collects KnowledgeGraphService's deduplicated snapshot, loops over the snapshot entities to obtain observations with entity ID/name/content, and labels the result `sourceType: 'knowledge'` (`src/ui/commands/entityCommands.ts:42`, `src/services/knowledgeGraphService.ts:67`). It passes that data and `workspaceFolder.uri.fsPath` to the service (`src/ui/commands/entityCommands.ts:1262`). This differs from visualization's independent group list; no currently selected graph view is an input here.

The important distinction is that these collected inputs do not currently determine the Copilot text. `AIIntegrationService.generateCopilotInstructions(workspaceRoot, _graphData?)` ignores `_graphData`, calls a parameterless `buildCopilotInstructionsContent()`, which calls `buildAgentKnowledgeRouterContent('en', '# VibeKnowledge Agent Instructions')`. That builder joins a fixed array of strings (`src/services/aiIntegrationService.ts:71`, `src/services/aiIntegrationService.ts:404`). Therefore:

| Apparent input/dependency | Current effect |
| --- | --- |
| Workspace root | Determines `.github/copilot-instructions.md` destination, not wording. Workspace name/path are not interpolated into the active content. |
| Entities, relations, observations, descriptions, graph source type | Collected and passed by the UI, but ignored by this service path; no project entity dump, statistics or dependency report is produced. |
| Entity/Relation/Observation services and DependencyAnalyzer | Constructor wiring remains; DependencyAnalyzer is instantiated, but active Copilot content building does not call its analysis or these data services. |
| UI locale | Localizes notifications/actions, but Copilot content explicitly uses English. Cursor is different: it chooses Chinese only for locale `zh`, otherwise English. |
| Scenario/custom AI template, project tech stack and relationship display setting | Not consulted by the active router builder. Long-form formatting/template/statistics/tech-stack helpers still exist elsewhere in this class, but are not reached by the current instruction builders. |

Evidence for constructor/active paths: `src/services/aiIntegrationService.ts:42`, `src/services/aiIntegrationService.ts:101`, `src/services/aiIntegrationService.ts:404`. The old Chinese/English Cursor builders read workspace/data/tech-stack and templates (`src/services/aiIntegrationService.ts:114`, `src/services/aiIntegrationService.ts:259`, `src/services/aiIntegrationService.ts:376`), while `readCustomAITemplate` delegates to ScenarioManager and `getMaxRelationsDisplay` reads configuration (`src/services/aiIntegrationService.ts:691`, `src/services/aiIntegrationService.ts:718`). Their presence/imports do not make them dependencies of the active content path. In particular, the doc comment promising default graph-service data (`src/services/aiIntegrationService.ts:66`) does not describe the actual Copilot implementation.

Inference: graph collection is still an execution dependency of the UI command despite being irrelevant to its bytes. If `getSnapshot()` or observation collection throws, the command reports failure before writing anything. Direct service callers can omit graph data, as the existing test does. Making output project-specific would turn currently ignored inputs into substantive content dependencies and would require a clear choice of aggregate versus independent-group semantics.

### What the generated file asks a future agent to do

The current file is a compact repository instruction/router, intended for Copilot/agents to use the generated graph on demand. It directs architecture/unfamiliar/cross-file/dependency/impact tasks to MCP `query_graph` with focused questions and a token budget, expands locally with `get_entity`, `get_neighbors`, `shortest_path`, and asks for evidence only for relationship auditing. If MCP is unavailable or unhelpful, it points to `.vscode/.knowledge/agent-context/index.md` and one best-matching group. It discourages default loading of the full `knowledge-graph.md` audit report, permits known-file small tasks to skip graph lookup, requires current-source verification, and forbids direct `graph.sqlite` edits (`src/services/aiIntegrationService.ts:432`).

These are instructions written as text, not actions taken by this generator. The generation path does not call MCP, configure/install it, inspect project sources or packages, validate graph freshness, create/check that context index or group views, regenerate a graph, or invoke Copilot. A successful write establishes a file, not working downstream discovery/query infrastructure or actual Copilot compliance (`src/services/aiIntegrationService.ts:71`, `src/services/aiIntegrationService.ts:404`). Actual Copilot discovery/runtime behavior was not verified in this read-only task.

### Destination, completion and failure boundaries

The service checks whether `.github` exists and creates it recursively if not; it then uses synchronous `fs.writeFileSync(..., 'utf-8')` to write `.github/copilot-instructions.md` and returns the path from its async method (`src/services/aiIntegrationService.ts:71`). The existing destination is overwritten, not merged. There is no confirmation, backup, temporary-file rename or rollback in this code. Existing `.github` being a non-directory, directory creation failures and write failures propagate as rejected generation promises.

The UI awaits generation, then offers localized “Open file” and “Show in folder.” Open uses `openTextDocument`/`showTextDocument`; reveal invokes `revealFileInOS` with the actual returned file URI. Dismissing the notification takes no additional action. The same catch covers snapshot collection, generation, the notification and its follow-up actions (`src/ui/commands/entityCommands.ts:1262`). Thus an open/reveal failure can produce a “Failed to generate” error even after a successful write; nothing deletes/restores the new file. A write failure likewise has no guaranteed atomic preservation of old contents—this is an inference from direct overwrite without transaction handling, not a failure exercised here.

There is a concrete notification-path mismatch: the command passes `.github/${basename(filePath)}` to `translations.success`, and both English and Chinese success functions prefix `.github/` again. Consequently the success message formats `.github/.github/copilot-instructions.md`, although the actual written/opened path contains only one `.github` (`src/ui/commands/entityCommands.ts:1271`, `src/i18n/en.ts:291`, `src/i18n/zh.ts:292`). This does not change the destination.

Most operational errors are caught within EntityCommands and shown through localized messages; the extension's outer catch is a fallback for errors escaping that method (`src/ui/commands/entityCommands.ts:1282`, `src/extension.ts:684`). No-workspace handling happens before data collection. Neither this single command nor its service provides cancellation/progress or an overwrite negotiation.

### Shared generation paths and change propagation

`generateCursorRules` writes `.cursorrules`; its active builder ignores graph data too and calls the same `buildAgentKnowledgeRouterContent`, with a localized Cursor title/language (`src/services/aiIntegrationService.ts:58`, `src/services/aiIntegrationService.ts:101`). Changing that shared router changes both product outputs, while changing only `buildCopilotInstructionsContent` can remain Copilot-specific.

The UI's Generate All AI Configs path is a second consumer of the two individual service methods. It collects graph data once, runs a non-cancellable notification workflow, awaits Cursor first, then Copilot, then offers either file for viewing. It does not call the service's similarly named bulk convenience method (`src/ui/commands/entityCommands.ts:1290`). That programmatic service method independently performs the same sequential calls and returns their paths (`src/services/aiIntegrationService.ts:89`). Therefore:

- Cursor failure prevents Copilot from starting.
- Copilot failure leaves the already written Cursor file and any created directory; neither bulk implementation rolls anything back.
- A follow-up open failure occurs after both files were produced but is reported through the bulk error catch.

The scenario-switch UI is another indirect entry: after a different scenario is selected and switched, choosing Generate dispatches `knowledge.generateAllAIConfigs` (`src/commands/scenarioCommands.ts:50`). The active router never reads that scenario/template, so scenario-triggered regeneration does not itself produce scenario-specific Copilot text. This is a meaningful distinction between the UI's apparent intent and the shared implementation, not a reason to revive legacy helpers without an explicit design decision.

### Existing tests and consequential gaps

This protects the current compact-router contract and demonstrates the service does not need functioning graph data services. The fixture lacks a preexisting `.github`, so the test exercises normal directory creation, but it does not explicitly assert the precise returned destination.

The tech-stack tests (`src/services/aiIntegrationService.test.ts:121`, `src/services/aiIntegrationService.test.ts:144`) call a private extraction helper directly; they verify Node runtime-version interpretation, not inclusion of tech-stack data in either generated file. Their existence must not be cited as project-specific instruction-generation coverage. The tests mock workspace folders as undefined and supply empty service objects (`src/services/aiIntegrationService.test.ts:16`, `src/services/aiIntegrationService.test.ts:42`), further distinguishing service tests from the workspace-gated UI command.

Targeted searches found no command-level tests for these generation methods or scenario-to-bulk dispatch in `src`, and no test files in `src/ui/commands`. Important missing tests for a more project-specific implementation are:

- Explicit nonempty/differing GraphData and locale/scenario/template inputs, to state which should affect output; current tests generate without data and only check selected substrings, not full output identity or all routing requirements.
- Exact first-workspace destination, missing-workspace behavior, success text/path formatting, dismissed/open/reveal actions and errors after an already successful write.
- Existing-file overwrite versus any proposed preservation policy, `.github` path collisions, mkdir/write errors, return/rejection behavior and partial-file risks.
- Both UI and programmatic bulk sequencing, partial success/no rollback, plus scenario regeneration's actual effect.
- If project-specific references are added: missing/stale context resources, bounded content selection, source-backed factual accuracy and the distinction between writing guidance and actually provisioning its dependencies.

No tests were executed, so these are mapped source assertions and identified coverage gaps, not a passing test report. The requested change was not implemented.
