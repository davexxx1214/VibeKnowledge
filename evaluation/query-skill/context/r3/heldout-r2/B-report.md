# Read-only analysis: visualization and Copilot instructions

The installed `vibeknowledge-query` Skill was used to route each named feature to its source-backed brief, followed by targeted source and test inspection. Both briefs reported matching cited-source hashes; that is not proof of exhaustive coverage. The findings below distinguish implementation facts from inferred risks. No source was changed, and no tests, builds, browser sessions, or generated instructions were executed. Background source-refresh behavior is outside this report.

## 1. Graph visualization

### Command, host, and page

The command is `knowledge.visualizeGraph`, contributed as “Knowledge: Visualize Graph” and exposed in the Knowledge Graph Explorer title toolbar (`package.json:57–59,244–246`). The extension registers it and invokes `GraphView.createOrShow(context.extensionUri)` inside an opening-error catch (`src/extension.ts:642–652`). Activation injects `KnowledgeGraphService` and `StructuralGraphService` into GraphView (`src/extension.ts:242–243`).

`createOrShow` uses one static panel. An existing panel is revealed in column one; if its translated title is unchanged, the host sends graph data without replacing HTML. A changed translated title causes `_update()` to rebuild HTML. A new panel enables scripts and `retainContextWhenHidden`. Disposal clears the singleton and disposables (`src/ui/webview/graphView.ts:157–203`). The browser initializes D3 on `load`, then posts `ready`; the host responds with the effective performance preference and curated graph groups (`graphView.ts:205–222,1205–1208`). The manual refresh button posts `refresh` and receives the same curated-data payload (`graphView.ts:263–274,2086–2089`).

The page embeds the performance and relation-tooltip helper strings, loads extension-local `dist/d3.min.js`, and uses SVG, zoom and force simulation. The generated HTML uses a random nonce and restrictive CSP, so changes must preserve both valid emitted JavaScript and the allowed local script-loading path (`graphView.ts:718–754,1137–1141,1303–1369,1566–1573`). This is not an independent browser app fetching graph data itself.

### Ordinary groups and advanced structural views

Ordinary views come from `KnowledgeGraphService.getGroups()`, not `getSnapshot()`. This distinction is substantive: groups intentionally preserve repeated symbols in separate framework/module/feature views, whereas the aggregate snapshot deduplicates them (`src/services/knowledgeGraphService.ts:67–118,147–173`). AgentGraphService reads the curated `.vscode/.knowledge/agent-graph.json` sidecar; it is not the raw structural JSON input (`src/services/agentGraph/agentGraphService.ts:87–118`). `_collectGraphGroups` turns each group into a page model, including observations, source location, curated/agent identity, relation provenance/confidence/evidence, and optional structural keys/paths (`graphView.ts:456–515`). Replacing this with the aggregate snapshot would lose independent membership and can break group-specific navigation.

The page sorts groups by `order`, then name. Sidebar buttons display name, kind, and entity/relation counts; only the selected group is rendered. A still-valid selected key is retained when groups arrive, otherwise the first sorted group is selected. Selecting writes `{ selectedGroupKey }` to VS Code Webview state (`graphView.ts:1372–1399,1423–1462`). An empty list stops particles/layout/simulation, clears geometry and cache, and shows the empty state. It sets the in-memory key to null but does not call `setState` to clear the previously stored key (`graphView.ts:1378–1393`).

The advanced selector offers Boundary, Community and File, with Boundary initially selected. Changing the select alone does not fetch data; clicking the adjacent structural button posts `requestStructuralOverview` with its current value (`graphView.ts:1101–1106,2091–2095,2173`). The host reads StructuralGraphService and calls `aggregateStructuralGraph` with a limit of 80 nodes. The result is converted to a synthetic `__structural_<level>` group with aggregate node metadata and source-backed relation drilldown paths (`graphView.ts:324–338,518–560`). A new structural result removes all existing `__structural_` groups, inserts itself, and becomes selected. Ordinary groups remain available. A later `graphData` message replaces the whole list with curated groups, removing the temporary structural view and falling back to the first curated group if necessary (`graphView.ts:1287–1295,1372–1413`). Thus revealing an existing panel through the command can discard an advanced view, even though merely unhiding the retained page need not.

Drilldown is a separate on-demand host path, not a different D3 engine:

- Curated-node double-click requests source navigation; Shift-double-click with a structural key, or right-click on a curated node, requests structural neighbors. Aggregate-node double-click requests a raw slice; structural-node double-click navigates to source (`graphView.ts:1761–1797`).
- Entity-neighbor analysis is both directions at depth one, with deduplicated relations capped at 120 and entities at 80; relations are then filtered to retained endpoints. Aggregate drilldown selects entities by the supplied files or aggregate boundary/file identity, again capped at 80 entities and 120 internal relations (`graphView.ts:365–443`).
- Relationship paths are drillable by double-click on the edge or label. The host matches raw relationships by source, target, verb and evidence location; missing/stale hops may produce an incomplete or empty slice, not a reconstructed relationship (`graphView.ts:340–359,627–640,1601–1611,1685–1696`). Aggregate edges retain at most eight raw relationship samples and omit within-group edges, so their displayed raw count is not the number of hops returned by edge drilldown (`resources/skills/vibeknowledge-dependency-graph/scripts/structural-analysis.mjs:416–427`; `graphView.ts:549–559`).

StructuralGraphService validates its document and throws when it cannot read it (`src/services/structuralGraph/structuralGraphService.ts:63–69,101–111`). The structural host handlers catch errors, post `structuralError`, and show a VS Code warning; the page shows a temporary error status and hides loading without replacing the current graph (`graphView.ts:450–454,1296–1299,1416–1420`). Curated missing/unreadable/invalid sidecar data instead becomes an empty snapshot, and `graphData` carries no generation-error field (`src/services/agentGraph/agentGraphService.ts:232–260`; `graphView.ts:263–274`). These are different failure presentations.

### Performance selector: behavior, not graph selection

The machine-scoped `knowledgeGraph.visualization.performanceMode` setting defaults to low and accepts low/high (`package.json:325–338`). The page starts with the effective preference and body class. A change is applied optimistically, rerenders the selected group, disables the selector, and posts `setPerformanceMode`. The host accepts only low/high, saves to `ConfigurationTarget.Global`, and always sends the actual preference in `finally`. A failed save shows an error and restores the actual UI choice; configuration changes made through Settings also send the preference. Receiving it re-enables the selector (`graphView.ts:150–154,300–321,1283–1285,2077–2084,2176–2182`). No different graph query or group data is requested by a mode change.

Low mode still uses D3 physics to find an initial arrangement, but stops its automatic timer and ticks in explicit animation-frame batches. The helper yields after approximately 6 ms per batch, and finishes on cooling, 120 ticks, or 600 ms accumulated compute/render time. It explicitly renders because `simulation.tick()` does not emit D3 tick/end events. Those are stopping checks, not hard preemption of an expensive individual tick (`src/ui/webview/graphPerformanceScript.ts:46–88`). Low-mode dragging stops unfinished layout, fixes/moves only the dragged node, zeroes velocity, redraws that node and incident geometry, and saves on release; it does not restart physics (`graphPerformanceScript.ts:91–118`; `graphView.ts:1916–1919,1950–1959`).

High mode uses interactive force simulation and reheat-on-drag, animated hover/fit, glow, label halos, flowing agent links and particles. One current-group particle loop is throttled to 30 FPS; after settling it caches path lengths. Low mode supplies no particles, removes flow/glow/halo effects, suppresses CSS animation/transitions, and uses immediate hover/fit (`graphView.ts:1080–1086,1154,1591–1594,1617–1675,1721–1759,1922–1928,2070–2074`). “High” does not mean physics runs forever: a cooled/restored settled simulation stays stopped until reheated, while particles may continue.

### Exactly what survives

| State | Group switch / mode rerender | Hide and show the retained page | Reveal via command / recreate document |
| --- | --- | --- | --- |
| Performance preference | Same global setting; mode change rerenders current group | Retained | Explicitly survives closing/reopening through configuration |
| Selected group key | Saved with `vscode.setState`; valid key reused | Retained with page | Same-title reveal sends curated groups; a structural key therefore disappears. HTML rebuild reads Webview state, but only a key still present in incoming groups is usable |
| Positions, pan/zoom, alpha/settled and auto-fit intent | Restored from bounded in-page cache if key/topology match | Saved on hide and retained in memory | Same HTML can reuse cache; HTML replacement or panel disposal creates a fresh cache. There is no application-level geometry persistence |
| Temporary structural group / selector DOM value | Group survives ordinary selections; new structural result replaces prior structural group | Retained with DOM | Curated `graphData` drops structural group. HTML replacement resets the selector to Boundary; selector value is not in Webview state |

Evidence for these lifetimes is `graphView.ts:157–203,1140–1153,1254–1278,1372–1413,1453–1454,1556–1579` and `graphPerformanceScript.ts:7–43`. The code does not provide cross-panel selected-key storage or a panel serializer in the inspected extension registration; do not promise restoration after disposal/restart simply because `getState` is used. Only the performance preference has explicit global persistence.

The cache stores geometry, transform, settled/alpha and auto-fit state, not source/evidence objects. Its topology signature consists of sorted node IDs and sorted edge source-ID/target-ID/verb tuples. Prose/evidence edits reuse geometry; changed topology invalidates it. Defaults bound it to eight groups and 2,000 total nodes; an entry also rejects nonfinite coordinates, more than 2,000 nodes, or more than 16,000 links (`graphPerformanceScript.ts:7–43`). Each render stops old work, saves its closure-bound group layout, interrupts transitions, and reconstructs nodes/links from current data. Cached positions do not replace new semantic objects (`graphView.ts:1479–1493,1504–1512,1552–1579`). Pending alpha and auto-fit are retained so rapid group switches do not falsely mark unfinished layouts as settled.

User zoom or dragging suppresses automatic fitting. Uncached low layouts fit on completion; high mode schedules a fit after one second. Manual Fit computes bounds, guards zero dimensions, clamps scale to 0.1–4, and is immediate in low versus a 750 ms transition in high. Resize is debounced by 120 ms: low mode fits; high mode reheats only while visible (`graphView.ts:1210–1231,1360–1369,1933–1959,2053–2074`). Consequently, “remember zoom” currently has a low-mode resize exception. On hide, the page suppresses CSS effects, stops particles without losing their resume callback, pauses static layout, stops simulation, interrupts transitions, clears fit/resize timers and saves geometry. On show it resumes unfinished low work or still-hot high physics and particles. Unload stops work and timers (`graphView.ts:1234–1278`). Inference/risk: a high-mode auto-fit timer canceled by hiding is not rescheduled by the visibility handler; this is a meaningful lifecycle case for any change to fit/restore behavior.

### Dependencies, correctness boundaries, and test coverage

The host/page message types, curated versus structural identities, fresh semantic payload versus cached geometry, current-group closure ownership, asynchronous setting acknowledgement, and cancellation of old frames/timers must remain aligned. Otherwise likely regressions include wrong-group source jumps, obsolete evidence appearing after cache hits, rapid switches freezing pending layouts, duplicate animation loops, lost user pan/zoom, or a disabled selector never recovering. Synchronous render exceptions and static-layout callback failures route to a separate render-error panel that stops work; this is not the same as “no data” (`graphView.ts:1458–1476,1933–1938`). Opening errors are caught separately by the extension command. Source navigation uses the first workspace root and excludes external entities; source-open errors must not be confused with layout errors (`graphView.ts:647–715`). The music button is also a selected-group consumer: it sends the selected key, but the host resolves only curated groups and falls back to the first, so structural selection currently does not mean structural music input (`graphView.ts:279–297,2115–2119`).

Existing test mapping (assertions inspected, not run):

- `src/ui/webview/graphView.test.ts:57–109` checks low/machine configuration, both localized choices, parseable emitted inline JavaScript, global save, reuse of an existing document, close/reopen performance preference, Settings synchronization, failed-save rollback and invalid-mode rejection. Its mocked host does not run the complete browser interaction or prove the selector's DOM acknowledgement/disable cycle.
- `src/ui/webview/graphPerformanceScript.test.ts:49–103` executes the shipped helper string in a VM: yielding/tick/time/cooling limits, no residual frame, hidden pause/single resume, replacement cancellation and failure cleanup. `:105–140` covers topology/prose cache behavior, transform retention, LRU group/node bounds and unfinished state; `:142–165` covers low-node-only versus high-physics dragging. This is meaningful helper coverage, not real D3/browser responsiveness measurement or end-to-end lifecycle wiring.
- `src/services/knowledgeGraphService.test.ts:60–100` protects independent duplicate-symbol groups and group-specific entity lookup. `src/ui/webview/graphWebviewClientScript.test.ts:30–38` protects relation tooltip formatting/provenance/evidence ranges and structural-path affordance.
- `src/services/structuralGraph/structuralAnalysis.test.ts:15–40,60–76,113–130` exercises source-backed impact/path results, bounded/truncated aggregation/community suggestions, and containment navigation. `src/services/structuralGraph/structuralGraphService.test.ts:150–162` checks that failed parsing retains the original error/cause and does not alter the invalid file. These do not test the advanced button/message/group-replacement/error-display integration.

Consequential gaps in the inspected tests are real-browser group switching plus zoom restoration, HTML/title rebuild versus true disposal, empty/nonempty state round-trips, structural view loss on command reveal/manual refresh, advanced drilldown caps and stale paths at the host/page boundary, visibility transitions during pending auto-fit and resize, mode switching while layout is unfinished, and D3/CSP/runtime-load failures. Cache bounds tests do not cover every rejection condition or DOM consumption of cached state. Preserve existing helper contracts and add focused lifecycle/integration cases before changing view memory or animation policy; current tests do not establish hardware performance.

## 2. Generate Copilot Instructions

### UI command and complete execution path

`package.json:85–93` contributes “Knowledge: Generate Copilot Instructions” (`knowledge.generateCopilotInstructions`) and “Generate All AI Configs”. The normal extension command awaits `EntityCommands.generateCopilotInstructions` and has an outer fallback error message (`src/extension.ts:679–701`). EntityCommands constructs its AIIntegrationService from entity, relation and observation services and also retains KnowledgeGraphService (`src/ui/commands/entityCommands.ts:23–39`). Activation creates this handler with those dependencies (`src/extension.ts:245–250`).

The handler uses `workspaceFolders?.[0]`; it does not ask the user to select a root, filename or template. If no folder exists it shows the localized no-workspace error and returns. Inside its try block it collects GraphData, passes the first root's filesystem path and GraphData to the service, waits for the returned filename, then offers Open file / Show in folder. Open calls `openTextDocument` and `showTextDocument`; reveal executes `revealFileInOS` with `Uri.file(filePath)`; dismissal performs neither (`entityCommands.ts:1255–1285`). Single generation has no progress/cancellation UI. At activation without a workspace, or after activation failure, the extension instead installs placeholder commands that show “Please open a folder…”; these are not generators (`src/extension.ts:48–57,938–942,960–998`).

The service checks whether `<workspaceRoot>/.github` exists and creates it recursively if absent. It builds text, synchronously writes UTF-8 to `<workspaceRoot>/.github/copilot-instructions.md`, and returns that path through its async API (`src/services/aiIntegrationService.ts:71–82`). The existence check is for the directory only; it does not read or inspect an existing instruction file.

One existing presentation inconsistency is source-confirmed: the caller passes `.github/${basename}` to the success formatter, while both English and Chinese formatters prepend `.github/` again. The resulting single-command success message can say `.github/.github/copilot-instructions.md`; the actual destination and subsequent open/reveal path remain correct (`entityCommands.ts:1271`; `src/i18n/en.ts:291–297`; `src/i18n/zh.ts:292–298`).

### Which inputs really affect output

| Apparent input/dependency | Actual current effect |
| --- | --- |
| `workspaceRoot` | Chooses destination and therefore filesystem success/failure; never interpolated into body |
| Graph entities, relations, observations, `sourceType` | UI collects and passes them, but service parameter `_graphData` is unused; body does not change |
| Workspace/project name, dependencies, technology stack, entity statistics or cycle analysis | No active Copilot builder call reaches these helpers |
| `ai-template.md`, active AI scenario, ScenarioManager | No active Copilot or compact Cursor builder invokes template reading |
| Interface locale | Changes UI messages; Copilot passes literal `'en'`. Cursor uses `getLocale()` and the shared builder's zh/en branches |
| MCP/index/group-file availability | Not probed by generation; only named as instructions for a later assistant |
| Preexisting destination contents | Ignored and replaced, not merged |

The causal distinction matters: `getGraphData()` obtains KnowledgeGraphService's deduplicated aggregate snapshot and loops through entity observations, assembling `{entities, relations, observations, sourceType:'knowledge'}` (`entityCommands.ts:43–63`; `src/services/knowledgeGraphService.ts:67–118`). This is not the visualizer's independent-group representation. That work is executed before the service call, so an exception there can prevent generation even though no graph content affects the resulting file. Empty graph data itself is not rejected. The service also works without a GraphData argument (`aiIntegrationService.ts:71–82`), contrary to the stale adjacent parameter comment claiming it falls back to services.

The active content call is only `generateCopilotInstructions → buildCopilotInstructionsContent → buildAgentKnowledgeRouterContent('en', '# VibeKnowledge Agent Instructions')`. The shared function joins constant English/Chinese lines, with no project reads, timestamps or model calls (`aiIntegrationService.ts:404–448`). It produces a compact English routing document, not a project-specific knowledge export. Entity/Relation/Observation services and the constructed DependencyAnalyzer exist on the class but are not consulted by that builder (`aiIntegrationService.ts:42–51`).

Long-form Cursor CN/EN builders remain in the class and contain project name, graph, statistics, technology stack and template logic, but the public Cursor path calls the compact router instead (`aiIntegrationService.ts:58–63,101–119,259–264,376–408`). The helper `readCustomAITemplate` would fetch the active ScenarioManager template (`:691–713`), and tech-stack extraction would probe package.json/Maven/Python manifests (`:857–889`), but neither is reachable from the active instruction builders. Editing those dormant helpers alone therefore will not make current Copilot output project-specific. This conclusion follows the active call chain, not the presence or names of imports.

### Shared generation paths and intended use

There are three relevant shared paths:

1. Public Cursor generation writes `.cursorrules`, ignores graph data in its active builder, and calls the same router with a locale-dependent title/language (`aiIntegrationService.ts:58–63,101–109`). Changing the shared router changes both products; changing only the Copilot wrapper can remain Copilot-specific.
2. UI “Generate All AI Configs” independently orchestrates Cursor then Copilot, within non-cancellable notification progress, and offers either completed file for viewing (`entityCommands.ts:1290–1334`). It calls the two individual methods, not the service's bulk method. The service also exposes `generateAllAIConfigs`, which runs the same sequence and returns an array of paths (`aiIntegrationService.ts:89–96`). Both must remain consistent if inputs or output paths change.
3. Switching AI scenario can prompt to regenerate, and selecting Generate executes `knowledge.generateAllAIConfigs` (`src/commands/scenarioCommands.ts:62–81`). Despite that UI connection, changing scenario does not change the current compact instruction body: the regenerated builders do not read the scenario. This is an existing expectation mismatch, not evidence of project customization.

The file is intended as repository-level GitHub Copilot/agent guidance. It tells the later assistant to use VibeKnowledge MCP `query_graph` for architecture/unfamiliar/cross-file/dependency/impact work when available, with a focused question and token budget; expand locally with `get_entity`, `get_neighbors` or `shortest_path`; request `includeEvidence=true` only for relationship auditing. If MCP is unavailable/unhelpful it points to `.vscode/.knowledge/agent-context/index.md` and one matching group; it discourages default loading of the full knowledge-graph audit report, allows known-file small tasks to skip the graph, requires current-source verification and forbids direct graph.sqlite editing (`aiIntegrationService.ts:432–447`).

Those are text instructions for a consumer, not actions performed by this command. Generation does not configure/install MCP, invoke its tools, create or validate the index/group files, regenerate graph artifacts, inspect source, modify graph.sqlite, send data to an AI model, or prove Copilot has discovered/followed the file. A successful write establishes only that this filesystem operation completed; downstream resource availability and actual Copilot behavior were not validated here (`aiIntegrationService.ts:71–82,404–448`).

### Existing files, errors, and change boundaries

`writeFileSync` overwrites an existing target without confirmation, merge, backup or atomic replacement. Thus custom edits can be lost on any direct or bulk regeneration. Errors creating `.github`, building content or writing reject the service promise; the service does not roll back a newly created directory or an overwritten/partially written file (`aiIntegrationService.ts:71–82`). Inference: an interrupted/failed non-atomic write cannot be assumed to preserve the old file. A path called `.github` that exists but is not a directory bypasses mkdir and fails at the write; no separate validation exists.

The UI try/catch also surrounds graph collection, the success notification, document opening and OS reveal. A file can therefore already have been successfully written—and success shown—before a later open/reveal error is reported as a generation failure. The catch does not remove or restore it (`entityCommands.ts:1262–1284`). Ordinary errors are handled there and not rethrown; the outer extension catch is fallback for errors escaping that handler (`src/extension.ts:680–687`).

Both bulk paths are sequential and non-transactional. Cursor may already have been overwritten when Copilot fails; neither path reverts it. UI bulk failure skips the final success chooser and shows the localized error, while programmatic bulk rejects instead of returning its partly accumulated path array (`aiIntegrationService.ts:89–96`; `entityCommands.ts:1300–1334`). “More project-specific” generation would add genuinely new content dependencies and failure modes; decisions about their absence, sensitive observations, size limits, multi-root selection, preservation of user text and shared Cursor impact should be explicit rather than inferred from dormant code.

### Existing tests and consequential gaps

`src/services/aiIntegrationService.test.ts:68–98` creates a temporary workspace and an ai-template marker, invokes Copilot generation without GraphData, reads the result and checks compact query/index/single-group guidance, selected evidence policy and audit-report avoidance. It excludes the marker and “Tech Stack”, “Dependency Details” and “Total Entities”. This protects the current compact contract and demonstrates a basic service write without graph-service APIs being supplied (`:42–47,78–81`). It does not prove every possible rich graph input is ignored, nor does marker exclusion alone exercise a real active scenario; the call chain provides those implementation facts.

The adjacent Cursor test (`:100–119`) protects shared compact routing and absence of template/graph dumps. Private technology-stack tests (`:50–58,121–162`) check that `@types/node` is not mistaken for the runtime and that engines/.nvmrc declarations are recognized. Those tests exercise a helper directly, not Copilot project-specific content; they are not coverage of the proposed behavior. KnowledgeGraphService's aggregate test (`src/services/knowledgeGraphService.test.ts:11–58`) protects upstream deduplication, but not whether generated text consumes it.

The inspected source/tests search found no command-level or bulk/scenario-generation test beyond these service content cases. Important gaps are exact destination/return-path assertions, overwrite/user-content preservation policy, mkdir/write/partial failure, first-root versus no-workspace behavior, snapshot/observation failure before the service, notification dismissal/open/reveal failures, duplicate `.github` success text, Copilot English invariance versus Cursor localization, shared-builder parity, bulk partial success and scenario-regeneration expectations. There are no tests establishing actual MCP/index availability or Copilot discovery/execution. Before changing the output contract, add tests using genuinely different project inputs and assertions about the intended retained compact routing, shared consumers, destination/error behavior and existing user text; simply extending helper tests would leave the actual command contract unprotected.
