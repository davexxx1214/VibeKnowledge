# Read-only feature impact analysis

Scope: the visualization page/view interaction contract, followed by Generate Copilot Instructions. This report is based on source and existing test inspection only; no tests or builds were run. Source citations are workspace-relative `path:line` references. “Fact” describes the current implementation; “implication/gap” identifies consequences or risks inferred from that implementation, not verified runtime failures.

## 1. Visualization

### Command → host → page

The command palette contribution is `knowledge.visualizeGraph` (“Knowledge: Visualize Graph”), also exposed in the Knowledge Graph explorer's title navigation (`package.json:57`, `package.json:244`). Activation injects the KnowledgeGraphService and StructuralGraphService into GraphView (`src/extension.ts:242`). The registered command calls `GraphView.createOrShow(context.extensionUri)` inside a synchronous error boundary that reports “Error opening graph” (`src/extension.ts:643`).

GraphView is a singleton panel. A new panel enables scripts and retains context when hidden. Its constructor installs HTML, the page-message handler, disposal handling, and a configuration listener. Reissuing the command reveals an existing panel in column one: normally it sends graph data without replacing HTML; if the translated title differs, it replaces HTML (`src/ui/webview/graphView.ts:128`, `src/ui/webview/graphView.ts:157`, `src/ui/webview/graphView.ts:199`). This distinction matters: revealing is not equivalent to reconstructing the page.

The page uses locally packaged D3 (`dist/d3.min.js`), a nonce/CSP, and two embedded helper scripts, not the repository's vis-network resource. Its load handler initializes the SVG and sends `ready`; the host responds with the effective performance mode and ordinary graph data (`src/ui/webview/graphView.ts:718`, `src/ui/webview/graphView.ts:751`, `src/ui/webview/graphView.ts:1137`, `src/ui/webview/graphView.ts:1205`, `src/ui/webview/graphView.ts:205`). D3 is copied into the distribution by `esbuild.js:12` and `esbuild.js:22`. Packaging or generated-script syntax failures can therefore prevent initialization before the normal render-error boundary is reached.

### Ordinary groups and structural views are deliberately different

**Ordinary groups.** The host calls `KnowledgeGraphService.getGroups()`, not the deduplicated aggregate snapshot. That method preserves repeated symbol occurrences in independent Agent groups (`src/services/knowledgeGraphService.ts:147`). `_collectGraphGroups()` creates browser view models containing group identity/order, entity positions in source, provenance, descriptions, observations, structural keys, and relation evidence/path metadata; absence of the graph service yields an empty list (`src/ui/webview/graphView.ts:456`). In the concrete KnowledgeGraphService implementation, `getObservations()` currently returns an empty array, so the observation-capable view model does not presently receive observations from this service (`src/services/knowledgeGraphService.ts:256`).

The host posts `{type: 'graphData', data: {groups, mode: 'knowledge'}}`. The browser replaces its group collection, sorts by `order` then `name`, rebuilds text-based sidebar buttons, and selects the saved key if present, otherwise the first group. A click records the selected key, marks the active button, and renders only that group (`src/ui/webview/graphView.ts:263`, `src/ui/webview/graphView.ts:1287`, `src/ui/webview/graphView.ts:1372`, `src/ui/webview/graphView.ts:1423`, `src/ui/webview/graphView.ts:1449`). The browser does not interpret the `mode: 'knowledge'` field to choose another graph source.

**Advanced structural overview.** The toolbar offers boundary/community/file aggregation; the advanced button sends `requestStructuralOverview` using the current selector value. Merely changing that selector does not issue a request (`src/ui/webview/graphView.ts:1101`, `src/ui/webview/graphView.ts:2091`, `src/ui/webview/graphView.ts:2173`). The host reads StructuralGraphService on demand and calls `aggregateStructuralGraph` with `limit: 80`, then produces a special group keyed `__structural_<level>`, with counts, aggregate file membership, and original structural hops on aggregate relations (`src/ui/webview/graphView.ts:324`, `src/ui/webview/graphView.ts:518`).

A `structuralGroup` response removes all previous `__structural_` groups from the browser collection, appends the new group, selects it, and displays a temporary node/relation count. Ordinary groups remain available, but only one structural result is kept in the sidebar (`src/ui/webview/graphView.ts:1401`). This is temporary browser state, not a saved curated group or another permanent graph source.

The drill-down paths must remain distinct:

- Double-click a relation or its label with a nonempty `structuralPath`: send `drillDownRelation`. The host matches hops against structural relations using source, target, verb, file, start and end lines, and includes their endpoints. An empty/missing path is an error; a nonempty path with no matching relations can produce an empty result rather than an error (`src/ui/webview/graphView.ts:1599`, `src/ui/webview/graphView.ts:1685`, `src/ui/webview/graphView.ts:340`, `src/ui/webview/graphView.ts:627`).
- Shift-double-click a curated entity with a structural key, or use its context menu: send `drillDownEntity`. The host requests depth-one impact in both directions, deduplicates relations, limits to 120 relations and 80 entities, and filters edges whose endpoints were excluded (`src/ui/webview/graphView.ts:1778`, `src/ui/webview/graphView.ts:1791`, `src/ui/webview/graphView.ts:365`).
- Double-click an aggregate: send its aggregate ID, level and file list. The host prioritizes that file membership, otherwise resolves a file/boundary, and returns up to 80 entities and 120 internal relations (`src/ui/webview/graphView.ts:1761`, `src/ui/webview/graphView.ts:407`). Raw slices receive timestamp-based group keys; entity IDs are SHA-1-derived browser-safe identities (`src/ui/webview/graphView.ts:564`, `src/ui/webview/graphView.ts:643`).
- Double-click a raw structural entity opens its resolved source location; ordinary double-click opens the curated entity location through KnowledgeGraphService. External entities do not open source. Both routes convert one-based lines to zero-based editor ranges and use the first workspace folder (`src/ui/webview/graphView.ts:1771`, `src/ui/webview/graphView.ts:1785`, `src/ui/webview/graphView.ts:647`, `src/ui/webview/graphView.ts:687`).

Structural service/read/analysis errors post `structuralError` and a host warning. The page clears loading and displays an error status, without replacing the current graph (`src/ui/webview/graphView.ts:450`, `src/ui/webview/graphView.ts:1296`). Missing ordinary service data instead leads to the empty state. A rendering exception while selecting a group stops animation/layout and presents the dedicated render-error UI (`src/ui/webview/graphView.ts:1458`, `src/ui/webview/graphView.ts:1465`). These are different failure outcomes, not one generic “empty graph” result.

### Performance selection changes rendering, not graph content

The setting is `knowledgeGraph.visualization.performanceMode`, enum `low|high`, machine-scoped and defaulting to `low` (`package.json:325`). The host treats only exact `high` as high; browser normalization does the same. The selector applies the mode optimistically, rerenders the selected group only when the mode changes, disables itself, and posts `setPerformanceMode`. The host accepts only the two valid values, writes the **Global** configuration target, then always posts the actual effective value back, including after a failed write. The response re-enables the selector; external Settings changes also post the effective value (`src/ui/webview/graphView.ts:300`, `src/ui/webview/graphView.ts:150`, `src/ui/webview/graphView.ts:2077`, `src/ui/webview/graphView.ts:2176`, `src/ui/webview/graphPerformanceScript.ts:3`). Thus settings failure can roll the optimistic page back; it must not silently leave the page at an unsaved mode.

Both modes build the same entities, relations, labels, source interactions, and D3 force model. Nodes/links are copied before D3 mutates them (`src/ui/webview/graphView.ts:1504`, `src/ui/webview/graphView.ts:1552`, `src/ui/webview/graphView.ts:1566`). The differences are:

- **Low:** normal simulation scheduling is stopped. Unsettled layouts run explicit D3 ticks in animation-frame batches, rendering after each batch. Batches target under 6 ms; the process ends on cooling, 120 ticks, or 600 ms accumulated computation, then sets alpha to zero. Those budgets are checked between ticks/batches, so they are not a hard interruption deadline for a single slow tick. `tick()` does not emit D3 tick/end events, hence the explicit render/completion callbacks (`src/ui/webview/graphPerformanceScript.ts:46`, `src/ui/webview/graphView.ts:1933`). No particles, flowing dashes, glow, text shadow, halo labels, or animated transitions are needed; ordinary relation labels and hover highlighting still work (`src/ui/webview/graphView.ts:1080`, `src/ui/webview/graphView.ts:1594`, `src/ui/webview/graphView.ts:1618`, `src/ui/webview/graphView.ts:1668`, `src/ui/webview/graphView.ts:1727`).
- **High:** interactive D3 cooling/reheating remains. Agent edges get animated flow, particles run in one selected-group requestAnimationFrame loop throttled to approximately 30 fps, and effect/transition layers are enabled. Paths are indexed once; settled lengths are cached and invalidated when geometry changes. A settled cached layout does not restart merely because it is displayed in high mode (`src/ui/webview/graphView.ts:1572`, `src/ui/webview/graphView.ts:1624`, `src/ui/webview/graphView.ts:1823`, `src/ui/webview/graphView.ts:1922`).
- **Drag:** low mode stops layout, moves only the dragged node, zeroes its velocity, and redraws its incident geometry without restarting physics. High mode reheats the force simulation. Both temporarily set `fx/fy`, clear those pins at drag end and save layout (`src/ui/webview/graphPerformanceScript.ts:91`, `src/ui/webview/graphView.ts:1950`).
- **Fit/resize:** fit clamps zoom to 0.1–4 with padding, immediately in low mode and with a 750 ms transition in high. New low layouts fit on completion; high layouts schedule an initial fit after one second. User zoom initiation/drag cancels auto-fit eligibility. Resize is debounced 120 ms, updates the center force, explicitly fits in low mode, and reheats high mode only while visible (`src/ui/webview/graphView.ts:1210`, `src/ui/webview/graphView.ts:1360`, `src/ui/webview/graphView.ts:1933`, `src/ui/webview/graphView.ts:2053`). A low-mode resize can therefore change the viewport even after a manual pan; preserving manual view across resize would be a behavioral change, not existing behavior.

### What “remember the view” currently means

| Event/state | Current contract and boundary |
| --- | --- |
| Selected ordinary group | Only `selectedGroupKey` is written with `vscode.setState` and read back during page initialization. It is not the whole view. Selection falls back to the first ordinary group when the stored key is absent (`graphView.ts:1150`, `graphView.ts:1396`, `graphView.ts:1453`). |
| Switching groups or performance mode | The old simulation/layout/particles stop and its layout is saved before SVG children are replaced. Cache restores x/y positions, zoom transform, alpha, settled status and auto-fit eligibility if the topology signature matches (`graphView.ts:1479`, `graphView.ts:1556`, `graphView.ts:1575`). No velocities, node pins, hover state, full source/evidence payload, or durable graph collection is cached. |
| Cache validity and retention | Per-page LRU defaults to at most eight group entries and 2,000 total nodes. Oversized entries, over 16,000 links, or non-finite node coordinates are rejected. Signature uses sorted node IDs and sorted source-ID/target-ID/verb tuples: prose/evidence changes reuse geometry, topology changes invalidate it. It is a JavaScript Map, not `setState` or disk (`src/ui/webview/graphPerformanceScript.ts:7`). |
| Reveal using the command | With unchanged title, HTML survives but new ordinary `graphData` replaces the group list and rerenders. An ordinary selected group can retain geometry via cache. A selected structural group is absent from that new list, so it is removed and selection falls back. The same applies to the page's refresh button (`graphView.ts:157`, `graphView.ts:1372`, `graphView.ts:2086`). |
| Hide and show without reissuing command | `retainContextWhenHidden` preserves the page collection/cache. Visibility change cancels particles without losing the resume callback, pauses static layout, stops simulation, interrupts transitions, clears fit/resize timers, and saves layout. On show, unfinished low layout resumes; high simulation restarts only if above alphaMin; particles can resume. CSS effects are paused too (`graphView.ts:176`, `graphView.ts:1254`, `graphView.ts:1080`). |
| Page replacement / actual close and reopen | A title-triggered HTML replacement constructs fresh in-memory cache/groups, with only the selected key eligible for Webview state restoration. Disposal clears the singleton/listeners; a later open creates a new panel. No panel serializer or application-level group/layout persistence is implemented in this path, so durable reopening of the old group/view is not promised. Performance does survive because it is a global machine setting (`graphView.ts:157`, `graphView.ts:186`, `graphView.ts:1138`, `graphView.ts:300`). |
| Empty data / removed groups | An empty group list clears live selected key, simulation and cache, removes SVG content and shows empty state, but does not call `setState` to clear the old stored key. A present group with zero entities still becomes selected, then renders empty. Structural raw slices use new timestamp keys, making repeat drill-down cache reuse different from stable ordinary-group keys (`graphView.ts:1378`, `graphView.ts:1495`, `graphView.ts:576`). |

In the table, abbreviated `graphView.ts` means `src/ui/webview/graphView.ts`.

**Implications for a change:** preserve the separation between durable machine preference, Webview selection state and bounded geometry cache. Preserve graph identity/topology checks rather than caching source metadata; switching a group must stop its callbacks so stale render/particle/fit work cannot affect the next group. Do not merge duplicate symbol occurrences across ordinary groups just because aggregate search deduplicates them. A richer persistence design would need explicit decisions about structural-result lifetime, removed groups, cache invalidation, viewport size changes and true panel disposal. The current cancellation of a high-mode fit timer on hide has no corresponding rescheduling on show; code resumes physics/particles, not that initial fit timer (`graphView.ts:1254`, `graphView.ts:1940`).

## 2. Generate Copilot Instructions

### UI entry and the actual inputs

`package.json:86` contributes `knowledge.generateCopilotInstructions` with the title “Knowledge: Generate Copilot Instructions”. Its extension handler awaits `entityCommands.generateCopilotInstructions()` and has an outer log/error boundary (`src/extension.ts:680`). EntityCommands constructs AIIntegrationService with entity, relation and observation services; that constructor also creates a DependencyAnalyzer, whose own constructor only stores service references (`src/ui/commands/entityCommands.ts:23`, `src/services/aiIntegrationService.ts:45`, `src/services/dependencyAnalyzer.ts:49`). Merely seeing those dependencies is not proof that generation uses their data.

The command selects `workspaceFolders?.[0]`, reports a localized error and returns if absent, and otherwise computes `getGraphData()` before calling the service with the first workspace folder's filesystem path. There is no target picker, graph-group selector, scenario question or save dialog in this command (`src/ui/commands/entityCommands.ts:1255`). Activation with no workspace instead registers placeholder commands and returns before real service setup (`src/extension.ts:48`).

`getGraphData()` obtains the unified snapshot, collects per-entity observations, and supplies `{entities, relations, observations, sourceType: 'knowledge'}` (`src/ui/commands/entityCommands.ts:42`). The snapshot deduplicates Agent entities across groups, remaps relation endpoints and excludes unresolved/self-collapsed endpoints (`src/services/knowledgeGraphService.ts:67`). The concrete observation method returns `[]`, making that collected list currently empty (`src/services/knowledgeGraphService.ts:256`).

However, `AIIntegrationService.generateCopilotInstructions(workspaceRoot, _graphData?)` ignores its second argument and calls a zero-argument content builder. The builder always calls `buildAgentKnowledgeRouterContent('en', '# VibeKnowledge Agent Instructions')`; the shared builder assembles fixed string arrays and joins them with newlines (`src/services/aiIntegrationService.ts:71`, `src/services/aiIntegrationService.ts:404`, `src/services/aiIntegrationService.ts:411`).

| Apparent input/dependency | Actual effect on current Copilot generation |
| --- | --- |
| `workspaceRoot` | Determines `.github/copilot-instructions.md` destination and directory creation, not content (`aiIntegrationService.ts:71`). |
| GraphData: entities, relations, observations, source type | UI pays collection cost and can fail collecting it, but content ignores it. Direct service calls work without GraphData (`entityCommands.ts:1262`, `aiIntegrationService.ts:71`). |
| Entity/Relation/Observation services; DependencyAnalyzer | Constructed dependencies; no analyzer/list/query call occurs in the active Copilot builder. No dependency statistics or entity dump is produced (`aiIntegrationService.ts:45`, `:404`, `:411`). |
| Project name, packages/manifests, language/runtime/frameworks | Not read by the active builder. No project name or generated timestamp is embedded. The old rich Cursor builders use these, but active generation does not dispatch to them (`aiIntegrationService.ts:101`, `:114`, `:259`, `:404`). |
| Scenario, custom template, `knowledgeGraph.aiConfig.maxRelationsDisplay` | No effect on current output. `readCustomAITemplate`, tech-stack extraction, relation display limit, stats and categorized observations belong to the unused rich-builder chain (`aiIntegrationService.ts:233`, `:378`, `:691`, `:718`, `:736`, `:806`, `:857`; setting contribution `package.json:416`). |
| UI language / locale | Notifications are localized through `t()`, but Copilot file content is explicitly English (`entityCommands.ts:1269`, `aiIntegrationService.ts:404`). |
| MCP availability, existing graph/index files, RAG/Gemini/AI model | No availability check, query execution, graph generation, network call or model inference occurs in this generation path. Their names in the output are guidance for a future consumer, not executed dependencies (`aiIntegrationService.ts:71`, `:411`). |

In the table, `aiIntegrationService.ts` means `src/services/aiIntegrationService.ts`; `entityCommands.ts` means `src/ui/commands/entityCommands.ts`.

**Causal implication:** a slow or throwing `getSnapshot()`/observation lookup can block the UI command before it writes a perfectly static file. Conversely, making old tech-stack/template helpers more sophisticated cannot make today's Copilot output project-specific without connecting new data into the active builder. The optional-GraphData documentation promising fallback service data is stale for this path (`src/services/aiIntegrationService.ts:66`).

### Intended output versus actions performed

The generated file is a compact repository-level agent/Copilot instruction document: treat the Knowledge Graph as an on-demand dependency navigator; for architecture/unfamiliar/cross-file/dependency/impact tasks use MCP `query_graph` when available with a focused question/token budget, then selectively expand with `get_entity`, `get_neighbors` or `shortest_path`; request evidence only for auditing. If MCP is unavailable or unhelpful, read the agent-context index and just the best-matching group. Do not load the full audit report by default; skip graph lookup for small known-file tasks; verify current source before editing/testing; never edit graph.sqlite (`src/services/aiIntegrationService.ts:432`).

These are instructions **to an assistant consuming the file**. The generator itself only computes those strings, ensures `.github` exists, writes UTF-8 and returns the path. It neither reads the referenced artifacts nor installs MCP, runs graph tools, refreshes a graph, edits SQLite, edits source, sends content to Copilot, or validates whether Copilot consumed the file (`src/services/aiIntegrationService.ts:71`). The intended tool behavior is therefore distinct from generation side effects.

### Destination, overwrite and completion/error semantics

The service computes `<workspaceRoot>/.github`, creates it recursively only if it does not exist, then uses `fs.writeFileSync(filePath, content, 'utf-8')` at `<workspaceRoot>/.github/copilot-instructions.md` (`src/services/aiIntegrationService.ts:72`). There is no existing-destination read, merge, preservation block, confirmation, backup, exclusive-create flag, temporary-file swap or rollback.

Consequences of those concrete operations:

- Existing instructions are replaced wholesale, including hand-written project rules. An existing `.github` directory is reused. If `.github` is a file or the target cannot be written, filesystem failure rejects the async service call.
- Synchronous filesystem APIs run on the extension host even though the method is declared async. The service has no local catch, so exceptions propagate to its caller. Directory creation or a partial/truncated write is not undone; no atomicity/recovery guarantee is implemented.
- On success, EntityCommands shows “Open file” and “Show in folder”. Open uses the returned path with `openTextDocument` then `showTextDocument`; reveal executes `revealFileInOS` with `Uri.file(filePath)`. Dismissing the notification leaves the newly written file in place (`src/ui/commands/entityCommands.ts:1269`).
- Graph collection, service generation, success notification and the selected open/reveal action share one try/catch. A post-write open/reveal failure is reported as generation failure even though the file already exists; errors are displayed, not rethrown by this handler. The extension-level catch is an outer fallback for escaping failures, not an additional rollback (`src/ui/commands/entityCommands.ts:1262`, `:1282`; `src/extension.ts:680`).
- A concrete presentation defect: EntityCommands passes `.github/<basename>` to `translations.success`, while both English and Chinese success functions prepend another `.github/`. The displayed success path is therefore `.github/.github/copilot-instructions.md`, whereas writing/opening/revealing uses the correct actual path (`src/ui/commands/entityCommands.ts:1271`, `src/i18n/en.ts:293`, `src/i18n/zh.ts:294`).

### Related paths share content, but not all orchestration

Cursor generation writes `<workspaceRoot>/.cursorrules`; its active builder also ignores GraphData and calls `buildAgentKnowledgeRouterContent`, with a Cursor-specific title (`src/services/aiIntegrationService.ts:58`, `src/services/aiIntegrationService.ts:101`). A shared router change therefore affects both products; a Copilot-only change belongs at its wrapper/builder boundary if that is the intended scope.

There is an actual locale mismatch in Cursor's active path: it tests `getLocale() === 'zh'`, but `getLocale()` delegates to `getLocaleCode()` returning `zh-CN` or `en-US`. With the current implementation it selects English even in Chinese UI; Copilot is separately hard-coded English (`src/services/aiIntegrationService.ts:101`, `src/i18n/i18nService.ts:126`, `src/i18n/i18nService.ts:148`). The existence of a Chinese shared string array does not imply it is reached by the present Cursor caller.

`AIIntegrationService.generateAllAIConfigs()` calls Cursor then Copilot sequentially and returns both paths. The UI's Generate All command does **not** call that wrapper: it repeats the two service calls inside non-cancellable notification progress (0/50/100), collecting GraphData once, then offers to view either file (`src/services/aiIntegrationService.ts:89`, `src/ui/commands/entityCommands.ts:1290`, `src/extension.ts:692`). Both entry paths use the same individual generators, but orchestration is duplicated. If Cursor fails, Copilot is not attempted; if Copilot fails, the already-written Cursor file stays changed. Neither path is transactional.

Switch AI Scenario is an additional route: after a scenario change it offers regeneration, and accepting invokes `knowledge.generateAllAIConfigs` (`src/commands/scenarioCommands.ts:62`). It changes scenario state, but current output still bypasses the ScenarioManager-based template helper. Thus a scenario change can cause files to be overwritten without producing scenario-specific instruction text.

### Existing tests and consequential gaps

`src/services/aiIntegrationService.test.ts:68` directly calls the service in a temporary workspace, with empty objects for the three service dependencies (`:42`). It asserts a compact Copilot router includes the fallback index, query/navigation tools, evidence flag, one-group fallback and avoidance of default full-report loading, and excludes an `ai-template.md` marker and rich graph/tech-stack sections. This protects the current query-first/no-dump design and exercises successful directory/file generation without real graph services. It does not test the UI's graph-data collection.

`src/services/aiIntegrationService.test.ts:100` similarly protects the active Cursor router and absence of template/graph dumps. The tech-stack tests at `:121` and `:144` call the private JavaScript extractor through a type escape (`:50`): they check that `@types/node` is not a runtime declaration, and support engines/.nvmrc. They are helper tests, **not evidence that either current instruction generator uses tech-stack detection**.

Consequential gaps in the inspected tests:

- No comparison across nonempty/distinct GraphData values, workspace identities, timestamps, scenario changes or UI locales. Copilot's deliberate English behavior and Cursor's `zh`/`zh-CN` mismatch lack explicit coverage. The test writes a template but has `workspaceFolders: undefined`, so it is not an end-to-end configured-scenario test (`src/services/aiIntegrationService.test.ts:16`, `:68`).
- No explicit existing-instructions preservation/overwrite contract, exact destination-path assertion, repeat generation, `.github`-is-file, permission/write failure, partial-write handling or filesystem rejection assertion. Read-after-success confirms a file was written, but does not establish recovery guarantees.
- No command tests for no workspace, first-folder choice, empty or failing graph collection, notification dismissal, open/reveal actions, or their post-write failures. No test catches the duplicated `.github/` success label.
- No tests for either Generate All orchestration or partial success/failure ordering, nor scenario-triggered regeneration. Changing one orchestration path alone could diverge them.
- The no-dump assertions are selected substring checks, not an enforced size budget or complete file contract; `get_entity`, known-file skip, source-verification and SQLite guidance are not all asserted by the Copilot test. A future project-specific implementation needs explicit decisions/tests for bounded output, which project facts are included, provenance/current-source verification, escaping/untrusted descriptions, custom-rule overwrite, and whether both products should change together. These are proposed verification needs, not implemented features.

Bottom line: current Copilot generation is deterministic fixed guidance plus filesystem/UI handling, with an unnecessary graph-collection dependency at the UI layer. Project-specific generation is an actual contract change: it must deliberately connect inputs to content, preserve the navigation-only intent where required, and define overwrite/error behavior rather than assuming the numerous older helpers already participate.
