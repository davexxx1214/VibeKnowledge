# Entity descriptions and MCP setup

Read-only source analysis; no source changes, package installation, network requests, builds, or tests were run. The installed query skill supplied feature briefs, then task-critical claims were checked against source. Citations are repository-relative `path:line` locations. **Fact** means directly observed code/test behavior; **inference** means a consequence or risk not demonstrated at runtime.

## 1. Entity descriptions

### Edit/reset → durable override → composed graph

**Fact.** `knowledge.editEntityDescription` accepts a tree item, an object with an ID, or an ID string. It re-resolves the entity through `KnowledgeGraphService`; if that fails it offers a QuickPick of aggregate entities. The input starts with the currently displayed description. `undefined` cancels; `''` is a valid saved override. An update returning `null` produces an error. Restore has no selection fallback: unresolved/non-Agent entities return silently, and the command announces success without checking the reset method's nullable result. (`src/ui/commands/entityCommands.ts:225`, `:242`, `:252`, `:268`, `:279`.) File CodeLens passes an entity ID to edit (`src/providers/codeLensProvider.ts:42`).

**Fact.** Activation wires `DatabaseService → AgentEntityOverrideService → AgentGraphService → KnowledgeGraphService → EntityCommands` (`src/extension.ts:63`, `:175`, `:246`). `KnowledgeGraphService.getEntity` searches the aggregate and then independent groups, so an occurrence not retained by aggregate de-duplication can still be edited. Update/reset delegate to `AgentGraphService`, which requires both a current entity and an override store. (`src/services/knowledgeGraphService.ts:192`, `:261`, `:276`; `src/services/agentGraph/agentGraphService.ts:143`.)

**Fact.** The mutation writes `agent_entity_overrides(agent_key, description, updated_at)` in `.vscode/.knowledge/graph.sqlite`, not the generated `agent-graph.json` or legacy `entities.description`. Edit is a parameterized upsert plus `save()`; reset deletes the matching override plus `save()`. SQLite is loaded into sql.js memory, and saving exports and synchronously rewrites the database file. (`src/services/agentGraph/agentEntityOverrideService.ts:47`, `:61`; `src/services/database.ts:17`, `:37`, `:118`, `:165`.)

**Fact.** Override scope is the stable entity **key**, whereas occurrence IDs incorporate group key plus entity key. Snapshot construction applies the override to every occurrence and retains `metadata.generatedDescription` and `descriptionSource`. It distinguishes absence from an empty string. Thus regeneration can change each group's underlying prose without replacing human prose; reset reveals each group's newest generated text, not a saved historical version. Aggregate entities keep the first normalized-identity occurrence; visualization groups retain duplicates. (`src/services/agentGraph/agentGraphService.ts:153`, `:165`, `:541`; `src/services/knowledgeGraphService.ts:67`, `:147`.) Entity edits do not change relation descriptions, group descriptions, or graph structure.

**Fact.** Lookup prefers an exact stored key, then a *unique* normalized identity match. Reset uses the same rule; ambiguous normalized matches are deliberately not selected. Set/upsert targets the exact current key rather than consolidating aliases. (`src/services/agentGraph/agentEntityOverrideService.ts:22`, `:47`, `:61`, `:78`.) Tests demonstrate portable slash spelling, case-distinct path-symbol identities, and ambiguous fallback handling (`src/services/agentGraph/agentEntityOverrideService.test.ts:28`, `:50`). **Inference:** a true key/identity change can orphan an override; reset of an exact alias may reveal another remaining equivalent row. “Stable” is essential to persistence across regeneration.

| Explorer and its description search | Command wrappers refresh the tree after the handler resolves. Tree refresh reloads the graph and fires its change event; tooltips display prose (including an explicit empty-description marker), and filtering searches description text. (`src/extension.ts:548`; `src/providers/treeDataProvider.ts:70`, `:172`, `:346`.) |
| Open graph webview | The same wrappers call `GraphView.refresh()`. It posts rebuilt group data from `getGroups()`, including each occurrence's effective description. (`src/extension.ts:555`, `:569`; `src/ui/webview/graphView.ts:124`, `:263`, `:462`.) |
| CodeLens | Explicit change event causes models to be rebuilt from current graph entities. Titles use compacted description, falling back to name. (`src/providers/codeLensProvider.ts:28`, `:73`; `src/providers/knowledgeCodeLensModel.ts:37`.) |
| Hover, entity details, exports/AI graph data | Hover resolves from the graph on each request; detail output includes the resolved entity description. `EntityCommands` injects the graph into `ExportService`, whose helpers prefer it over legacy entities, and builds AI graph data from its snapshot. These are newly requested outputs, not subscriptions that rewrite previously exported files or open text documents. (`src/providers/hoverProvider.ts:25`, `:42`; `src/ui/commands/entityCommands.ts:29`, `:43`, `:338`; `src/services/exportService.ts:685`, `:697`.) |
| MCP graph search/query | Merged search gets the database override map and applies it before searching descriptions. Graph-query engines are constructed with fresh override maps. MCP uses a read-only `better-sqlite3` connection, opened at server startup. (`packages/mcp-server/src/mergedGraph.ts:27`, `:110`; `packages/mcp-server/src/agentGraphStore.ts:342`, `:564`; `packages/mcp-server/src/tools/registerGraphQueryTools.ts:251`; `packages/mcp-server/src/database.ts:119`, `:380`; `packages/mcp-server/src/index.ts:13`.) |
| Portable query CLI | Curated entity/query commands open the existing SQLite file read-only through `node:sqlite`, validate/read overrides, close it, and build entities with those overrides. No database/table gives an empty map; corrupt SQLite errors propagate. Structural/context branches and overview return before reading overrides, so not every query is a description consumer. (`packages/mcp-server/src/queryCli.ts:47`, `:70`, `:97`, `:107`.) |

**Fact.** A manifest create/change/delete watcher also refreshes tree, webview, and CodeLens (`src/extension.ts:265`). Command wrappers refresh even after cancellation, a silent reset no-op, or a handled null-update failure; a thrown exception skips the refreshes and is logged/shown (`src/extension.ts:548`). Empty prose remains the effective value although truthy-only renderers such as hover hide the description section (`src/providers/hoverProvider.ts:42`).

### Important boundaries and failures

- **Fact / inference:** The extension's graph/database and manifest watcher are anchored to the **first** workspace folder (`src/extension.ts:57`, `:64`, `:176`, `:268`). CodeLens/hover derive paths relative to the document's own folder (`src/providers/codeLensProvider.ts:58`; `src/providers/hoverProvider.ts:101`). In a multi-root window, another folder's same relative path can therefore be resolved against the first folder's graph; this is a scope risk, not verified runtime behavior.
- **Fact / inference:** SQL mutation happens before file export, without using `DatabaseService.transaction`; a failed save throws before graph refresh (`src/services/agentGraph/agentEntityOverrideService.ts:56`, `:73`; `src/services/database.ts:165`). Therefore failure can leave changed in-memory SQL, stale cached prose, and old/partially written disk state. No rollback or atomic temporary-file replacement is present in this path. UI error does not prove the edit was wholly undone.
- **Fact / inference:** Manifest read/parse/override-read errors are caught by `load()`, replacing the snapshot with empty data and retaining the error/signature; missing manifests also yield empty data (`src/services/agentGraph/agentGraphService.ts:232`). An entity disappearing during the edit can return null. A reset can misleadingly announce success because the UI ignores that result (`src/ui/commands/entityCommands.ts:273`). A later explicit refresh is needed to retry a cached failure when manifest signature is unchanged.
- **Fact / inference:** Explicit in-process refresh repairs the normal edit path, but the cache key does not include overrides, and the shown watcher watches the manifest rather than SQLite. The editor database itself is an in-memory load; merely refreshing AgentGraphService does not reload SQLite from disk (`src/services/database.ts:37`; `src/services/agentGraph/agentGraphService.ts:243`; `src/extension.ts:265`). External writers therefore are not synchronized with editor state, and multiple editor writers risk whole-file overwrite/lost updates. MCP queries re-read SQL but retain a connection opened at startup; visibility under sql.js whole-file rewrites/concurrent processes is not demonstrated. Do not equate per-call querying with proven cross-process invalidation.
- **Fact:** MCP overview's `lastUpdatedAt` uses the Agent generation timestamp, not override timestamps (`packages/mcp-server/src/mergedGraph.ts:74`). **Inference:** an external client using that field as a prose freshness token can miss description-only changes.

**Test evidence, not test results.** Cross-group regeneration/reset is asserted in `src/services/agentGraph/agentGraphService.test.ts:393`; key fallback/save behavior in `src/services/agentGraph/agentEntityOverrideService.test.ts:28`; read-only CLI visibility, byte preservation, and corrupt-database failure in `tests/querySkill.test.ts:86`. These do not establish native UI refresh timing, real restart durability, or multi-process concurrency. Legacy entity/observation mutation and RAG indexing are not claimed to follow this override path.

## 2. MCP setup

### UI and target selection

**Fact.** `knowledge.setupMcp` is a contributed command and Explorer-title action (`package.json:71`, `:214`); `knowledge.settings` offers install/reconfigure or native settings (`src/commands/mcpSetupCommands.ts:100`). Registration occurs before workspace/database initialization, so database failure or no open project does not prevent registration (`src/extension.ts:38`, `:48`).

**Fact.** Installation checks workspace trust first. It uses machine-scoped `knowledgeGraph.mcp.workspacePath` if set; otherwise it presents local open folders plus a folder chooser. It rejects a nonabsolute target; the service then resolves the real path and verifies it is a directory. Auto client detection checks whether the current app name contains Cursor. A modal shows the project and destination `.cursor/mcp.json` or `.vscode/mcp.json`; acceptance saves the selected path globally **before** installation. Concurrent invocations in this registration closure show the existing output channel while selection/install is active. (`src/commands/mcpSetupCommands.ts:15`, `:23`, `:39`, `:44`, `:52`; `src/services/mcpSetupService.ts:154`; `package.json:288`.)

**Inference.** The selected target need not be the first/open extension workspace; setup's trust check is the current VS Code workspace flag, not a separate trust check for an arbitrary external folder. The modal supplies target-specific confirmation. On retries, the persisted workspace setting can bypass folder selection, so inspect the modal's paths or clear/change that setting.

### Child-process and dependency chain

1. **Validate first.** The service validates integer audit timeout (10–120 seconds, default 60), resolves the target, reads existing client JSONC, and validates it before downloading. Invalid JSON, array/null roots, or nonobject server maps fail without replacement. (`src/services/mcpSetupService.ts:122`, `:142`, `:150`.)
2. **Resolve external Node/npm.** A child of configured `nodePath` prints version, executable path, ABI, platform and architecture. The supported version regex accepts stable Node 26 with minor >=1, rejecting 26.0, 27 and prereleases. The resolved executable is subsequently used for both install and published runtime; npm-cli.js is an explicitly configured absolute file or discovered beside the real Node installation. npm major <11 is rejected, and the selected Node directory is prepended to inherited PATH. (`src/services/mcpSetupService.ts:91`, `:98`, `:104`, `:162`.) The npm check is a numeric-major comparison, not full semantic-version validation (`:169`).
3. **Stage outside the business project.** UI supplies `<extension>/dist/mcp-server` and `<globalStorage>/mcp`. A lock/Node/platform/architecture-derived prefix plus `mkdtemp` creates a unique attempt directory; bundle contents are copied there. Node invokes npm-cli.js with `ci --omit=dev --audit --ignore-scripts`; Windows supplies a known script-shell argument, but the parent spawn still uses `shell:false`. (`src/commands/mcpSetupCommands.ts:64`; `src/services/mcpSetupService.ts:171`.) The bundle `.npmrc` also enables audit and disables install scripts (`packages/mcp-server/.npmrc:1`).
4. **Gate on a separate production audit.** Node runs the copied audit helper with the same npm CLI and an explicit timeout environment. The helper runs `npm audit --json --audit --omit=dev --audit-level=high --fetch-retries=0`. A nontruncated report with complete nonnegative integer severity counts, exit 0, no timeout/error and zero high/critical findings is required; low/moderate findings do not block this threshold. (`src/services/mcpSetupService.ts:187`; `scripts/audit-dependencies.cjs:56`, `:63`.)
5. **Initialize missing DB, then health gate.** Only after audit does the UI callback initialize/close `DatabaseService` if the target's `graph.sqlite` is absent. Existing databases are not recreated by that callback. Then the service runs staged `health-check.mjs <real-workspace>` with a 45-second deadline and only proceeds on success. (`src/commands/mcpSetupCommands.ts:73`; `src/services/mcpSetupService.ts:196`.)

**Fact.** Build wiring emits portable Node-26 ESM, copies package metadata/lock/`.npmrc`, shared graph modules and audit/health helpers; MCP external dependencies include the SDK and `better-sqlite3`, unlike the editor's sql.js. (`esbuild.js:11`; `scripts/build-mcp-runtime.cjs:17`; `packages/mcp-server/package.json:44`; `src/services/database.ts:4`.) **Evidence gap:** `packages/mcp-server/scripts/health-check.mjs` was absent when read through the observer. The copy is mandatory (`scripts/build-mcp-runtime.cjs:35`), so a fresh build from this exact incomplete source is expected to fail there. Its actual native-SQLite/protocol/tool assertions and bundle completeness cannot be certified; the setup log's claimed health checks are not substitute evidence.

### Configuration publication, cancellation, and safe retries

**Fact.** JSONC modification replaces only `servers.vibeknowledge` for VS Code or `mcpServers.vibeknowledge` for Cursor; it preserves surrounding fields/comments and accepts trailing commas. The replacement entry uses the resolved Node plus `[<unique-install>/dist/index.js, '--workspace', <real-target>, '--rag-mode', 'none']`; VS Code additionally gets `type:'stdio'`. Any previous custom fields **inside** the VibeKnowledge entry are replaced, not merged. (`src/services/mcpSetupService.ts:122`.)

**Fact.** After health success and an abort check, setup compares current config text with the initial text and refuses detected intervening edits. It backs up nonempty original text using exclusive creation, writes a unique temporary file, then renames it over the destination. Only after this block is `published` set. Failed attempts remove only their unique staging directory; successful and older installations remain for existing processes. (`src/services/mcpSetupService.ts:200`.) The user must still trust/start or restart the server in the client; setup does not generate graphs and publishes RAG-disabled arguments (`src/commands/mcpSetupCommands.ts:83`; `src/services/mcpSetupService.ts:135`).

**Fact.** Processes use argument arrays, no shell interpolation, hidden Windows windows and piped output. Spawn/nonzero-exit errors reject; default step timeout is five minutes. Abort/timeouts attempt child-tree termination using taskkill on Windows or process-group signals elsewhere, followed by a hard stop. Captured stdout/tail are bounded and common credentials are redacted in logs. UI progress cancellation and extension disposal abort the controller; errors are logged and offer MCP settings, and state flags clear in `finally`. (`src/services/mcpSetupService.ts:31`; `src/commands/mcpSetupCommands.ts:13`, `:57`, `:88`.)

**Fact.** Automatic retries belong to the audit helper, not the entire installer: up to three attempts with 2/4-second backoff. Timeouts, DNS/network/registry failures and missing/invalid reports are retryable; TLS, authorization, local-input and process-start failures are not. Vulnerability findings fail immediately. Per-attempt npm process limit is request timeout +15 seconds; the enclosing helper deadline is `3 × (request timeout +15s) +45s` (270 seconds by default, 450 at maximum). Connectivity diagnostics do not convert failure into success or disable audit/TLS. (`scripts/audit-dependencies.cjs:3`, `:6`, `:74`, `:90`, `:121`; `src/services/mcpSetupService.ts:190`.)

**Retry guidance inferred from these guards:** rerun after correcting Node/npm paths, invalid JSONC, permissions, or approved registry/proxy/CA access; fix vulnerable locked dependencies rather than bypassing the gate. If the config changed during installation, rerun to validate/merge the new version. Increasing the supported audit timeout is appropriate only for genuinely slow requests. Each retry gets a new isolated stage and leaves old working installs intact.

**Limits of “previous configuration preserved”:** ordinary install/audit/health failures occur before publication, but the operation is not a transaction across all side effects. The selected global workspace setting, a newly initialized database, a backup, or storage directories may already exist after failure (`src/commands/mcpSetupCommands.ts:52`, `:73`; `src/services/mcpSetupService.ts:161`, `:205`). **Inference:** text comparison followed by rename is not an atomic compare-and-swap; another process can edit during that gap. Cancellation after the last abort check is not rechecked during publication. A temporary-file cleanup exception after a successful rename occurs before `published = true`, so final cleanup could remove the now-referenced runtime. Likewise, a failure opening the success dialog's configuration document is caught by the UI's generic “preserved” error despite completed publication (`src/services/mcpSetupService.ts:200`–`:218`; `src/commands/mcpSetupCommands.ts:87`–`:94`). After a late error, inspect the actual config and referenced install before assuming rollback or deleting anything.

**Test evidence, not test results.** Tests assert JSONC preservation and Node bounds (`tests/mcpSetup.test.ts:9`, `:34`), process ordering/isolation/backup and timeout forwarding (`:82`, `:124`), stage cleanup, concurrent-edit refusal and cancellation (`:110`, `:140`, `:150`), and real argument/cancellation handling (`:167`). UI tests cover early registration, trust and timeout forwarding (`tests/mcpSetupCommands.test.ts:53`); audit tests cover fail-closed classification/retry policy (`tests/dependencyAudit.test.ts:16`, `:23`, `:35`, `:75`). Most installer stages use a mocked runner and a placeholder health script (`tests/mcpSetup.test.ts:63`, `:73`), so they do not prove a real install/handshake. Bundle tests expect the missing helper (`tests/mcpRuntimeBundle.test.ts:14`).
