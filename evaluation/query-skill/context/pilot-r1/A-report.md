## 1. Local: DebouncedStructuralGraphUpdater

**Facts.** The constructor defaults to **500 ms** (`src/services/structuralGraph/debouncedStructuralGraphUpdater.ts:12`). Every accepted `notify()` adds the path to a Set and restarts the timer, so this is a trailing debounce after the latest notification, not a fixed polling interval (`src/services/structuralGraph/debouncedStructuralGraphUpdater.ts:17`). `flush()` clears the timer, snapshots unique paths in English-locale sort order, clears the Set, and chains a callback onto `running`; it catches the *previous* promise's rejection so later batches can proceed (`src/services/structuralGraph/debouncedStructuralGraphUpdater.ts:31`). The extension separately supplies an explicit `500`, so changing only the constructor default would not change the extension's background delay (`src/extension.ts:184`, `src/extension.ts:203`).

**Disposal boundary.** `dispose()` marks the updater disposed, discards paths still in the Set, and cancels its outstanding timer. Later `notify()` is ignored; later `flush()` returns `running` without scheduling another batch. It does **not** replace/cancel/await `running`, and the already-appended `.then(() => this.callback(paths))` has no disposal check. Thus callbacks already queued in the promise chain—including a callback not yet started—still run, and a running callback continues. These are code-derived consequences, not claims of cancellation support (`src/services/structuralGraph/debouncedStructuralGraphUpdater.ts:18`, `src/services/structuralGraph/debouncedStructuralGraphUpdater.ts:32`, `src/services/structuralGraph/debouncedStructuralGraphUpdater.ts:43`, `src/services/structuralGraph/debouncedStructuralGraphUpdater.ts:49`).

**Tests and gaps.** `src/services/structuralGraph/debouncedStructuralGraphUpdater.test.ts:9` tests duplicate coalescing, sorting, and timer reset with an explicit 100 ms delay. `src/services/structuralGraph/debouncedStructuralGraphUpdater.test.ts:29` tests serialization of two flushed batches while the first callback is active. Both dispose only after completion; neither establishes the default 500 ms nor disposal while a timer/callback/queued batch is outstanding. Before changing lifecycle semantics, add those cases and rejection-then-next-batch recovery; do not interpret existing end-of-test `dispose()` calls as cancellation coverage.

## 2. Refresh: event → scheduler → generation → consumers

### Registration and execution

1. **Facts:** activation selects the first workspace and initializes services before constructing the updater (`src/extension.ts:48`, `src/extension.ts:57`, `src/extension.ts:174`). Two first-folder filesystem watchers cover `ts/tsx/js/jsx/html/htm` and `**/{tsconfig,jsconfig}*.json`. Create/change/delete events all go through one callback; it makes a normalized workspace-relative path and ignores `../` and the listed generated/VCS directories. Both watchers, their event registrations, and the updater join extension subscriptions (`src/extension.ts:205`, `src/extension.ts:217`, `src/extension.ts:231`).
2. **Facts:** after debounce/serialization, the callback first checks `hasGraph()` and returns if the output does not exist. It calls `generate()` with **no changed-path or force options**; changed paths only provide a log count. Generation errors are caught and logged, with no automatic retry or force rebuild in that callback (`src/extension.ts:184`). Therefore source events maintain an existing graph; they do not bootstrap it. `hasGraph()` checks existence, not validity (`src/services/structuralGraph/structuralGraphService.ts:59`).
3. **Facts:** the service supplies workspace-rooted output `.vscode/.knowledge/structural-graph.json` and cache `.vscode/.knowledge/cache/structural`; it exposes `.vscode/.knowledge/structural-graph.previous.json`. `generate()` synchronously invokes `updateStructuralGraph()` and assigns statistics only after success (`src/services/structuralGraph/structuralGraphService.ts:25`, `src/services/structuralGraph/structuralGraphService.ts:82`). The extractor reads the previous output, computes an incremental result, checks safe replacement, then persists it (`resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:103`).
4. **Facts:** “incremental” is content/cache based, not a restricted list of watcher paths. Extraction scans sources, loads compiler configuration, discovers HTML entrypoints, computes configuration/runtime-input identity, and creates a TypeScript program (`resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:134`). Each source's content hash/cache key determines reusable facts (`resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:293`). Changed/deleted/summary-invalidated files seed a transitive reverse-importer closure using old and current dependencies (`resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:1990`). Cached resolved contributions are restored and the affected set is re-resolved (`resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:197`). Missing cache rebuilds; incompatible version/scope/configuration identity also rebuilds, whereas corrupt cache raises recovery-required errors (`resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:1586`).

**Inferences relevant to a scheduling change:** the async wrapper does not make the synchronous scanner/TypeScript work nonblocking; it runs on the extension host's thread. Serializing this updater does not provide a cross-process lock for another CLI writer. Continuous events can postpone a trailing debounce indefinitely. Only on-disk filesystem events are registered here, not unsaved editor-buffer changes; the first-root watchers do not maintain every root of a multi-root workspace. No activation-time refresh is called by this registration block, so an existing stale graph can remain stale until a watched event or explicit generation. A prior CLI scope/config choice is not retained by the callback's default `generate()` call; default scope is `.` (`src/extension.ts:184`, `src/extension.ts:205`, `src/services/structuralGraph/debouncedStructuralGraphUpdater.ts:21`, `src/services/structuralGraph/structuralGraphService.ts:82`, `resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:139`).

### Failure and staleness boundaries

- **Pre-write protection, fact:** invalid existing graph/cache, previously valid changed source that no longer parses, and abnormal shrink can block replacement. Force bypasses recovery protections and is deliberately absent from background refresh (`resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:1586`, `resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:2055`, `resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:2226`, `resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:2255`). The manual generation command catches recovery-required errors, asks for modal confirmation, then retries with force; cancellation leaves the existing graph (`src/extension.ts:339`). A background refusal leaves a potentially stale snapshot and only a console warning; paths have already been removed from the updater's pending Set.
- **Not every diagnostic aborts, fact:** source read failures add diagnostics and skip the file; malformed compiler config can produce diagnostics/default options. Safety thresholds may catch a large resulting loss, but the implementation does not reject every error diagnostic (`resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:300`, `resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:1264`, `resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:2281`).
- **Persistence limit, fact and inference:** persistence writes individual cache entries, preserves the old graph when structural facts differ, replaces the graph, and **then** replaces the cache index. Each text write uses a temporary file plus rename, but the whole set is not one transaction (`resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:2189`, `resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:2362`). Consequently an index-write failure can occur after the new graph was published; the callback's blanket “previous graph was preserved” warning is not guaranteed for every filesystem failure. Likewise service statistics remain from the last fully successful call. The previous snapshot is only rotated when version/scope/entities/relations differ, not merely because time or file hashes changed (`resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:2207`).
- **Read freshness, fact:** `StructuralGraphService.read()` parses and schema-validates the stored document; it does not compare its hashes to current sources (`src/services/structuralGraph/structuralGraphService.ts:63`, `src/services/structuralGraph/structuralGraphService.ts:101`). The MCP structural store similarly reads/schema-validates current and previous snapshots (`packages/mcp-server/src/structuralGraphStore.ts:83`). Thus a successful read is not itself evidence of current-source freshness. The separate structural CLI test explicitly demonstrates stale-hash detection by the validator (`src/services/structuralGraph/structuralGraphCli.test.ts:48`).

**Facts:** MCP setup is independently registered before workspace/database initialization (`src/extension.ts:38`).
