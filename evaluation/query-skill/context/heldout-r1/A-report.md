## 1. Entity descriptions

### Edit/reset → storage → effective graph

- **Fact — entry points and cancellation.** Tree context menus expose edit for entity/agentEntity and reset only for agentEntity (`package.json:200`). CodeLens invokes `knowledge.editEntityDescription` with the entity ID (`src/providers/codeLensProvider.ts:42`). Edit resolves a string, entity object, or tree item's entity against the current graph; if unresolved it offers the unified entity picker. It prefills effective prose, treats `undefined` as cancellation, but accepts an empty string. It checks the update result before announcing success (`src/ui/commands/entityCommands.ts:225`, `src/ui/commands/entityCommands.ts:279`). Reset has no picker: it requires a resolvable agent entity and calls reset directly (`src/ui/commands/entityCommands.ts:268`).
- **Fact — the write target is an override, not generated structure.** `KnowledgeGraphService.updateDescription/resetGeneratedDescription` delegates to `AgentGraphService`, which resolves the occurrence ID and writes/deletes by its stable entity key, then forces a reload (`src/services/knowledgeGraphService.ts:261`; `src/services/agentGraph/agentGraphService.ts:144`). The store upserts `agent_entity_overrides(agent_key, description, updated_at)` and calls `save()`; reset deletes the matching row (`src/services/agentGraph/agentEntityOverrideService.ts:47`). This table has no group key or entity foreign key (`src/services/database.ts:120`). SQL.js loads and exports the workspace's `.vscode/.knowledge/graph.sqlite`; saving rewrites that file synchronously (`src/services/database.ts:17`, `src/services/database.ts:165`). The description route never writes `agent-graph.json` or legacy `entities.description`.
- **Fact — one symbol, multiple occurrences.** Generated occurrence IDs include both group and entity key; override lookup uses only the entity key. Every occurrence receives the override, while metadata retains `generatedDescription` and marks `descriptionSource`. Presence is tested with `!== undefined`, so blank prose deliberately overrides generated prose (`src/services/agentGraph/agentGraphService.ts:537`). Reset exposes each group's latest generated description, not the description from the time of editing. The regeneration test explicitly expects two different generated descriptions after reset (`src/services/agentGraph/agentGraphService.test.ts:393`). The unified snapshot deduplicates normalized symbol identities; visual groups retain occurrences (`src/services/knowledgeGraphService.ts:67`, `src/services/knowledgeGraphService.ts:152`).
- **Fact — identity and workspace scope.** Exact key matches win; otherwise the store accepts only one normalized-identity match, declining ambiguous matches. Delete follows the same exact-or-unique lookup (`src/services/agentGraph/agentEntityOverrideService.ts:22`, `src/services/agentGraph/agentEntityOverrideService.ts:61`). Tests cover portable path spelling variants, distinguish symbol case, and decline ambiguous legacy aliases (`src/services/agentGraph/agentEntityOverrideService.test.ts:28`, `src/services/agentGraph/agentEntityOverrideService.test.ts:50`). Extension services and the graph watcher belong to the first workspace folder, with the override store injected into that folder's graph service (`src/extension.ts:57`, `src/extension.ts:174`, `src/extension.ts:265`). This is workspace-local prose, not a global or per-group preference.

### Important failure cases and limits

1. **Fact / inference — failure is not fully transactional.** An unavailable entity/store returns null; edit reports failure, but reset ignores its nullable return and announces success (`src/ui/commands/entityCommands.ts:252`, `src/ui/commands/entityCommands.ts:273`; `src/services/agentGraph/agentGraphService.ts:148`). SQL mutation happens before disk save; save errors propagate, so refresh and UI refresh are skipped on that exception (`src/services/agentGraph/agentEntityOverrideService.ts:56`; `src/services/database.ts:175`; `src/extension.ts:553`). **Inference:** failed persistence can leave memory changed while disk/cached consumers retain older prose; there is no rollback in this write path.
2. **Fact / inference — identity migration has boundaries.** Upsert does not normalize or remove old alias rows, and reset deletes only one row (`src/services/agentGraph/agentEntityOverrideService.ts:47`). **Inference:** editing after a key-spelling change can create two alias rows; resetting the new exact row may reveal the older unique override instead of generated prose. A genuine rename/key change can orphan an override, while later key reuse can reapply it. Ambiguous fallback is intentionally refused, not arbitrarily resolved.
3. **Fact / inference — missing or bad graph is not preserved as last-good data.** A missing manifest yields an empty graph with no error; parse/validation/override-load errors replace the cached snapshot with empty data and record the failure (`src/services/agentGraph/agentGraphService.ts:232`). **Inference:** an entity removed while the edit input is open can fail the later ID lookup. The same invalid file signature can keep the failure cached until explicit refresh or file change.
4. **Fact / inference — external updates are a separate coherence problem.** The extension loads SQLite into memory once and watches the manifest, not SQLite (`src/services/database.ts:37`; `src/extension.ts:265`). **Inference:** externally changing SQLite is not equivalent to using the edit command; clearing the graph cache does not reread SQLite. MCP has a long-lived native read-only connection, opened at startup, despite querying overrides afresh (`packages/mcp-server/src/index.ts:13`; `packages/mcp-server/src/database.ts:119`, `packages/mcp-server/src/database.ts:380`). Cross-process visibility/locking during SQL.js whole-file rewrites is not established by these source tests; do not claim an integration guarantee. Also, effective entity timestamps remain generation timestamps and merged overview reports generation time, so timestamp-only consumers cannot reliably detect prose edits (`src/services/agentGraph/agentGraphService.ts:562`; `packages/mcp-server/src/mergedGraph.ts:78`).
5. **Inference — multi-root mismatch.** CodeLens computes paths relative to whichever folder contains the document, but queries the single first-folder graph (`src/providers/codeLensProvider.ts:58`; `src/extension.ts:57`). Identical relative paths in another root can therefore select the wrong graph's entity/prose.

## 2. MCP setup

### UI, selection, and process chain

1. **Fact — setup is independent of graph activation.** `registerMcpSetupCommands` runs before the no-workspace return and database initialization (`src/extension.ts:36`). Both `knowledge.setupMcp` and the install choice under `knowledge.settings` call the same handler. It refuses untrusted workspaces and suppresses concurrent selection/installation within this registration (`src/commands/mcpSetupCommands.ts:8`, `src/commands/mcpSetupCommands.ts:100`).
2. **Fact — choose the target project, not necessarily the open/first folder.** A trimmed machine-scoped `workspacePath` wins. Otherwise a picker lists local file-scheme workspace folders plus an external folder dialog; cancelled/non-file selections return. UI requires an absolute path; the service resolves its real path and checks that it is a directory. Client selection is explicit Cursor or automatic app-name detection, otherwise VS Code. A modal shows the project/config destination and intended effects; acceptance saves `workspacePath` globally before installation (`src/commands/mcpSetupCommands.ts:23`; `src/services/mcpSetupService.ts:154`; `package.json:288`).
3. **Fact — the same external Node installs and later runs MCP.** The handler passes bundled `dist/mcp-server`, global storage's `mcp` directory, selected workspace, Node/npm settings, cancellation, and logging (`src/commands/mcpSetupCommands.ts:64`). Service validates existing JSONC before downloads, probes the selected Node for version/resolved executable/platform/architecture/ABI, requires stable Node 26.1+ below 27, finds absolute `npm-cli.js` beside real Node or at the configured path, and requires npm major 11+ (`src/services/mcpSetupService.ts:98`, `src/services/mcpSetupService.ts:148`). It uses returned `execPath` thereafter and prepends its directory to a copied PATH, preserving inherited proxy/CA environment (`src/services/mcpSetupService.ts:91`, `src/services/mcpSetupService.ts:163`). It does not invoke Electron, `npm.cmd`, or `npm.ps1`.
4. **Fact — isolated installation with two explicit gates.** Lockfile plus Node/version/platform/architecture determines a prefix, but every attempt uses a fresh `mkdtemp` directory; the bundle is copied there. Node runs `npm-cli.js ci --omit=dev --audit --ignore-scripts`, then the audit helper, then database initialization if missing, then `health-check.mjs <workspace>` with a 45-second limit (`src/services/mcpSetupService.ts:171`). The bundle builder emits portable JS and copies lockfile, npm settings, audit, and health helpers rather than shipping native dependencies (`scripts/build-mcp-runtime.cjs:5`). The manifest depends on better-sqlite3 13 and `.npmrc` keeps audit enabled/install scripts disabled (`packages/mcp-server/package.json:44`; `packages/mcp-server/.npmrc:1`).
5. **Fact — child handling.** `spawn` uses an argument array, `shell:false`, hidden Windows windows, piped output, and a default five-minute step deadline. Cancellation/timeout kills the child tree with `taskkill` on Windows or process-group signals elsewhere, with a three-second hard-stop fallback. Spawn errors/nonzero exits reject; logs are redacted and the retained error tail is bounded (`src/services/mcpSetupService.ts:31`). Progress cancellation and extension disposal abort the active controller; the handler releases its guard in `finally` (`src/commands/mcpSetupCommands.ts:13`, `src/commands/mcpSetupCommands.ts:57`, `src/commands/mcpSetupCommands.ts:97`).

**Verification boundary:** the health-check invocation and success gate are concrete code facts, but the referenced source `packages/mcp-server/scripts/health-check.mjs` was absent (observer returned ENOENT). The builder expects it at `scripts/build-mcp-runtime.cjs:35`; the setup tests substitute a fake helper/runner (`tests/mcpSetup.test.ts:63`, `tests/mcpSetup.test.ts:73`). Therefore the exact handshake/tool probes cannot be established here. The separate native-runtime test intends to load the packaged SQLite binary in a fresh process (`packages/mcp-server/tests/nativeRuntime.test.ts:19`); it was inspected, not run.

### Audit, config publication, and safe retries

- **Fact — audit fails closed, with selective bounded retries.** Each request defaults to 60 seconds, configurable from 10–120, and gets a larger process deadline. The helper performs production `npm audit --json --audit --audit-level=high`, explicitly disabling npm's own fetch retries. A valid complete report and successful exit are required; high/critical findings fail immediately, while moderate findings alone are allowed. DNS/network/timeouts/429/5xx/invalid reports may retry up to three attempts with 2s/4s delays; TLS/auth/local-input/spawn failures do not. Connectivity diagnostics cannot turn failure into success and do not disable auditing/TLS (`scripts/audit-dependencies.cjs:6`, `scripts/audit-dependencies.cjs:56`, `scripts/audit-dependencies.cjs:74`, `scripts/audit-dependencies.cjs:113`). The enclosing process budget accounts for all attempts/backoff/diagnostics: 270 seconds by default, 450 at the maximum setting (`src/services/mcpSetupService.ts:187`; `tests/mcpSetup.test.ts:124`).
- **Fact — write only after gates, preserve unrelated config.** Immediately before publication, the service rereads config and rejects if it differs from its original text. JSONC editing replaces only `servers.vibeknowledge` for VS Code or `mcpServers.vibeknowledge` for Cursor, retaining unrelated content/comments. It writes resolved Node plus `[installed dist/index.js, --workspace, real workspace, --rag-mode, none]`; only VS Code gets `type:stdio` (`src/services/mcpSetupService.ts:122`, `src/services/mcpSetupService.ts:201`). Existing nonempty config receives a timestamped exclusive `.bak`; an exclusive temporary file is renamed over config. Failed attempts remove only their unique staging installation; successful and older installations remain (`src/services/mcpSetupService.ts:204`).
- **Fact — setup does not itself activate the persistent client server.** Success asks the user to trust and start/restart the client entry (`src/commands/mcpSetupCommands.ts:82`). On later launch, explicit `--workspace` overrides environment/current-directory selection, and `--rag-mode none` overrides environment/settings. The entry opens the project's database, registers graph resources/tools, and connects stdio (`packages/mcp-server/src/config.ts:84`; `packages/mcp-server/src/index.ts:6`; `packages/mcp-server/src/server.ts:25`). Setup may initialize a missing SQLite database, but does not generate the graph (`src/commands/mcpSetupCommands.ts:73`).
- **Fact / inference — what a safe retry preserves.** Service tests assert preservation of existing config/old installations on install, audit, and health failure; they also cover concurrent edits, cancellation, malformed config, JSONC preservation, and shell-metacharacter arguments (`tests/mcpSetup.test.ts:8`, `tests/mcpSetup.test.ts:110`, `tests/mcpSetup.test.ts:140`, `tests/mcpSetup.test.ts:167`). **Inference:** after correcting runtime/npm paths, project/config input, registry/proxy/CA access, or dependency/platform problems, rerunning the UI is designed to make a fresh attempt without destroying a working installation. High/critical vulnerabilities require changed dependencies, not an audit bypass. To select another project, change/clear the persisted machine-level workspace path; otherwise later runs reuse it.
- **Inference — limits of the preservation promise.** This is not an all-or-nothing transaction: the global workspace preference is saved before setup, and a newly initialized database can remain after health failure (`src/commands/mcpSetupCommands.ts:52`, `src/commands/mcpSetupCommands.ts:73`). The concurrency guard is per extension instance; the final compare and rename are not an atomic compare-and-swap, leaving a small external-edit race. Cancellation is checked before that publication sequence, not between each file operation. Successful old installs/backups accumulate intentionally (`src/services/mcpSetupService.ts:200`). Finally, a failure after rename but before `published=true` (for example temporary-file cleanup failure) can enter failed-staging cleanup despite published config; the UI's blanket “previous configuration was preserved” message is therefore stronger than the code can universally guarantee (`src/services/mcpSetupService.ts:207`; `src/commands/mcpSetupCommands.ts:88`).
