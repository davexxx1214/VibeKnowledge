## Scoring rules

- Score each task independently. `C` items are critical required facts; `S` items are supplemental and cannot compensate for a missing critical fact. Report critical coverage and supplemental coverage separately.
- For each item: `1` = correct causal explanation with traceable source/test evidence; `0.5` = substantially correct but missing a material part of the relationship or its evidence; `0` = absent, materially wrong, or contradicted elsewhere in the answer. Equivalent wording and other valid source anchors count. Do not require the exact prose or every anchor listed here.
- A file list is not an explanation. Credit must connect the named implementation to the requested behavior or proposed change's impact. Do not reward length, generic warnings, speculative redesigns, or unrelated test inventories.
- Record every applicable major false-claim trap separately. A major false claim prevents a “fully correct/safe assessment” verdict even if unrelated facts are correct; do not hide it in an aggregate score. Mere omission is not a false claim. A clearly labeled proposal is not a claim about current behavior.
- Relevant tests mean tests tied to a particular behavior. A read-only assessment need not execute tests. Do not reward claims that tests passed unless execution evidence exists, and do not treat a proposed test as an existing test.

## Task 1 — Default delay and disposal of pending, queued, and running work

Critical coverage: 7 items. Supplemental coverage: 1 item.

1. **C1 — Default delay.** The constructor defaults to **500 ms**, not the 100 ms or 10,000 ms values supplied by tests. The extension also explicitly passes 500 ms; changing only the constructor default would not change that call site's delay. Evidence: `src/services/structuralGraph/debouncedStructuralGraphUpdater.ts:12`, `src/extension.ts:184`, `src/extension.ts:203`. Full credit requires the default; the explicit call-site observation can supply useful impact context without becoming a separate requirement.
2. **C2 — Meaning of queued work.** `flush()` snapshots and clears the current path set, then appends the callback to `this.running` with `.catch(...).then(...)`; callbacks are serialized, not run concurrently. This distinguishes work already chained by `flush()` from paths still waiting for their timer. Evidence: `src/services/structuralGraph/debouncedStructuralGraphUpdater.ts:31`, `src/services/structuralGraph/debouncedStructuralGraphUpdater.ts:39`.
3. **C3 — Unflushed pending work is discarded.** `dispose()` sets the disposed flag, clears the path set, and clears/unsets the timer. A merely scheduled debounce timer does not later flush those pending paths. Evidence: `src/services/structuralGraph/debouncedStructuralGraphUpdater.ts:49`.
4. **C4 — Already-chained callbacks survive disposal.** A callback appended by `flush()` still executes when its predecessor settles, even if disposal happens before that callback starts. The `.then()` callback has no disposed check, and `dispose()` does not replace or cancel the promise chain. Evidence: `src/services/structuralGraph/debouncedStructuralGraphUpdater.ts:43`, `src/services/structuralGraph/debouncedStructuralGraphUpdater.ts:49`.
5. **C5 — Running callbacks are not aborted or awaited by disposal.** There is no abort mechanism; `dispose(): void` returns without waiting for active callback completion. Evidence: callback type at `src/services/structuralGraph/debouncedStructuralGraphUpdater.ts:1`, promise chaining at `src/services/structuralGraph/debouncedStructuralGraphUpdater.ts:43`, disposal at `src/services/structuralGraph/debouncedStructuralGraphUpdater.ts:49`.
6. **C6 — Calls after disposal.** `notify()` becomes a no-op. `flush()` returns the existing `running` promise without scheduling another callback, so a caller can still await already-chained work; disposal does not imply that promise is already settled. Evidence: `src/services/structuralGraph/debouncedStructuralGraphUpdater.ts:17`, `src/services/structuralGraph/debouncedStructuralGraphUpdater.ts:31`.
7. **C7 — Test coverage and its limit.** Identify the two existing tests and what they actually check: explicit-delay debounce reset/deduplication, and serialization of two flushed batches. Neither directly tests default timing nor disposal with pending/queued/running work; their final `dispose()` cleanup is not such a test. Appropriate additional regression cases may be proposed but must not be described as existing. Evidence: `src/services/structuralGraph/debouncedStructuralGraphUpdater.test.ts:9`, `src/services/structuralGraph/debouncedStructuralGraphUpdater.test.ts:29` (file ends at line 54).
8. **S1 — Batch details.** `notify()` resets a trailing-edge timer, paths are deduplicated by a `Set`, and `flush()` sorts the batch. The leading `.catch()` allows a later queued batch to proceed after a previous callback rejection; it is not cancellation or a guarantee that the current callback cannot reject. Evidence: `src/services/structuralGraph/debouncedStructuralGraphUpdater.ts:7`, `src/services/structuralGraph/debouncedStructuralGraphUpdater.ts:21`, `src/services/structuralGraph/debouncedStructuralGraphUpdater.ts:39`.

Major false-claim traps:

- “Dispose cancels all queued callbacks,” including callbacks already appended by `flush()` (contradicts C4).
- “Dispose aborts the active callback,” “dispose waits/drains everything,” or “flush after disposal starts the remaining paths” (contradicts C3–C6).
- “The default is 100 ms/10 seconds,” or a guaranteed 500 ms completion SLA regardless of earlier running callbacks (contradicts C1–C2).
- Claiming existing tests prove disposal cancellation or default-delay behavior (contradicts C7).

## Task 2 — Background structural refresh impact trace

Critical coverage: 8 items. Supplemental coverage: 2 items. The explanation must connect registration → scheduling → generation → persisted artifacts → consumers, not merely name those layers.

1. **C1 — Event entry and boundary.** Activation uses the first workspace folder. Two filesystem watchers cover source `ts/tsx/js/jsx/html/htm` files and `tsconfig/jsconfig*.json`; create/change/delete callbacks all route through `queueStructuralRefresh`. It normalizes separators and filters parent-relative paths and named generated/dependency/metadata directories before notifying the updater. Thus changes outside those registrations/filters do not trigger this route. Evidence: `src/extension.ts:49`, `src/extension.ts:57`, `src/extension.ts:205`, `src/extension.ts:217`, `src/extension.ts:231`. Do not require recital of every ignored directory if the boundary is accurately explained with examples.
2. **C2 — Scheduling boundary.** The extension supplies 500 ms; rapid events are deduplicated/debounced and flushed batches are serialized. Registered subscriptions dispose watchers/updater, but disposal only drops unflushed pending work, not already-chained/active callbacks. Evidence: `src/extension.ts:184`, `src/extension.ts:203`, `src/extension.ts:231`, `src/services/structuralGraph/debouncedStructuralGraphUpdater.ts:17`, `src/services/structuralGraph/debouncedStructuralGraphUpdater.ts:31`, `src/services/structuralGraph/debouncedStructuralGraphUpdater.ts:49`.
3. **C3 — Background callback policy.** `hasGraph()` is an existence check; absent structural output causes a return, so this route does not bootstrap the first graph. Otherwise it calls `generate()` with no changed-path or force argument; `changedPaths` is used for logging. Failures are caught and warned about, with no automatic force rebuild or retry loop in this callback. Evidence: `src/extension.ts:185`, `src/services/structuralGraph/structuralGraphService.ts:59`.
4. **C4 — Actual generation owner and output.** `StructuralGraphService.generate()` synchronously delegates to `updateStructuralGraph` in the bundled dependency-generation extractor, passing workspace/options plus `.vscode/.knowledge/structural-graph.json` and `.vscode/.knowledge/cache/structural`; it records returned statistics. The extractor scans/configures the project and manages incremental reuse itself. The watcher path batch is not a list of files handed to an incremental parser. Evidence: `src/services/structuralGraph/structuralGraphService.ts:3`, `src/services/structuralGraph/structuralGraphService.ts:25`, `src/services/structuralGraph/structuralGraphService.ts:82`, `resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:103`, `resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:143`.
5. **C5 — Preservation versus freshness.** Corrupt graph/cache, newly broken previously usable source, and abnormal shrink can raise recovery-required errors before graph replacement. Background handling retains old output for these protected failures, which means consumers may still see a stale snapshot; existence/readability is not proof of freshness. Explicit generation offers a user-confirmed forced rebuild instead of background auto-force. Evidence: `resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:119`, `resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:1586`, `resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:2055`, `resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:2226`, `resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:2255`, `src/extension.ts:357`. No exact shrink thresholds are required.
6. **C6 — Direct structural consumers.** Structural GraphView overview/drill-down operations read the current structural file on request; MCP structural analysis/impact/path tools use the read-only `StructuralGraphStore`, and diff also reads the previous snapshot. These consumers do not automatically regenerate live source. Explain the artifact handoff and stale/missing/invalid-read implications. Evidence: `src/extension.ts:243`, `src/ui/webview/graphView.ts:326`, `src/ui/webview/graphView.ts:345`, `src/ui/webview/graphView.ts:370`, `packages/mcp-server/src/structuralGraphStore.ts:83`, `packages/mcp-server/src/tools/registerStructuralAnalysisTools.ts:48`, `packages/mcp-server/src/tools/registerStructuralAnalysisTools.ts:70`, `packages/mcp-server/src/tools/registerStructuralAnalysisTools.ts:97`.
7. **C7 — Curated/UI freshness is a separate boundary.** Structural output is not `agent-graph.json`. Curation separately consumes a structural document and writes the agent graph. The agent-graph watcher refreshes tree/GraphView/CodeLens; the background structural callback neither calls curation nor that UI refresh path. A structural refresh therefore must not be presented as automatically refreshing every curated view or an already-rendered structural slice. Evidence: `src/services/structuralGraph/curatedGraphService.ts:34`, `src/services/structuralGraph/curatedGraphService.ts:47`, `src/extension.ts:185`, `src/extension.ts:266`, `src/extension.ts:494`, `src/extension.ts:522`.
8. **C8 — Relevant regression tests, mapped to risk.** At minimum map scheduling to the updater tests (`src/services/structuralGraph/debouncedStructuralGraphUpdater.test.ts:9`, `:29`); incremental correctness to leaf reuse/importer closure/deletion/rename tests (`src/services/structuralGraph/structuralGraphIncremental.test.ts:40`, `:103`, `:151`); and failure preservation/staleness to the recovery and source-hash tests (`src/services/structuralGraph/structuralGraphIncremental.test.ts:216`, `src/services/structuralGraph/structuralGraphCli.test.ts:48`). Consumer-oriented additions can cite snapshot diff/impact/path tests at `packages/mcp-server/tests/structuralAnalysisTools.test.ts:69` and `:85`. These are not an end-to-end VS Code watcher/disposal test; gaps should be labeled as proposed coverage.
9. **S1 — Incremental dependency boundary.** Cache reuse is based on compatible configuration/schema/extractor/scope and file contributions; affected-file planning includes transitive reverse dependencies and deleted files. Renames are covered as deletion plus new file. Narrowing a refresh to only the event path could miss importer consequences. Evidence: `resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:1611`, `resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:1990`, `resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:2016`, `src/services/structuralGraph/structuralGraphIncremental.test.ts:151`.
10. **S2 — Publication and diff boundary.** Validated output uses temporary-file rename; the previous snapshot is updated only for structurally different facts, not every timestamp-only regeneration. Writes are ordered per file (cache entries → previous snapshot → current graph → cache index), not one multi-file transaction. A late I/O failure can therefore occur after current graph publication despite the broad background warning text. Evidence: `resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:2189`, `resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:2207`, `resources/skills/vibeknowledge-dependency-graph/scripts/structural-extractor.mjs:2362`, `src/services/structuralGraph/structuralGraphIncremental.test.ts:178`. This nuance is supplemental; a categorical guarantee of rollback on every possible error is still false.

Major false-claim traps:

- Treating the source watcher as a save-only hook, claiming all workspace folders are watched by this code, or claiming it initially generates missing output (contradicts C1/C3).
- Claiming `changedPaths` directly controls a changed-file-only extraction, or the background path always forces a full rebuild (contradicts C3/C4).
- Claiming errors are automatically force-retried, all source parse errors are harmlessly ignored, or old output proves fresh source coverage (contradicts C5).
- Claiming structural updates automatically rewrite curated groups, refresh all UI consumers, update a structural SQL graph, or run through MCP installation (contradicts C4/C6/C7).
- Claiming every failure atomically rolls back all graph/cache files (contradicts S2), or that `.previous.json` necessarily means the immediately preceding timestamp (contradicts S2).
- Claiming disposal cancels already-chained/running callbacks or that the existing unit tests prove the whole watcher lifecycle (contradicts C2/C8).

## Task 3 — Query Skill installation-directory impact assessment

Critical coverage: 9 items. Supplemental coverage: 1 item. Assess the current installation contract; do not require a particular migration design or any production edits.

1. **C1 — User command reaches the installer.** `knowledge.installQuerySkill` is contributed in the manifest/menu and registered in the extension's shared Skill-install loop using `new AgentSkillService(context.extensionPath, QUERY_SKILL_NAME)`. The successful install's returned path is optionally opened in the editor. Evidence: `package.json:170`, `package.json:229`, `src/extension.ts:843`, `src/extension.ts:866`.
2. **C2 — Three different path roles.** Authoring assets are under `resources/skills/vibeknowledge-query`; the build emits the portable Skill under `dist/skills/vibeknowledge-query`; the query installer copies from that **built** extension directory to `<workspace>/.agents/skills/vibeknowledge-query` and returns its `SKILL.md`. The authoring directory and `dist` are not the project installation target. Evidence: `scripts/build-query-skill.cjs:5`, `scripts/build-query-skill.cjs:24`, `src/services/agentSkillService.ts:15`, `src/services/agentSkillService.ts:23`, `src/services/agentSkillService.ts:32`.
3. **C3 — Shared helper scope.** `getInstallDirectory()` is the target source of truth for detection, copy destination, and installed document path. It is shared by dependency-generation and query Skills, so an unconditional base-directory change affects both. A query-only change must account for that distinction; changing the destination does not inherently require changing the bundle source. Evidence: names/default at `src/services/agentSkillService.ts:4`, `src/services/agentSkillService.ts:11`; path consumers at `src/services/agentSkillService.ts:23`, `src/services/agentSkillService.ts:32`, `src/services/agentSkillService.ts:36`, `src/services/agentSkillService.ts:49`.
4. **C4 — Detection/overwrite consequences.** Installation detection tests directory existence, including a partial installation. Existing targets require explicit overwrite; the command prompts, and cancellation returns without installing. Moving the target changes which installations are detected; the current helper contains no old-location search or migration. Returned-path opening tracks the helper, not a separate hard-coded UI path. Evidence: `src/services/agentSkillService.ts:36`, `src/services/agentSkillService.ts:49`, `src/extension.ts:852`, `src/extension.ts:866`; partial-install regression at `src/services/agentSkillService.test.ts:97`. A migration recommendation is optional, but do not claim migration already exists.
5. **C5 — Complete bundle contract.** Installation first requires bundled `SKILL.md`; the query Skill additionally requires `scripts/query.cjs`, otherwise it reports a missing runtime/rebuild error. It recursively copies the bundle, not just the Markdown file, and does not build/download that runtime at install time. Evidence: `src/services/agentSkillService.ts:40`, `src/services/agentSkillService.ts:54`, `src/services/agentSkillService.ts:58`; regressions at `src/services/agentSkillService.test.ts:42`, `:55`, `:117`.
6. **C6 — Build and packaging chain.** `buildQuerySkill` copies authoring assets and bundles `packages/mcp-server/src/queryCliEntry.ts` into `scripts/query.cjs`; `esbuild.js` invokes it into `dist/skills/vibeknowledge-query` during extension asset building. Prepublish runs compile, and `.vscodeignore` excludes raw query assets, source packages, and build scripts—not the built query bundle. Thus a path change must preserve agreement between build output, packaged assets, and installer source/target roles. Evidence: `scripts/build-query-skill.cjs:5`, `esbuild.js:5`, `esbuild.js:11`, `esbuild.js:48`, `package.json:455`, `.vscodeignore:8`, `.vscodeignore:12`.
7. **C7 — MCP installation is a different workflow.** `knowledge.setupMcp` is registered by `registerMcpSetupCommands`, takes its bundle from `dist/mcp-server`, stages/version-installs under extension global storage's `mcp` directory, installs/audits dependencies and checks the connection before publishing the client's `.vscode/mcp.json` or `.cursor/mcp.json`. It is not the `.agents/skills` destination. It can ensure the database exists but does not regenerate the graphs. Evidence: `src/extension.ts:38`, `src/commands/mcpSetupCommands.ts:48`, `src/commands/mcpSetupCommands.ts:64`, `src/commands/mcpSetupCommands.ts:101`, `src/services/mcpSetupService.ts:119`, `src/services/mcpSetupService.ts:173`, `src/services/mcpSetupService.ts:185`, `src/services/mcpSetupService.ts:197`, `src/services/mcpSetupService.ts:203`. Do not require npm flag trivia to earn this distinction.
8. **C8 — Query installation is not graph generation.** The query Skill is independently installable from the generation Skill; installing copies executable/instruction assets, not graph data. Existing graph artifacts are queried read-only, with explicit failure on absent/corrupt artifacts rather than automatic generation. Structural generation is a separate command/service route. Evidence: `src/extension.ts:843`, `src/services/agentSkillService.test.ts:42`, `tests/querySkill.test.ts:48`, `tests/querySkill.test.ts:77`, `src/extension.ts:339`, `src/services/structuralGraph/structuralGraphService.ts:82`. Importing a CLI entry from the MCP source package does not make query installation an MCP server installation.
9. **C9 — Regression tests tied to the directory change.** Identify `AgentSkillService` tests for standalone query copy/missing runtime, full `.agents/skills` installation, overwrite and partial installation; connect them to target-path/copy/detection behavior (`src/services/agentSkillService.test.ts:42`, `:55`, `:64`, `:85`, `:97`). 10. **S1 — Portable runtime boundaries.** The query runtime is a bundled Node 26 CommonJS asset using root-resolved Zod; the build rejects MCP SDK/native SQLite/Google server dependencies and copies license files. Tests run a copied Skill without local `node_modules`, with spaces/Unicode, and assert no MCP package dependencies enter the bundle. Evidence: `scripts/build-query-skill.cjs:8`, `scripts/build-query-skill.cjs:15`, `tests/querySkill.test.ts:23`, `tests/querySkill.test.ts:32`, `tests/querySkill.test.ts:39`.

Major false-claim traps:

- “The query Skill installs from raw `resources/skills`,” “installs into `dist`,” or “uses a user-global Skill directory” (contradicts C2).
- “Changing `getInstallDirectory` only affects query,” “isInstalled verifies a complete runtime,” or “old installations are automatically migrated/cleaned up” (contradicts C3/C4).
- “Only `SKILL.md` needs copying,” “the installer builds or downloads missing `query.cjs`,” or “the raw query assets are the published runtime” (contradicts C5/C6).
