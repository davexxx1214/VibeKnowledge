# 独立 Agent A/B：查询 Skill 对比直接源码检索

日期：2026-09-04。

**本轮没有证明 Skill 节省 token。** 在同等验收要求下，Skill 一侧实际读入的工具文本增加 **19.8%**，模型累计总 token 增加 **67.0%**。这与先前固定检索脚本得到的 18.3% 节省方向相反；不能将检索代理评测当作完整 Agent 编码收益。

## 实验设计

- A：独立子 Agent `/root/ab_source_only`，只搜索、读取源码，没有安装图谱或 Skill。
- B：独立子 Agent `/root/ab_query_skill`，先读取并使用 `vibeknowledge-query`，再核验源码。
- 两侧均为 `gpt-5.6-sol`、`xhigh`，`fork_turns: none`，不继承父任务对话，不互通结果。
- 来自同一份 NestJS RealWorld 源码快照，每侧一个独立可写副本；只有 B 有已有图谱与查询 Skill。两侧使用同一套只读依赖和测试配置。
- 相同任务、相同顺序：①实现标签按 `tag ASC` 的数据库查询排序，保留接口结构，补充无 MySQL 的服务/控制器单测；②只读分析 ArticleEntity、Comment、UserEntity 的关系、所有权、加载/删除声明和受影响服务引用，并给出源码位置。
- 所有读取、搜索、查询、测试均经过相同观察包装器；没有预设五文件上限。代码编辑使用正常 patch，计入模型运行记录。
- 父 Agent 的环境准备、图谱生成、独立验收和报告汇总不计入任一侧。原工程源码哈希核验没有变化。

## 正确性与回归检查

| 检查 | A：源码检索 | B：查询 Skill |
| --- | --- | --- |
| 子 Agent 编写并执行的单测 | 2 套 / 6 项通过 | 2 套 / 6 项通过 |
| 事先准备、未提供给子 Agent 的独立验收 | 6/6 通过 | 6/6 通过 |
| 额外副本撤销排序修改，重跑各自单测 | 3 项服务测试按预期失败 | 3 项服务测试按预期失败 |
| ORM 关系及具体服务引用复核 | 满足任务要求 | 满足任务要求 |
| 非标签业务源码修改 | 无 | 无 |

两侧生产修改相同：服务向仓库传入 `{ order: { tag: 'ASC' } }`；新增服务单测，替换依赖数据库的控制器测试。A 直接构造服务，B 使用 Nest 测试容器和仓库 token，均验证精确的排序参数、返回值和异常传播。

关系分析均正确指出：author/articles 与 article/comments 是双向关系；favorites 是单向多对多且 User 拥有 JoinTable；Comment 没有直接 User 关系；Article.comments 的 JoinColumn 放置不能使其成为外键所有方；只有 comments 显式 eager，没有显式 cascade/onDelete。两侧均定位到具体的 authorId 查询字符串、comments/favorites 数组操作和 articles 关系加载，并没有声称验证了真实数据库行为。

## Token 结果

| 指标 | A：源码检索 | B：查询 Skill | B 相对 A |
| --- | ---: | ---: | ---: |
| 工具可见文本，逐次输出只计一次 | 7,315 | 8,766 | **+19.8%** |
| 模型累计输入，含缓存与上下文重放 | 257,226 | 432,259 | +68.0% |
| 其中缓存输入 | 232,192 | 408,192 | — |
| 未缓存输入 | 25,034 | 24,067 | -3.9% |
| 模型输出，包含推理 token | 6,188 | 7,632 | +23.3% |
| 模型累计总量：输入 + 输出 | 263,414 | 439,891 | **+67.0%** |
| 模型响应轮次 | 8 | 13 | +5 |
| 外层工具调用 | 7 | 12 | +5 |

累计输入/输出来自这两个独立会话的运行遥测，不是字符估算；各 response 的 usage 加总与会话总数一致。推理 token 已包含在 output 中，未重复相加。工具文本另用 `tiktoken 0.12.0 / o200k_base` 计算，包括 Skill 正文、图谱结果、源码和测试输出，但不包含上下文重放。

**这不是费用账单。** B 的缓存输入更多，因此不能将总 token 增加 67.0% 解释成费用也增加 67.0%，也不能只挑未缓存输入下降 3.9% 来宣称整体节省。

## 开销来自哪里

| 阶段的工具可见文本 | A | B | 观察 |
| --- | ---: | ---: | --- |
| 标签修改与测试 | 1,961 | 3,418 | Skill 说明、overview、局部图查询和额外回读增加开销 |
| ORM 关系分析 | 5,354 | 5,348 | 几乎持平，少读的源码被查询输出抵消 |

A 执行了 13 次观察操作，B 为 20 次（一次外层调用可包含多个操作）。B 共查询图谱 4 次。关系阶段 B 显式读出的源码从 435 行降为 362 行，但两个图查询抵消了文本收益。标签阶段，B 还额外回读了修改后的服务与测试；这属于本次 Agent 的具体执行轨迹，不是 Skill 强制要求，不能将全部差异归因于 Skill 文案。

两侧仍需查看相同核心实体和服务。额外查询没有替代足够多的源码调查，还增加模型往返，从而放大上下文重放。A/B 实际用时约 152/177 秒，仅作记录：同机并行运行与调度会影响该数值，不是可靠的性能基准。

## 能得出和不能得出的结论

- 能得出：在这个小型工程和这两项明确任务中，当前 Skill 流程没有减少整体 token；可用性和正确性并不自动等于节省。
- 不能得出：Skill 在所有工程都无效，或较大/陌生工程一定能省。仅一对 Agent，未重复、未随机化，也没有比较多个模型。
- 两侧均在公共观察工具约束下工作；这不是所有客户端默认行为的复现。
- 单测采用 Jest 25 / ts-jest 的 isolated transpilation，公共 shim 补齐老 Nest TypeORM 所用、Node 26 已删除的 util 方法。未连接数据库、运行 HTTP E2E 或完成整个项目类型检查。
- 旧样例依赖仅安装在临时目录，忽略原生包安装脚本；锁文件的旧镜像 URL 规范化到 npm 官方 registry，版本和 integrity 保留。未关闭 TLS 验证，未改原工程依赖。这些准备成本不计入 A/B。

## 下一步建议（本轮未修改 Skill）

1. 明确文件/符号且范围很小的任务，允许直接源码搜索，不强制图谱前置。
2. 合并分组发现与首次查询，减少单独 overview 和工具往返。
3. 返回更紧凑的源码行锚点和测试入口，让查询真正替代宽范围读取。
4. 用更多不同规模的工程、重复独立试验检验改动；保持相同验收标准。
