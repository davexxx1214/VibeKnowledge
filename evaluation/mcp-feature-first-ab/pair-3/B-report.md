## 1. Visualization

### Command, data, and selection

**Implementation.** `Knowledge: Visualize Graph` is contributed as `knowledge.visualizeGraph`, including the Knowledge Graph Explorer navigation action (`package.json:57–59`, `package.json:243–246`). Its registered handler calls `GraphView.createOrShow(context.extensionUri)` and reports synchronous opening errors (`src/extension.ts:642–652`). Activation supplies the knowledge and structural services (`src/extension.ts:242–243`). `GraphView` creates one script-enabled panel with `retainContextWhenHidden: true`; subsequent calls reveal that panel and resend graph data, except a translated-title change replaces its HTML. Disposal clears the singleton (`src/ui/webview/graphView.ts:157–202`). Browser `load` initializes D3 and sends `ready`; the host responds with performance preference and graph data (`src/ui/webview/graphView.ts:1205–1208`, `src/ui/webview/graphView.ts:205–222`).

Ordinary views come from `KnowledgeGraphService.getGroups()`, enriched with observations and source/structural identifiers, not from the deduplicated aggregate snapshot. This matters because the same symbol can occur independently in framework, module, and feature groups, with group-specific IDs (`src/ui/webview/graphView.ts:456–490`, `src/services/knowledgeGraphService.ts:147–173`). The service obtains curated groups from `agent-graph.json`, not raw structural JSON (`src/services/agentGraph/agentGraphService.ts:87–118`). The browser replaces its group array on `graphData`, sorts by order then name, renders sidebar buttons with kind and entity/relation counts, and selects the remembered key if present or the first group otherwise. Only that group is rendered; clicking a button persists its key using `vscode.setState` (`src/ui/webview/graphView.ts:1287–1289`, `src/ui/webview/graphView.ts:1372–1398`, `src/ui/webview/graphView.ts:1423–1462`).

The advanced structural action sends the selected boundary/community/file level as `requestStructuralOverview`; it does not switch the ordinary data service. The host reads `StructuralGraphService`, aggregates at most 80 nodes, converts the result, and sends `structuralGroup` (`src/ui/webview/graphView.ts:2091–2095`, `src/ui/webview/graphView.ts:223–241`, `src/ui/webview/graphView.ts:324–338`). The browser removes every previous `__structural_` group, inserts the new one, selects it, and displays a transient count/status message. Ordinary groups remain available, but only one temporary structural view remains in the list (`src/ui/webview/graphView.ts:1401–1420`).

Drilldown is a distinct message contract, not ordinary source navigation:

- Curated nodes open their source on double-click; Shift-double-click or right-click requests structural neighbors when a structural key exists. Aggregate nodes request a raw slice; structural nodes request their source location (`src/ui/webview/graphView.ts:1761–1797`). Neighbor slices use both directions, depth 1, deduplicate relations, cap at 120 relations/80 entities, then remove edges whose endpoints were excluded (`src/ui/webview/graphView.ts:365–404`). Aggregate slices use selected files or aggregate membership and include only internal relations, also capped at 80/120 (`src/ui/webview/graphView.ts:407–443`).
- Relationships with a nonempty `structuralPath` request raw supporting relations. The host matches relation identities in the current structural graph and derives endpoints from matched relations (`src/ui/webview/graphView.ts:1599–1611`, `src/ui/webview/graphView.ts:340–362`). Aggregate counts are not complete drilldown payloads: aggregation excludes within-group edges and retains at most eight raw samples per aggregate edge (`resources/skills/vibeknowledge-dependency-graph/scripts/structural-analysis.mjs:416–427`, `src/ui/webview/graphView.ts:549–559`). A stored path with no current matches can therefore produce an empty slice rather than a proof that the displayed relationship still exists.

### Performance and the lifetime of a view

**Implementation.** The performance setting is a machine-scoped `low`/`high` preference defaulting to `low` (`package.json:325–338`). A selector change immediately changes CSS and rerenders the currently selected group, disables the selector, and sends `setPerformanceMode`. The host accepts only those two values and saves globally, not to workspace files. Configuration changes push the current preference back into the page; the response reenables the selector. Failed persistence shows an error and still resends the actual preference, rolling back the optimistic UI (`src/ui/webview/graphView.ts:150–154`, `src/ui/webview/graphView.ts:300–321`, `src/ui/webview/graphView.ts:1283–1285`, `src/ui/webview/graphView.ts:2077–2084`, `src/ui/webview/graphView.ts:2176–2182`). Changing mode does not request a different graph dataset.

Both modes use D3 SVG, zoom, and a force simulation; D3 is loaded from extension-local `dist/d3.min.js` under the page's nonce CSP (`src/ui/webview/graphView.ts:718–754`, `src/ui/webview/graphView.ts:1566–1579`). Low mode stops D3's automatic simulation and manually ticks in animation-frame batches, with a roughly 6 ms batch target. It finishes after cooling, 120 ticks, or 600 ms accumulated compute time. Each batch explicitly updates geometry because manual D3 ticks do not emit tick/end events. This bounds accumulated work, not the duration of an individually expensive tick (`src/ui/webview/graphPerformanceScript.ts:46–89`). Low dragging directly updates the dragged node and connected geometry without restarting physics; high dragging reheats the simulation (`src/ui/webview/graphPerformanceScript.ts:91–118`, `src/ui/webview/graphView.ts:1950–1959`).

High mode adds agent-edge flow, node glow, animated fitting/hover, and one particle loop for the selected group, throttled to 30 fps. Low mode omits particle data and glow; switching to high does not necessarily restart already-settled physics because cached settling state is respected (`src/ui/webview/graphView.ts:1154`, `src/ui/webview/graphView.ts:1572–1573`, `src/ui/webview/graphView.ts:1591–1594`, `src/ui/webview/graphView.ts:1617–1656`, `src/ui/webview/graphView.ts:1721–1753`, `src/ui/webview/graphView.ts:2073–2074`).

| Transition | What survives, and why |
| --- | --- |
| Switch ordinary/structural group, or change performance mode | Before clearing the old rendering, the page stops work and saves geometry. A per-group cache restores node positions, pan/zoom, alpha, settled status, and auto-fit permission when topology matches. Selection is separately stored in Webview state (`src/ui/webview/graphView.ts:1453–1459`, `src/ui/webview/graphView.ts:1479–1493`, `src/ui/webview/graphView.ts:1556–1579`). |
| Hide then reveal the existing tab | Retained page state includes its group list, temporary structural view, selection, and in-memory cache. On hide, the page stops particles/simulation, pauses static layout, interrupts transitions, clears fit/resize timers, and saves geometry. On show, it resumes unfinished low layout or high physics above the cooling threshold and resumes particles (`src/ui/webview/graphView.ts:175–177`, `src/ui/webview/graphView.ts:1254–1269`). |
| Invoke Visualize Graph again while the panel exists | Usually preserves the document/cache, but the command resends ordinary groups. A valid curated selected key survives; a temporary structural group disappears and selection falls back to the first ordinary group. Clicking the page's Refresh likewise requests ordinary `graphData` (`src/ui/webview/graphView.ts:157–165`, `src/ui/webview/graphView.ts:219–222`, `src/ui/webview/graphView.ts:1372–1410`, `src/ui/webview/graphView.ts:2086–2089`). |
| HTML replacement / close and create a new panel | Only the selected key is read from Webview state; cache, structural groups, and layout are JavaScript memory. Replacing HTML recreates these, then incoming ordinary data validates the key. Closing disposes the panel; there is no selected-view restoration in the new-panel constructor, so persistence across a genuinely new panel is not implemented here. The global performance preference is read again and does survive (`src/ui/webview/graphView.ts:169–202`, `src/ui/webview/graphView.ts:300–302`, `src/ui/webview/graphView.ts:1140–1154`). |

Cache validity uses sorted node IDs and relationship endpoint/verb topology, not descriptions or evidence. Entries copy only positions/transform/settling state, so current source metadata is used even when geometry is reused. The LRU defaults to eight groups and 2,000 total nodes, rejects oversized/invalid geometry, and is cleared by completely empty group data (`src/ui/webview/graphPerformanceScript.ts:7–43`, `src/ui/webview/graphView.ts:1378–1393`). Thus remembered geometry is intentionally bounded and conditional, not permanent storage.

Auto-fit is also part of correctness: user zoom or drag disables pending auto-fit; low layout fits on completion, whereas high mode schedules a one-second fit. Low resize immediately fits, and high resize reheats visible physics. Hiding cancels fit/resize timers; the show handler does not recreate the high-mode fit timer (`src/ui/webview/graphView.ts:1210–1230`, `src/ui/webview/graphView.ts:1254–1269`, `src/ui/webview/graphView.ts:1360–1367`, `src/ui/webview/graphView.ts:1931–1959`). A view-memory change must deliberately decide whether to retain those existing fit behaviors, rather than assuming zoom always survives every resize/show transition.

### Failure boundaries and test implications

**Implementation and impact inference.** Preserve cancellation of the previous group's work before replacement, pending-layout alpha rather than incorrectly declaring every cached layout settled, and geometry-only cache entries. Otherwise quick switches can freeze half-laid-out graphs, old callbacks can affect a new group, or stale metadata can survive updates. Empty data has explicit cleanup and an empty-state display; render exceptions stop work and show a separate render-error panel. Hidden/unloaded pages must not keep layout/particle loops or fit timers running (`src/ui/webview/graphView.ts:1272–1278`, `src/ui/webview/graphView.ts:1378–1393`, `src/ui/webview/graphView.ts:1465–1493`).

The data failures are intentionally different: missing/unreadable/invalid curated sidecar data becomes an empty Agent snapshot and the normal payload has no generation-error field; structural reads validate and throw, producing both page status and a VS Code warning. Source navigation resolves group-specific IDs, uses the first workspace root, and does not open external entities as files (`src/services/agentGraph/agentGraphService.ts:232–260`, `src/ui/webview/graphView.ts:263–274`, `src/services/structuralGraph/structuralGraphService.ts:63–69`, `src/services/structuralGraph/structuralGraphService.ts:101–111`, `src/ui/webview/graphView.ts:450–453`, `src/ui/webview/graphView.ts:648–683`). Selection also feeds music: the page sends its selected key, but the host resolves only curated groups and falls back to the first, so a structural selection is not automatically a structural music input (`src/ui/webview/graphView.ts:279–297`, `src/ui/webview/graphView.ts:2115–2119`).

Existing tests map to these risks as follows; these are inspected assertions, not test runs or measured browser coverage:

- `src/ui/webview/graphView.test.ts:57–109` checks the manifest default/scope, localized choices, inline-JavaScript syntax, global saves, existing-document reuse, new-panel performance preference, Settings synchronization, failed-save rollback, and invalid mode rejection. It mocks VS Code and does not execute the full page/D3 interaction.
- `src/ui/webview/graphPerformanceScript.test.ts:49–103` executes the shipped helper string in a VM with fake frames/time/simulation to check yielding, tick/time/cooling limits, pause/resume, replacement cancellation, and failure cleanup. `:105–140` checks topology invalidation, prose reuse, LRU/node bounds, and pending-state retention; `:142–165` checks mode-specific drag behavior. These do not prove actual group switching, frame latency, or complete page visibility behavior.
- `src/services/knowledgeGraphService.test.ts:60–100` protects independent repeated-symbol groups and group-specific lookup; `src/ui/webview/graphWebviewClientScript.test.ts:30–38` protects provenance/evidence/path tooltip text. `src/services/structuralGraph/structuralAnalysis.test.ts:15–40` checks source-backed impact/path results, and `:60–75` checks aggregation limits/truncation/counts. `src/services/structuralGraph/structuralGraphService.test.ts:150–162` checks that an invalid read preserves its parse cause and file.

**Consequential gaps in the inspected tests:** real DOM/D3 tests for restoring pan/zoom and an unfinished layout after switching, hidden high-mode animations and cancelled auto-fit, actual selector disable/rollback rendering, structural replacement/reveal/refresh selection fallback, drilldown message-to-slice limits and errors, and source navigation are not supplied by the above assertions. A syntax check and a helper cache-state test are not substitutes for those integrated transitions.

## 2. Instructions

### Actual command and inputs

**Implementation.** The contributed `Knowledge: Generate Copilot Instructions` command is `knowledge.generateCopilotInstructions` (`package.json:85–89`). Its extension handler awaits `EntityCommands.generateCopilotInstructions()` and has an outer error notification (`src/extension.ts:679–689`). The command chooses `workspaceFolders[0]`, reports a localized no-workspace error and returns if absent, then collects graph data before calling the service (`src/ui/commands/entityCommands.ts:1255–1267`). It does not ask for a project, destination, graph group, template, or content preferences.

`EntityCommands` constructs `AIIntegrationService` with entity, relation, and observation services. `getGraphData()` obtains the KnowledgeGraphService snapshot, collects every snapshot entity's observations as entity ID/name/content, and returns entities, relations, observations, and `sourceType: 'knowledge'` (`src/ui/commands/entityCommands.ts:23–63`). This snapshot deduplicates symbols across groups, unlike visualization's independent groups (`src/services/knowledgeGraphService.ts:67–118`).

However, the active service accepts `_graphData` and never consumes it. `generateCopilotInstructions()` only creates the destination directory, calls a no-argument Copilot builder, writes the returned text, and returns the path. That builder invokes `buildAgentKnowledgeRouterContent('en', '# VibeKnowledge Agent Instructions')`; the shared builder joins literal lines (`src/services/aiIntegrationService.ts:71–82`, `src/services/aiIntegrationService.ts:404–447`). Consequently:

- Workspace root affects where bytes are written, not their text. Project name, selected editor/group, graph entities/relations/observations, source type, project packages/tech stack, and dependency statistics do not personalize current Copilot output.
- Interface locale affects command notifications, but Copilot text is always English. Cursor's active builder does use `getLocale()` for its title and router language (`src/services/aiIntegrationService.ts:101–109`, `src/services/aiIntegrationService.ts:404–408`).
- The service constructs a `DependencyAnalyzer`, and the class contains long-form Cursor builders, tech-stack/statistics helpers, and a scenario-template reader. They are not on the active Copilot or Cursor router path. The old builders call those helpers; the active builder does not (`src/services/aiIntegrationService.ts:45–50`, `src/services/aiIntegrationService.ts:101–119`, `src/services/aiIntegrationService.ts:259–264`, `src/services/aiIntegrationService.ts:378–381`, `src/services/aiIntegrationService.ts:691–711`). Editing those old helpers alone will not make current instructions project-specific.

**Inference.** Graph collection is currently an execution dependency but not a content dependency: if snapshot/observation collection throws, the UI catches the error before writing, even though the writer could generate the same content without graph data (`src/ui/commands/entityCommands.ts:1262–1284`). Adding personalization must decide how missing graph data, repeated groups, evidence, locale, and templates enter the active builder; their presence elsewhere in the class is not existing output behavior.

### File contract, shared paths, and failures

The service ensures `.github` exists using recursive `mkdirSync`, then synchronously writes UTF-8 to `<first-workspace>/.github/copilot-instructions.md`. Existing contents are overwritten: there is no read/merge, confirmation, backup, or atomic temporary-file swap in this path (`src/services/aiIntegrationService.ts:71–82`). A failure rejects the async service call. The command catches graph collection, generation, notification, document-open/display, and OS-reveal failures in the same block and reports a localized generation error (`src/ui/commands/entityCommands.ts:1262–1284`).

After a successful write, the notification offers Open file or Show in folder. The former opens and displays a text document; the latter runs `revealFileInOS` using the returned path; dismissing the notification does nothing further (`src/ui/commands/entityCommands.ts:1269–1281`). There is a display-only mismatch: the caller passes `.github/<basename>` to a success formatter that itself prefixes `.github/`, in both English and Chinese. The notification can therefore show `.github/.github/copilot-instructions.md`, while the actual destination and open/reveal actions remain correct (`src/ui/commands/entityCommands.ts:1271`, `src/i18n/en.ts:293`, `src/i18n/zh.ts:294`).

**Failure inference.** A post-write open/reveal failure does not undo the generated file despite the error wording. Directory creation may also have succeeded before a subsequent write fails. Since the write is direct and there is no rollback, callers cannot assume an existing file remains untouched after every write failure (`src/services/aiIntegrationService.ts:72–81`, `src/ui/commands/entityCommands.ts:1276–1284`).

The related paths share more than a filename:

- `generateCursorRules()` writes `.cursorrules`; its active builder uses the same router body with a locale-specific Cursor heading. Both active writers ignore graph content (`src/services/aiIntegrationService.ts:58–64`, `src/services/aiIntegrationService.ts:101–109`, `src/services/aiIntegrationService.ts:411–447`). A change to the shared router changes both products unless deliberately split.
- The UI's Generate All AI Configs has a non-cancellable progress notification, gathers graph data once, writes Cursor first and Copilot second, then offers either output for viewing. It calls the individual methods directly, not the service's bulk convenience method (`src/ui/commands/entityCommands.ts:1290–1334`). The separate programmatic `AIIntegrationService.generateAllAIConfigs()` performs the same sequential writes and returns both paths (`src/services/aiIntegrationService.ts:89–96`). Neither path is transactional: Copilot failure leaves the earlier Cursor write; Cursor failure prevents Copilot from starting.
- Switching AI scenarios can prompt the user to execute `knowledge.generateAllAIConfigs` (`src/commands/scenarioCommands.ts:62–81`). Yet the active router never invokes `readCustomAITemplate`, so choosing a different scenario and regenerating does not currently insert its template into either compact output. This is an existing UI expectation versus implementation mismatch, not evidence that the generator uses scenario content.

### Intended use versus work performed

The generated repository-level file is a policy for a future coding assistant: use the Knowledge Graph as an on-demand dependency navigator; start appropriate architecture/unfamiliar/cross-file/impact work with focused MCP `query_graph` and a token budget; expand with `get_entity`, `get_neighbors`, or `shortest_path`; request evidence only for relationship auditing. If MCP is unavailable/unhelpful, read `agent-context/index.md` and one matching group view. Do not load the complete human audit report by default; skip graph lookup for small known-file work; verify behavior in current source; never edit `graph.sqlite` directly (`src/services/aiIntegrationService.ts:432–447`).

These are instructions in a file, not actions performed by generation. The writer does not call an LLM or MCP, install/configure an MCP server, inspect the index or group views, create/refresh graph artifacts, edit SQLite, or verify that Copilot discovers or follows the file. Successful generation proves the write completed, not that referenced downstream resources exist or are usable (`src/services/aiIntegrationService.ts:71–82`, `src/services/aiIntegrationService.ts:404–447`).

### Tests and consequential gaps

**Inspected coverage.** `src/services/aiIntegrationService.test.ts:68–98` invokes the service in a temporary workspace with an `ai-template.md` marker and no graph argument, reads the returned output, and asserts MCP/index/single-group/evidence guidance and avoidance of the audit report. It asserts the marker, Tech Stack, Dependency Details, and Total Entities are absent. The neighboring Cursor test protects equivalent compact behavior (`src/services/aiIntegrationService.test.ts:100–119`). These tests use empty service stubs (`src/services/aiIntegrationService.test.ts:42–47`), demonstrating that this service-level happy path does not require functioning entity/relation/observation data access. The tests at `:121–163` exercise a private JavaScript runtime-detection helper, not project-specific content in the active instructions generator.

**Gaps and change implications.** The inspected tests do not exercise nonempty/different `GraphData` inputs, assert identical output across projects/locales/scenarios, or assert an exact compact size/output snapshot. The marker test alone does not establish every template/scenario path; the active call chain establishes non-use. They also do not test existing-file overwrite/merge policy, directory or write failures, first-folder selection, no-workspace handling, notification dismissal/open/reveal failures, the duplicated notification prefix, bulk partial success, or scenario-triggered regeneration. The source search for these generation APIs in test files found the service tests, not a command-level interaction suite. This is a bounded coverage finding, not a claim of measured whole-project coverage.

For a project-specific change, the high-risk contracts are which data truly enters the shared builder, whether the single-file and both bulk entry points remain consistent, whether Cursor intentionally changes too, and how user-authored existing instructions and partial failures are handled. Current tests explicitly reject several kinds of graph dump, so personalization must preserve or consciously revise that compact-router contract rather than merely enabling dormant long-form formatting.
