## 1. Visualization

### Command, host, and page

**Implementation facts.** `knowledge.visualizeGraph` is contributed as “Knowledge: Visualize Graph” and placed in the Knowledge Graph Explorer toolbar (`package.json:57`, `package.json:244`). Activation injects the product graph and structural graph services into `GraphView` (`src/extension.ts:242`). The registered command calls `GraphView.createOrShow(context.extensionUri)` and reports synchronous opening failures (`src/extension.ts:643`).

`GraphView` owns a singleton panel. Creating it enables scripts and retains its browser context while hidden; an existing panel is revealed in column one. An unchanged localized title causes a data message, not an HTML reload; a changed title causes `_update()` to replace the document. Disposing clears the singleton and disposes listeners (`src/ui/webview/graphView.ts:128`, `src/ui/webview/graphView.ts:157`, `src/ui/webview/graphView.ts:186`). The HTML loads packaged `dist/d3.min.js` through `asWebviewUri` under a nonce/CSP and embeds the performance helper script; this is a D3 SVG renderer, not the repository’s vis-network library (`src/ui/webview/graphView.ts:718`, `src/ui/webview/graphView.ts:751`, `src/ui/webview/graphView.ts:1137`, `src/ui/webview/graphView.ts:1303`). On browser load, `initGraph()` runs, then the page sends `ready`; the host replies with the effective performance mode and ordinary graph groups (`src/ui/webview/graphView.ts:205`, `src/ui/webview/graphView.ts:1205`).

Ordinary framework/module/feature views come from `KnowledgeGraphService.getGroups()`, not its deduplicated aggregate snapshot. Repeated symbols deliberately remain separate group occurrences; their group-local IDs remain resolvable for navigation (`src/services/knowledgeGraphService.ts:147`, `src/services/knowledgeGraphService.ts:192`). The host maps each group to a separate view model, adding observations, provenance, descriptions, evidence and structural drill-down keys/paths, and posts `graphData` (`src/ui/webview/graphView.ts:263`, `src/ui/webview/graphView.ts:456`). The page sorts by order then name, makes sidebar buttons with type/entity/relation counts, chooses the saved key if present or the first group, and renders only that group. Selecting a button is browser-local, not a host query (`src/ui/webview/graphView.ts:1372`, `src/ui/webview/graphView.ts:1423`, `src/ui/webview/graphView.ts:1449`). Rendering replaces the prior SVG children and clones nodes/relations before handing them to D3; preserving this separation avoids leaking simulation mutations into the incoming models (`src/ui/webview/graphView.ts:1479`, `src/ui/webview/graphView.ts:1504`, `src/ui/webview/graphView.ts:1552`).

### Advanced structural view

The advanced toolbar action sends `requestStructuralOverview` with the current aggregation level. The host reads the structural service and calls `aggregateStructuralGraph` with a limit of 80; boundary is the default, and the aggregate contract also supports file/community levels (`src/ui/webview/graphView.ts:75`, `src/ui/webview/graphView.ts:223`, `src/ui/webview/graphView.ts:324`, `src/ui/webview/graphView.ts:2091`). It converts aggregate nodes and counted relations into the same renderer contract, with `source: 'aggregate'`, raw files and relationship paths, and a stable `__structural_<level>` group key (`src/ui/webview/graphView.ts:518`). On `structuralGroup`, the browser removes all previous `__structural_` groups, appends the new group, selects it and shows a temporary node/relation-count status. There is only one structural view in the list at once, not a navigation stack (`src/ui/webview/graphView.ts:1293`, `src/ui/webview/graphView.ts:1401`).

Double-clicking an aggregate requests its raw slice. Double-clicking a raw structural node jumps to source. An ordinary node normally jumps to the entity; Shift-double-click or its context menu requests structural neighbors. Double-clicking an edge/label with a nonempty structural path requests the raw path (`src/ui/webview/graphView.ts:1601`, `src/ui/webview/graphView.ts:1686`, `src/ui/webview/graphView.ts:1761`). These are distinct messages and depend on preserving source tags, structural keys and relation evidence, not just visible labels.

The host’s neighbor request takes both directions at depth one, deduplicates relations, limits to 120 relations/80 entities, then filters dangling endpoints. Aggregate drill-down selects by explicit files when supplied, otherwise file/boundary identity, and limits to 80 entities/120 internal relations. Path drill-down validates a nonempty array and matches existing relations by source, target, verb and source location; it is not subject to those same explicit slice limits (`src/ui/webview/graphView.ts:340`, `src/ui/webview/graphView.ts:365`, `src/ui/webview/graphView.ts:407`, `src/ui/webview/graphView.ts:627`). Raw slices get hashed entity IDs but timestamp-based group keys, so a fresh request does not normally reuse the prior drill-down group’s layout (`src/ui/webview/graphView.ts:564`, `src/ui/webview/graphView.ts:643`).

**Failure boundary.** Missing services, bad/missing drill-down inputs and analysis exceptions become `structuralError` plus a VS Code warning; the page clears the loading indicator and displays the error without replacing the existing graph (`src/ui/webview/graphView.ts:450`, `src/ui/webview/graphView.ts:1296`). A valid but unmatched stored path can instead produce an empty slice: matching is a filter and does not assert that every requested hop still exists (`src/ui/webview/graphView.ts:349`). Thus preserving the distinction between an error, an empty graph and a bounded/truncated result matters.

### Performance selector and view memory

The setting is machine-scoped, defaults to `low`, accepts `low`/`high`, and explicitly does not change graph data (`package.json:325`). A browser selection applies immediately, re-renders the selected group if the mode changed, disables the selector and sends `setPerformanceMode`. The host validates it and writes the **Global** configuration, then always sends back the effective value; a failed save shows an error and the reply rolls the optimistic page choice back. Settings UI changes also cause a host reply, which re-enables the selector (`src/ui/webview/graphView.ts:150`, `src/ui/webview/graphView.ts:300`, `src/ui/webview/graphView.ts:1283`, `src/ui/webview/graphView.ts:2077`, `src/ui/webview/graphView.ts:2176`).

- **Low mode:** D3’s continuous simulation is stopped. An unfinished layout runs manual ticks in animation-frame batches, aiming at under 6 ms per batch and stopping at cooling, 120 ticks or 600 ms accumulated compute time. Geometry is explicitly redrawn because manual D3 ticks do not emit tick/end events. The budget is cooperative, not preemption of an expensive individual tick (`src/ui/webview/graphPerformanceScript.ts:46`, `src/ui/webview/graphView.ts:1933`). Particles and flowing agent-link classes are omitted, visual effects are reduced, and fit is immediate (`src/ui/webview/graphView.ts:1594`, `src/ui/webview/graphView.ts:1619`, `src/ui/webview/graphView.ts:1727`, `src/ui/webview/graphView.ts:2073`). Dragging stops layout, updates the dragged node directly, zeros its velocity and redraws its incident geometry; it does not restart physics (`src/ui/webview/graphPerformanceScript.ts:91`, `src/ui/webview/graphView.ts:1916`, `src/ui/webview/graphView.ts:1950`).
- **High mode:** D3 uses animated force layout unless hidden or a cached layout is already settled. Dragging reheats the simulation. Link particles use a single loop throttled to about 30 fps, alongside richer styles and fit transitions (`src/ui/webview/graphView.ts:1154`, `src/ui/webview/graphView.ts:1566`, `src/ui/webview/graphView.ts:1630`, `src/ui/webview/graphPerformanceScript.ts:97`). A first automatic fit is delayed one second; low mode fits on layout completion. User zoom/pan or dragging disables automatic fitting (`src/ui/webview/graphView.ts:1360`, `src/ui/webview/graphView.ts:1933`, `src/ui/webview/graphView.ts:1957`). Resize is debounced 120 ms; low mode fits, while visible high mode reheats to alpha 0.15 (`src/ui/webview/graphView.ts:1210`).

The relevant state has different lifetimes:

| Event/state | Actual behavior and causal boundary |
| --- | --- |
| Ordinary group switch | `vscode.setState` stores only `selectedGroupKey`. Before replacing the old rendering, a closure saves that old group’s geometry, zoom, alpha, settled flag and auto-fit flag. Returning to a compatible cached group restores those values (`src/ui/webview/graphView.ts:1453`, `src/ui/webview/graphView.ts:1479`, `src/ui/webview/graphView.ts:1556`). |
| Cache compatibility and eviction | Cache keys include the group key and a sorted topology signature of node IDs plus source/target/verb triples. Prose/evidence edits do not invalidate it; topology changes do. It stores geometry, not graph/evidence objects or velocities/fixed coordinates. Limits are eight groups and 2,000 total cached nodes, with LRU eviction; oversized, excessively linked or nonfinite-position entries are rejected (`src/ui/webview/graphPerformanceScript.ts:7`). |
| Reveal existing panel | If the localized title is unchanged, the document and cache stay alive, but ordinary `graphData` is sent and the selected group is re-rendered. That response replaces the entire list, so an advanced structural view disappears and its selected key falls back to the first ordinary group (`src/ui/webview/graphView.ts:157`, `src/ui/webview/graphView.ts:1372`). This also applies to the page’s Refresh button (`src/ui/webview/graphView.ts:2086`). |
| Hide/show without reissuing the command | Context is retained. On hide, particles and layout are paused, simulation stopped, transitions interrupted, fit/resize timers cleared, and current layout saved. On show, low layout resumes or an unfinished high simulation restarts, and particles may resume. A canceled high-mode auto-fit timer is not recreated by this visibility handler (`src/ui/webview/graphView.ts:176`, `src/ui/webview/graphView.ts:1254`). |
| HTML replacement / close then reopen | The layout cache is a new page-local object; only the group key uses the VS Code webview-state API (`src/ui/webview/graphView.ts:1141`, `src/ui/webview/graphView.ts:1150`). Title-triggered HTML replacement therefore loses page-memory geometry and structural groups. Closing disposes the singleton; a new panel is created, with no explicit transfer of its prior group state/cache. Do not promise restoration across close/reopen. The performance preference does survive because it is read from Global configuration (`src/ui/webview/graphView.ts:157`, `src/ui/webview/graphView.ts:186`, `src/ui/webview/graphView.ts:300`). |

**Change implications/inferences.** Preserve cache invalidation and bounded retention, save the *outgoing* group before replacing it, and preserve unfinished alpha/auto-fit state so a quick switch does not freeze an incomplete layout. Do not conflate a persisted preference, same-panel saved key and in-memory view geometry. Preserve cancellation and the one-loop invariant when switching groups/modes or hiding the page, otherwise old simulations/particles can compete with the new graph. Preserve D3-readable endpoints, group-local IDs and structural metadata while changing state representation. Rendering exceptions are caught by `selectGraphGroup` and stop work/show a dedicated error state; an empty group/list has separate cleanup (`src/ui/webview/graphView.ts:1378`, `src/ui/webview/graphView.ts:1458`, `src/ui/webview/graphView.ts:1465`). Initial `initGraph()` runs before that catch and before `ready`, so a missing/broken D3 asset can fail earlier than the normal render-error path (`src/ui/webview/graphView.ts:1205`, `src/ui/webview/graphView.ts:1303`).

These are mocked-host tests: they do not execute the page’s rollback, group selection or browser layout.

These protect responsiveness mechanics, not measured rendering performance.
- `src/ui/webview/graphPerformanceScript.test.ts:105`, `:119`, and `:133` cover topology/prose cache behavior, LRU/node bounds and preservation of unfinished state; `:142` contrasts low direct dragging with high physics. The unfinished-state test verifies stored fields, not a complete real-page quick-switch sequence.
- `src/services/knowledgeGraphService.test.ts:60` verifies repeated group symbols remain independent and group-local entity navigation resolves. `src/services/structuralGraph/structuralAnalysis.test.ts:15` covers source-backed impact/path results; `:60` covers bounded, counted aggregation. Those algorithm/service tests do not exercise advanced-toolbar messages, raw-slice conversion, replacement/fallback or host warning handling.
- `src/ui/webview/graphWebviewClientScript.test.ts:6` executes relation-tooltip formatting including provenance, evidence and a raw-path affordance, protecting a rendering dependency.

Consequential gaps in the focused tests are end-to-end group/zoom restoration, structural-view loss on reveal/refresh, actual hidden-page/particle/transition behavior, empty/error recovery, repeated mode switching, locale-triggered reload and large-graph responsiveness. The supplied focused tests do not establish these browser lifecycle contracts; no tests/builds were run for this assessment.

## 2. Instructions

### Command, real inputs, and output

**Implementation facts.** The UI contribution is `knowledge.generateCopilotInstructions`, titled “Knowledge: Generate Copilot Instructions” (`package.json:86`). Its extension handler awaits `EntityCommands.generateCopilotInstructions()` and has an outer logging/error catch (`src/extension.ts:680`). Activation constructs `EntityCommands` with entity, relation, observation and product knowledge-graph services, and the command object constructs its `AIIntegrationService` (`src/extension.ts:245`, `src/ui/commands/entityCommands.ts:23`).

The command chooses `workspaceFolders[0]`; no workspace means a localized error and immediate return. It does not ask for a project, destination, graph selection or prompt. It calls `getGraphData()`, which takes the unified snapshot and visits each entity’s observations, assembling entities, relations, `{entityId, entityName, content}` observations and `sourceType: 'knowledge'`, then passes that payload with the first workspace’s filesystem path (`src/ui/commands/entityCommands.ts:43`, `src/ui/commands/entityCommands.ts:1255`).

The service’s real behavior is much narrower than those apparent inputs suggest: `generateCopilotInstructions(workspaceRoot, _graphData?)` makes `.github` recursively if absent, calls a no-argument content builder, writes UTF-8 `.github/copilot-instructions.md` synchronously and returns the path (`src/services/aiIntegrationService.ts:71`). The content builder calls the shared router with the literal English locale and `# VibeKnowledge Agent Instructions`; its body is a fixed array of strings joined by newlines (`src/services/aiIntegrationService.ts:404`, `src/services/aiIntegrationService.ts:411`).

| Apparent dependency/input | Effect on current Copilot generation |
| --- | --- |
| Workspace root | Determines the destination and filesystem success/failure, not file wording (`src/services/aiIntegrationService.ts:71`). |
| Graph entities, relationships, observations, source type | Collected by the UI but ignored by `_graphData`; no snapshot/prose/statistics are embedded (`src/ui/commands/entityCommands.ts:43`, `src/services/aiIntegrationService.ts:71`, `src/services/aiIntegrationService.ts:404`). |
| Entity/relation/observation services and `DependencyAnalyzer` | The service stores these and constructs an analyzer, whose constructor only stores references. They do not supply content on the active router path (`src/services/aiIntegrationService.ts:43`, `src/services/dependencyAnalyzer.ts:49`). The UI’s graph collection remains a real preceding cost and possible failure point despite being content-irrelevant. |
| Extension locale | Localizes command feedback, but Copilot content always uses English. Cursor content does consult `getLocale()` (`src/ui/commands/entityCommands.ts:1269`, `src/services/aiIntegrationService.ts:101`, `src/services/aiIntegrationService.ts:404`). |
| Workspace name, technology manifests, scenario/custom template, relation-display setting | Not consumed by this active builder. Rich CN/EN Cursor builders still contain project-name/statistics/tech-stack/template work, but the active Cursor entry calls the compact shared router instead (`src/services/aiIntegrationService.ts:101`, `src/services/aiIntegrationService.ts:114`, `src/services/aiIntegrationService.ts:259`). The dormant helpers read the current scenario, `aiConfig.maxRelationsDisplay`, and JS/Maven/Python manifests (`src/services/aiIntegrationService.ts:691`, `src/services/aiIntegrationService.ts:718`, `src/services/aiIntegrationService.ts:857`). Their existence does not mean Copilot generation detects a technology stack. |
| MCP availability, graph artifacts, model/API configuration | The builder writes advice mentioning these resources; it makes no MCP/LLM call, availability check, graph-artifact read or dependency-analysis call (`src/services/aiIntegrationService.ts:71`, `src/services/aiIntegrationService.ts:404`). |

**Inference.** Different projects receive the same Copilot text today unless code changes: there is no project-sensitive branch, locale lookup, timestamp or interpolation from `workspaceRoot`/graph data in its builder. Making the output project-specific is therefore an actual contract change, not merely fixing a parameter that is already used. Merely editing the dormant rich builders would not change this output.

### Shared generation paths and intended use

The shared router tells a *future coding agent* to use `query_graph` first for architecture/unfamiliar/cross-file/dependency/impact work when MCP is available, expand locally with `get_entity`, `get_neighbors` or `shortest_path`, and request evidence only for relation audits. It describes the fallback to `agent-context/index.md` and one matching group, discourages default loading of the complete human audit report, allows skipping graph lookup for small known-file tasks, requires verification in current source, and prohibits editing `graph.sqlite` (`src/services/aiIntegrationService.ts:435`). These are generated instructions, not actions the generator performs. The generator does not itself query MCP, install/configure Copilot, verify graph freshness, refresh graph artifacts, edit the database, or run tests.

`generateCursorRules` writes `.cursorrules` and uses the same `buildAgentKnowledgeRouterContent`, with a Cursor-specific title and English/Chinese locale (`src/services/aiIntegrationService.ts:58`, `src/services/aiIntegrationService.ts:101`). Changes to the shared router can consequently affect both products; changes solely to Copilot’s wrapper need not affect Cursor.

There are two “all configs” implementations to preserve: the service’s `generateAllAIConfigs` sequentially calls Cursor then Copilot and returns both paths (`src/services/aiIntegrationService.ts:89`), while the UI command does **not** call that convenience method. It independently collects graph data, runs those same two single-file service calls under noncancellable progress, and offers to open either file (`src/ui/commands/entityCommands.ts:1290`). A separate scenario-switch command can invoke the UI all-config command after the user accepts regeneration (`src/commands/scenarioCommands.ts:62`). **Inference:** that offer currently rewrites the same compact routers rather than incorporating the newly selected scenario, since neither active builder reads it. This is a consequential caller even though scenario templates do not affect content today.

### Existing destination and completion/error boundaries

There is no overwrite prompt, merge, backup, existing-file content read, atomic replacement or undo/rollback in the service. `writeFileSync` overwrites an existing instructions file, including user edits; only the directory has an existence check. Its synchronous filesystem failures reject the async method (`src/services/aiIntegrationService.ts:71`). **Inference:** a write failure can leave prior contents already truncated/partially written, and creating the directory is not rolled back. An existing non-directory `.github` also passes the existence check before the write fails. These risks become more important if project-specific output requires extra work around the write.

On success the UI offers “Open file” and “Show in folder”; it either opens/shows the returned path, invokes `revealFileInOS`, or does nothing further when dismissed. All those steps share the same `try` with graph collection and writing. Therefore a collection failure prevents the write, a filesystem failure prevents the success prompt, but an open/reveal failure can report “Failed to generate…” even though the file was already written. The command catches errors without rethrowing, so its outer extension catch is normally not reached (`src/ui/commands/entityCommands.ts:1262`, `src/extension.ts:680`).

There is also a presentation defect: the command passes `.github/${basename}` to the success formatter, and both locale formatters prepend `.github/` again. The displayed success path is doubled, but the actual path used for writing/opening is correct (`src/ui/commands/entityCommands.ts:1271`, `src/i18n/en.ts:293`, `src/i18n/zh.ts:294`).

For all-config generation, the writes are sequential and nontransactional. Cursor failure prevents Copilot; Copilot failure can leave `.cursorrules` already overwritten. Neither the service convenience path nor the UI path rolls the first file back, and the UI reports an overall error rather than partial completion (`src/services/aiIntegrationService.ts:89`, `src/ui/commands/entityCommands.ts:1306`, `src/ui/commands/entityCommands.ts:1332`).

### Existing tests and consequential gaps

`src/services/aiIntegrationService.test.ts:68` generates the Copilot file in a temporary workspace with an `ai-template.md` marker. It asserts the query-first/router guidance, focused fallback and exclusion of the marker, tech stack, dependency details and total-entity dump. With empty mocked entity/relation/observation services (`:42`), success also establishes that this direct service call needs no working graph-service methods. It exercises creation of the missing `.github` directory indirectly by reading the returned file. It does not directly assert the exact destination, provide populated `GraphData`, configure a real workspace/scenario, or compare different projects. In particular, the template-marker assertion should not be overstated as exhaustive scenario integration coverage: the mock has no workspace folder (`:16`).

The sibling test at `src/services/aiIntegrationService.test.ts:100` verifies compact query-first Cursor output and absence of its template marker/graph dump. Tests at `:121` and `:144` call the private JavaScript tech-stack extractor directly, checking that `@types/node` is not a runtime version and that engines/`.nvmrc` declarations are honored. Those protect a helper, not proof that generated instructions contain project/runtime information.

The focused suite lacks command-level tests for no workspace, first-root/multi-root selection, graph collection failure, open/reveal/dismiss handling, duplicated success-path text, and the distinction between generation and post-generation UI failures. It also lacks overwrite/user-edit preservation tests, permission/mkdir/write failures, atomicity, populated-graph invariance, Copilot locale invariance, scenario-triggered regeneration, and both all-config paths’ ordering/partial-failure behavior. A project-specific change should explicitly decide how much of the compact-router/no-dump contract to retain and test the chosen input-to-content behavior; otherwise tests of unused analysis helpers can give false confidence while shared Cursor output or file safety regresses. This is a source-based contract assessment, not a test execution result.
